Most application search setups force a trade-off: settle for simple text filters, or manage a separate search cluster like Elasticsearch with complex synchronization pipelines.

In a new video course on the freeCodeCamp.org YouTube channel, I demonstrate how to run an entire production-grade search pipeline inside PostgreSQL. By pairing lexical keyword matching with dense vector embeddings in a single database, you eliminate external dependencies while preserving ACID guarantees for your search index.

Search queries usually demand two different retrieval behaviors. Exact queries like "Apollo 13" require precise keyword matching, which keyword engines handle best. Conceptual queries like "animals that make their own light" describe an idea without naming bioluminescence, which is where semantic vector search excels. Hybrid search executes both strategies simultaneously and uses Reciprocal Rank Fusion (RRF) in SQL to merge the results into one ranked list.

In this course I build a complete full-stack search application over 240,000 Simple English Wikipedia articles. The tutorial covers setting up the pg_textsearch extension for corpus-aware BM25 ranking, storing 384-dimensional sentence embeddings with pgvector and pgvectorscale, and profiling query plans with EXPLAIN (ANALYZE, BUFFERS). Until now, the packages were scattered across multiple repositories, with their own version and lifecycle. Gotrue was on v6.x.x, Realtime on v7.x.x, while the main package was on v1.x.x.

This package also follows lockstep-versioning, and therefore starts at v8.0.0 as well.

Browsers have also allowed importing CSS files as CSSStyleSheets with type: "css" for a few years now.

To support importing these files, people might use ambient module declarations in TypeScript using a wildcard pattern (e.g. *.css).

This is okay, but it doesn’t work for all environments as it doesn’t account for import attributes at all.

You might ask why this is an issue – at first glance, it seems like the only problem is that it just allows people to accidentally leave off an import attribute.

But that is still a problem worth fixing. Another issue is that it becomes repetitive. With import attributes, the entire issue is that the runtime cares about the attributes, not the file extension. We shouldn’t have to re-declare a pattern for both .txt and .md files if both were going to use type: "text".

But a major issue is that runtime environments may support different import attributes entirely, and may act differently depending on whether they’re present. For example, bundlers might use a build-time feature called CSS Modules as the default behavior when importing .css files, but specifying the browser-supported type: "css" in the import statement will override this behavior and ensure the .css file is brought in as a CSSStyleSheet object.

That’s why TypeScript 7.1 introduces support for import attributes in ambient module declarations. You can now declare the following in your TypeScript projects, get an error if you try to import a file without the required import attributes, and get the correct type based on the import attributes.

Note that imports matching these declarations are not validated against files on disk. As is currently the behavior when an import matches an ambient module declaration, failed lookups will be reported at runtime or during a bundler’s build process.

Also note that these declarations are not shipped as part of the TypeScript built-in libraries. We recommend libraries not include them in their published packages, and end-users will need to declare them in their own projects if necessary. That will provide end-users with flexibility on how the global scope is configured (e.g. lib.dom.d.ts versus @types/node) and will prevent conflicts with built-in declarations in the future.

Source phase imports are a proposed new feature in ECMAScript. The feature introduces a new source modifier/keyword that follows the import keyword. Only default imports can be written with import source.

The idea with this feature is that when we use import source, we’ll get back an object that represents the module after it’s been parsed and analyzed by the runtime, but before its imports have been loaded (and therefore, before they have been validated or linked against other modules, and before any code contained in the module can run). This object on its own is kind of “inert” – it’s an instance of something called an AbstractModuleSource which is eventually meant to be imported or instantiated.

For WebAssembly (wasm) imports, that object will be an instance of a WebAssembly.Module. What’s useful with these objects is that they can be passed directly into WebAssembly.instantiate.

WebAssembly source imports are already supported in recent versions of Node.js.

At the moment, you can’t do much with a source import of a JavaScript file. The spirit of the proposal implies at some point we might be able to pass a JavaScript module source directly into an import() call.

Another part of the idea with JavaScript source imports is that, over time, we may gain other features that will allow us to be able to customize behavior around how modules are loaded and instantiated, similar to how we did with WebAssembly.instantiate above. But we’re not there yet, and in fact, many environments and tools still don’t currently support JavaScript source imports in the first place.

Source imports aren’t limited to import statements though. You can also perform a dynamic source import as well via the import.source meta-property function.

Source imports retain identity. That means you can use them in Maps and Sets, or compare against them reliably.

When using import source, every imported module has the type AbstractModuleSource, a new global type in lib.esnext.d.ts. You must have an appropriate --module setting (i.e. esnext, nodenext, or preserve) to use source imports, as well as the appropriate esnext option in --lib or --target.

A straight line equation is a good place to start understanding how a neural network works. It's what we explored in my previous article, How Neural Networks Work – Explained Using the Straight Line Equation (y=ax+b).

But, what if the relationship between the input and the output isn't linear?

We all know that in the real world, the data doesn't always follow a straight line pattern. This is where things start getting interesting: sometimes a single rule isn't enough to describe the relationship between the variables.

That’s where non-linearity comes in. It allows neural networks to capture changing behaviour in data.

In this article, we'll explore the concept of non-linearity that can capture complex relationships in data. Using a simple example, we'll try to understand piecewise linear curves, ReLU functions, S-shaped curves, and sigmoid functions in relation to how they help neural networks learn patterns that a straight line can't describe.

The biggest thing I would recommend is: stop one-shot prompting.

#586. How Wearables Can Adapt When Pregnancy Changes a User's Regular Baseline

📅 Oct 20, 2026  |  Category: Technology  |  Read Source →

Your smart ring or watch has many useful jobs, including learning your usual physiological patterns and showing you when they change.

Resting heart rate, heart rate variability (HRV), temperature, and breathing rate can all contribute to that picture, although each device interprets these measurements differently.

That works well until pregnancy changes what usual looks like for several of those metrics.

The first app I open every morning is Oura, so I know how much one score can shape my day. A low Readiness Score can make me feel like I've done something wrong, even when I haven't. Now imagine seeing that for weeks while your body is going through expected physiological changes.

That's what I want to look at here, and I've pulled in the research so you don't have to take my word for it.

What Pregnancy-Aware Wearables Still Need

Most wearables use a combination of personal trends and device-specific reference ranges to interpret your measurements. The problem is that pregnancy changes several physiological metrics, and a baseline established before pregnancy may not reflect what's expected at a particular stage of pregnancy.

Oura, for example, gives people who join while already pregnant a calibration window of 7 to 15 days so the app can establish a personal baseline. Its current support guidance describes a period of 7 to 14 days of consistent ring wear before Pregnancy Trends become available.

The distinction matters because a baseline established during pregnancy may represent that stage of pregnancy, rather than your pre-pregnancy physiology.

Pregnancy can change cardiovascular measurements quite early. Cardiac output, the amount of blood the heart pumps per minute, increases during pregnancy, as does heart rate. The magnitude and timing vary between individuals, so these changes shouldn't be treated as a fixed curve that everyone follows.

A 2023 study published in Sensors also discusses research showing that resting heart rate can rise by 10 to 20 beats per minute, with changes beginning as early as weeks 5 to 7. But that increase isn't universal, and the trajectory varies across studies.

A system that relies too heavily on pre-pregnancy measurements may interpret expected changes as unusual. But pregnancy doesn't make every abnormal reading harmless, either. The challenge is helping users understand what their data might mean without treating a consumer wellness score as a medical assessment.

Let's get into it. Much of this research involves small samples and different devices, so treat the numbers as observations from specific studies, not predictions of what will happen to everyone.

A study conducted at University Hospital Zurich followed 23 healthy pregnant women who wore a bracelet at night. Average resting heart rate rose from about 61 beats per minute at week 8 to about 67 by week 35. It sat around 66 between weeks 24 and 32 and dropped slightly near the end.

HRV, which measures variations in the time between consecutive heartbeats, declined across roughly the first two-thirds of pregnancy in this sample, then climbed back toward where it started. HRV is often used as one indicator of physiological recovery or stress, but it isn't a direct measure of either. Its interpretation depends on personal history, measurement methods, and other factors.

A WHOOP study involving active women, including research associated with West Virginia University, reported a similar pattern of declining HRV and rising resting heart rate. Activity levels affected how much these measurements changed. Regular exercise, therefore, doesn't necessarily prevent pregnancy-related changes in either metric.

WHOOP also shares a rower's account in which her average HRV went from 64 before pregnancy to 50 during the first six months. That's an individual example, not a typical trajectory for every pregnant person. Still, it raises an important question: what happens when a recovery score interprets a change from someone's usual HRV as a negative signal without enough pregnancy context?

A 2025 scoping review of six wearable HRV studies found a similar overall pattern: HRV tended to decline during pregnancy and move back toward pre-pregnancy levels postpartum. But the studies differed in their methods, and the findings don't establish one expected HRV curve for everyone.

This one is trickier because the results depend on what you measure, where you measure it, and when.

A 2024 study published in npj Digital Medicine analyzed Oura Ring data from 120 people, including 97 full-term pregnancies. After conception, nightly peak skin-temperature measurements rose above pre-pregnancy levels before gradually declining. Nightly lowest measurements followed a different pattern, dipping early in pregnancy and then rising towards delivery.

These were skin-temperature measurements recorded by a wearable, not direct measurements of core body temperature.

The Zurich bracelet study measured wrist skin temperature during sleep and found relatively little change across pregnancy. The authors discuss how skin blood flow and the conditions under which measurements are taken may help explain this result.

The two studies used different devices, measurement sites, and methods, so their results aren't directly interchangeable.

This is why "your temperature is up" doesn't mean the same thing in week 6 as it does in week 36. A useful wearable needs to account for the measurement method and the stage of pregnancy before interpreting a temperature trend. A change in skin temperature alone also can't establish whether someone has an infection or another medical condition.

In the Zurich study, breathing rate rose from about 12 breaths per minute around weeks 9 and 10 to about 16 around week 17, then eased down later. This was the pattern observed in that small sample, rather than a universal trajectory for pregnancy.

Sleep changes too. A 2026 study in Frontiers in Global Women's Health tracked 14 women with an Oura ring over 981 observation days. As pregnancy progressed, deep sleep began later and occurred less frequently, while time spent awake increased.

More deep sleep was associated with lower heart rate and higher HRV, while REM sleep showed the opposite associations. These are associations, not proof that one sleep stage causes a particular cardiovascular response. The sample was also small, so the findings need further study.

Still, the results raise a practical question. An app that treats reduced deep sleep as an isolated negative signal may fail to communicate how sleep patterns can change during pregnancy. A sleep score should help users understand their trends, not imply that every change represents poor recovery.

Several major wearable companies now offer pregnancy-related features, although their approaches differ.

Oura launched Pregnancy Insights in August 2025. It tracks temperature trends, resting heart rate, HRV and respiratory rate across pregnancy, with pregnancy-specific context to help users interpret these measurements. Users can also record symptoms and experiences, including nausea and Braxton Hicks contractions.

Oura's Pregnancy Insights documentation describes the feature's introduction, while its support guidance explains how pregnancy trends and Readiness contributors are presented.

WHOOP has its own Pregnancy Insights. Users enter their due date to receive weekly guidance, and the feature provides pregnancy-related recovery context for up to 12 weeks postpartum. WHOOP also makes clear that its wearable can't detect or diagnose pregnancy. Its pregnancy coaching guide explains the feature and its intended use.

Apple added pregnancy-related tracking support with watchOS 11 and iOS 18. After a user logs a pregnancy in the Health app, Cycle Tracking can display gestational age on Apple Watch. Apple also prompts users to review high-heart-rate notification settings if the threshold is set below 120 bpm. Its guidance recommends turning off Cardio Fitness notifications during pregnancy and until 12 weeks after pregnancy ends.

I read that last recommendation as a reminder that standard health metrics and notifications may need different handling during pregnancy. But Apple's pregnancy logging and notification adjustments aren't the same as the pregnancy-specific trend analysis offered by Oura or the coaching offered by WHOOP.

These are useful steps, but the features shouldn't be treated as equivalent. Each company uses different measurements, algorithms, and forms of guidance, and none of these features replace clinical assessment.

This part is my wish list, based on the research and the gaps I see in how consumer wearables communicate health data.

ACOG's guidance says perceived exertion may be more useful than heart-rate targets for monitoring exercise intensity during pregnancy, since heart-rate responses to exercise can be regular or blunted. Its exercise guidance discusses the use of perceived exertion and the talk test.

Most strain and training scores rely heavily on heart rate. I'd like a pregnancy mode that offers a talk-test prompt or a quick effort rating alongside heart-rate data, rather than relying on heart-rate zones alone.

The aim shouldn't be to discard heart-rate measurements. It should be to give them the right context and help users interpret exercise intensity using more than one signal.

The research shows that HRV may fall and then rise, breathing rate can change at different stages, and temperature patterns vary depending on what the device measures. A system that relies only on recent trends could misinterpret a late-pregnancy rise in HRV as improved recovery unless it accounts for gestational age and the wider pattern.

Oura already places pregnancy trends alongside reference patterns observed during pregnancy, which is a useful step. I'd like every brand to build on this approach by comparing measurements with both the user's own history and appropriate reference ranges for the relevant stage of pregnancy.

That would require more than assigning every pregnant user the same expected curve. Companies would need validated reference data, consistent measurement methods and testing across different populations. They would also need to account for missing data and explain when the available measurements aren't enough to draw a clear conclusion.

Not every sensor measures the same thing in the same way. Oura measures skin temperature at the finger, while the Zurich bracelet study measured wrist skin temperature. The studies produced different temperature patterns, but differences in sensor location, measurement methods, and study design make a direct comparison difficult.

This is worth remembering when comparing your numbers with charts you find online from another device. A difference between two readings doesn't automatically mean that one device is wrong. The measurements may reflect different signals.

I'd like companies to explain what their sensors measure, how they process the data, and which comparisons are appropriate. That information would make it easier for users to understand what a trend can and cannot tell them.

Nausea, food aversions, Braxton Hicks contractions and plain exhaustion are exactly the kind of context that can help explain an unusual morning score. The Zurich study also linked self-reported feelings such as stress and tiredness with changes in HRV and breathing rate.

Oura already offers a way to record this context through its Pregnancy Insights symptom tags. In the app's Keeping Track section, users can log symptoms, activities, emotions and other factors that may affect how they feel during pregnancy. Examples include nausea, heartburn, vomiting, and Braxton Hicks contractions. These tags can be viewed alongside biometric trends, helping users identify patterns over time. They don't directly change daily scores or prove that a particular symptom caused a change in HRV, heart rate or sleep.

I'd like to see this feature go one step further with a one-tap check-in when a score changes noticeably, making it easier to record relevant symptoms at the time. That context could help users interpret their trends more clearly, without treating symptoms as a reason to dismiss unusual readings or replacing medical advice.

That doesn't mean symptoms should be used to dismiss unusual readings. Instead, they should help the app explain the data more clearly and identify when a trend needs attention rather than simply assigning a lower score.

Routine prenatal visits may be separated by several weeks, depending on gestational age and individual needs. Continuous wearable measurements could provide additional observations between appointments, but more data doesn't automatically lead to better clinical decisions.

Researchers have suggested that HRV could be worth studying as a potential signal associated with hypertensive disorders, while temperature measurements could contribute to research into infection detection.

But the evidence discussed here doesn't establish either metric as a validated standalone screening tool for these conditions. Larger studies and clinical validation are needed before such alerts can be relied on.

Getting an unexplained notification about a physiological change can cause a pregnant person unnecessary concern, particularly when an app can't establish whether that change is clinically significant. If pregnancy-related alerts are introduced, the wording needs care. The app should explain what changed, acknowledge uncertainty, and provide appropriate guidance on when to contact a healthcare professional.

Your baseline changes again after birth. WHOOP offers pregnancy-related guidance for up to 12 weeks postpartum, while Apple recommends turning off Cardio Fitness notifications during pregnancy and for 12 weeks afterward.

These product settings recognize that pregnancy-related changes can extend beyond delivery, but they shouldn't be interpreted as a universal physiological recovery timeline. The 2025 HRV review found that HRV tended to return toward pre-pregnancy levels postpartum, but individual recovery patterns vary.

A device shouldn't automatically treat your pre-pregnancy numbers as the only reference point on day one after birth. It should account for postpartum trends and allow time for measurements to change. And honestly, with a newborn at home, sleep data needs a fair amount of context too.

Baseline tracking only works if the baseline is allowed to change. Pregnancy affects several physiological measurements in patterns researchers are still working to understand, and Oura, WHOOP, and Apple have all introduced features to address parts of the problem.

My wish list is short: reference ranges by gestational week, exercise guidance that considers perceived effort, sleep scoring that accounts for changes in sleep patterns, careful alerts, and a gradual return to pre-pregnancy comparisons after birth.

The next step is to validate these approaches across larger and more varied groups of pregnant users. Wearables need to explain changes clearly, account for individual differences, and distinguish unusual measurements from clinically meaningful signals.

And if you're pregnant and wearing one of these devices, discuss health concerns with your care team regardless of what your wearable reports. These devices can provide useful context, but they don't replace prenatal care.

#38. Embracing Playful Imperfection With The CSS `random()` Function

📅 2026-10-20  |  Category: Technology  |  Read Source →

Brecht De Ruyte is a self-taught front-end developer located in Belgium with a passion for UX and Design. After more than a decade of working in tech, he … More about Brecht ↬

Weekly tips on front-end & UX.Trusted by 182,000+ folks.

In design, we love spending hours obsessing over consistency, grids, and alignment. But when I heard that the native CSS random() function landed in Safari and is rolling out in Chrome 156, I started wondering: where does randomness actually make sense on the web? Is it something we want in our design system? To find out, I did what I always do in doubt: I built a bunch of playful CodePen demos exploring organic typography, bouncing letters, splayed cards, and a punk fanzine.

As someone who loves building design systems and tinkering with CSS architecture, a big part of my day job revolves around control. We set up spacing scales, lock down typography, set up color tokens, and make sure everything aligns on a grid. Consistency is usually our bread and butter as design engineers and a proud badge of skill when creating design systems. If a card suddenly jumps 20 pixels to the left on a refresh, it’s not creative expression; it’s a bug that the project manager will log.

So when I first heard that the native random() function from the CSS Values and Units Level 5 spec was shipped in Safari, and is currently rolling out in Chrome 156 (with positive signals from Mozilla on Firefox as well), my first reaction was: that’s pretty cool!

And my second reaction was: wait… where would I actually use this without making a mess? How can I convince designers that random might be a good idea for a design system?

Because let’s be honest: why on earth would we want randomness in our stylesheets when we’ve spent the last decade trying to make the web more predictable? Even when using flexbox or fluid typography, we’re still trying to make things as aligned and uniform as possible.

If you step away from the browser for a second and look at physical things around you, nothing is ever truly uniform.

Take an old letterpress print: the ink bleeds slightly into the paper grain, some letters have a microscopic tilt, and the baseline isn’t always that straight. Or think about a deck of Polaroid photos dropped on a coffee table; those photos aren’t perfect, probably not straight either. Or what about lights flickering in a street at night? That little bit of analog messiness is what makes things feel alive, organic, and human.

On the web, we’ve gotten so good at pixel perfection that sometimes our interfaces end up feeling a bit sterile. We notice this even more now with rapidly created designs by an unguided LLM; we usually end up with the same sort of design we had 10 years ago. Everything is squared off, aligned, neat. It works, but frankly, it does get a bit boring.

Randomness in CSS doesn’t have to mean throwing your design system out the window. It’s about little imperfections and playfulness. Maybe let’s even call it fun.

To see what this actually looks like in practice, I spent a few hours tinkering in CodePen. The demos might feel a bit isolated, but I’m sure that many designers could make the best of this controlled chaos. But before we look at those demos, let’s take a look at the syntax.

The optional third argument is the step size. If you don’t add it, the browser picks from a continuous range. But if you provide a step, it rounds the random value to discrete increments:

This can be helpful in cases where you want things to jump around a bit, but you still want them to land on your pre-defined grid.

Normally, every time random() is evaluated on a property, it creates an independent random value. But there could be an example where you create a box that sets inline-size and block-size at random, but at the same time you need them to match so the element stays a perfect square.

In the latest spec, a bare dashed ident like --square-size shares its seed globally across every element in the document (which would make all cards identical). To keep width and height linked on a single element while giving each card its own independent size, the spec requires pairing it with the element-scoped keyword (e.g. --square-size element-scoped).

Any time you use animations, you have to respect user preferences for reduced motion:

If someone prefers reduced motion, it could also be a good idea to flatten the angles, not just the animations. I can imagine that a lot of random angles can also upset people while scrolling. Design should be fun, but never at the cost of accessibility.

Tinkering with random() over the last couple of days was a lot of fun. I’m still not sure if I’ll be able to convince my designer friends, but what I do know is that it brings a bit of joy.

Whenever we wanted a bit of organic randomness on the web, we had to make compromises: either pull in a JavaScript animation library, or write huge preprocessor loops that spit out hundreds of lines of static CSS. Having this built into the browser engine with zero JavaScript overhead is such a welcome addition.

We spent the last decade mastering consistency, tokens, and design systems. Now that we have that foundation in place, maybe it’s time to let a little bit of playful messiness back onto the web.

I really believe that the web is supposed to be fun.
