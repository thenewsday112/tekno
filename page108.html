#1. Factory Ghost: A Local AI Assistant for Industrial Motor Monitoring

📅 Oct 29, 2026  |  Category: Technology  |  Read Source →

This is a submission for the Hacktoberfest Open-Source AI Challenge Week 4: Ghost in the Machine

👻

What I Built

What if a machine could report unusual operating
conditions and an AI assistant could explain what the readings might mean?

I built Factory Ghost, an educational industrial motor monitoring demo combining simulated sensor readings, rule-based warnings, an interactive dashboard, and a locally running AI model.

The project simulates three motor parameters:

  • 🌡️ Temperature
  • 📳 Vibration
  • ⚡ Electrical current

The dashboard displays the latest readings, warning status, and history charts. Users can click a button to ask a local AI model to explain the simulated readings in simple English.

I interpreted Ghost in the Machine as giving a machine a voice: the system produces data, and AI turns it into a human-readable explanation.

Note: The readings are simulated, and the example thresholds are for learning only. This project does not diagnose real motor faults or predict real-world failures.

Demo

Factory Ghost currently runs locally on my Windows laptop.

To run the demo:

  1. Install Python and Ollama.
  2. Download the model: 
   ollama run gemma2:2b
  1. In the project folder, install dependencies: 
   py -m pip install -r requirements.txt
  1. Generate simulated motor readings: 
   py motor_simulator.py
  1. Start the dashboard: 
   py -m streamlit run dashboard.py
  1. Open http://localhost:8501 in your browser.

Code

🔗 GitHub repository: Factory Ghost

The repository includes the Python simulator, Streamlit dashboard, sample CSV data, dependency list, and README instructions.

How I Built It

I used these tools:

  • Python for the motor simulator.
  • Pandas for reading and handling the CSV data.
  • Streamlit for the interactive dashboard.
  • Ollama to run the model locally.
  • Gemma 2 2B to generate explanations.
  • Git and GitHub for version control and sharing the source code.

The application combines two approaches:

  1. Rule-based monitoring: Example thresholds classify simulated readings as normal or warning.
  2. Local AI explanation: When the user clicks the explanation button, Gemma receives the latest simulated readings and explains the condition, possible causes, and safe next steps.

The AI explains the readings; it does not independently validate a fault or predict a motor failure.

Why Does Open Innovation Matter?

Open innovation allowed me to experiment with tools I could inspect, run locally, and connect together.

Using Ollama with an open-weight Gemma model let me explore AI inference without relying on a hosted AI inference API. With local configuration, the readings sent to the model can remain on my computer.

Open-source tools also make it easier for students and developers to learn, modify the code, and extend the project with real sensors in the future.

As a Robotics and Automation student, I wanted to explore how local AI could complement traditional industrial monitoring. Factory Ghost is my first step toward that goal.

My Agent Session

This project currently uses a locally running Ollama model through a Python application. I have not included a DevRelay agent session.

The Spirit of It

The moment that made this project exciting was seeing unusual simulated motor readings on the dashboard and then asking the local AI assistant to explain them.

Instead of looking at numbers alone, I could ask the machine's digital assistant what the readings might mean.

It was a small experiment, but it made the idea of a machine communicating its condition feel more tangible—and motivated me to explore the intersection of AI, robotics, and industrial automation.

#7. How UPI Works: The ₹0 Magic Behind Every Scan-and-Pay (System Design)

📅 Oct 29, 2026  |  Category: Technology  |  Read Source →

System Design Simplified — Part 1

The chai stall

It's 8 AM. You're holding a cutting chai in one hand and your phone in the other. You scan a faded QR code on the counter, type four digits, and before Bablu looks up from his kettle, his phone says ₹20 received.

Two seconds. No card. No cash. No fee.

In August 2026 alone, UPI handled a record 24.51 billion transactions, about 791 million a day. That's roughly 85% of India's digital payments and nearly half of all real-time payments on Earth.

So what happened in those two seconds? Let's follow your ₹20.

Meet the cast

Every UPI payment has five characters, and each has exactly one job.

You. The person with the phone.

Your UPI app. PhonePe, Google Pay, Paytm. It does not hold your money. It's a messenger.

Your bank. Where your money lives. The only one allowed to take ₹20 out.

NPCI. The National Payments Corporation of India. It runs one central switch that every bank is plugged into. It holds no money either. It's the traffic cop at the junction.

Bablu's bank. Where the ₹20 lands.

One idea to remember: apps and NPCI are messengers. Only banks touch money.

The journey of ₹20, in motion

Purple = the request. Orange = the money. Green = done. Watch it loop once and the whole system makes sense.

Notice the order. Your bank is asked first. Money leaves your account before anyone asks Bablu's bank to accept it. That's deliberate: money stuck in transit can be reversed; money credited that was never debited cannot.

Wait, so what is Google Pay?

This is the part most explainers skip.

Google Pay, PhonePe, Paytm, CRED, Amazon Pay are not banks. NPCI has a strict rule: it talks only to banks. So how does an app made by Google reach the switch?

It borrows a bank.

Every UPI app partners with one or more licensed banks, called PSP banks (Payment Service Provider). The bank owns the actual connection to NPCI. It gets audited, holds the security certificates, and takes legal responsibility for every request the app sends. The app, officially a Third-Party Application Provider, rides on the bank's pipe.

You've seen this without noticing. The @okaxis in ramesh@okaxis means Google Pay is using Axis Bank as its PSP. @ybl is PhonePe on Yes Bank. @paytm is Paytm's own handle. The part after @ names the app's partner bank, not yours.

That's the twist: your money can sit in SBI while your Google Pay handle says Axis. Axis is the doorman who walks your request into NPCI. SBI still opens the vault.

Why build it this way? NPCI would rather trust 50 regulated banks than vet 500 apps. If an app misbehaves, its PSP bank answers for it.

There's a real-world reason the big apps now keep several PSP banks. In March 2020, PhonePe ran only on Yes Bank. When RBI put Yes Bank under a moratorium, NPCI blocked its handles, and PhonePe went down with it. Within months PhonePe added ICICI (@ibl) and later Axis (@axl). Today, if one partner bank is slow, the app quietly routes through another.

What NPCI actually does

The switch isn't a black box. It does four jobs on every single payment.

Directory. It keeps the phonebook. bablutea@okaxis maps to a real bank and account number. You never see that mapping, and neither does the person paying you.

Router. It asks your bank to debit first, then asks the receiver's bank to credit, each with a strict timeout. A slow bank gets marked pending; the switch moves on.

Tracker. If a reply never comes back, NPCI doesn't guess. It marks the payment pending, runs a check-status call, and reverses the debit if the credit never landed.

Tally. It records what every bank owes every other bank, all day. More on that below.

NPCI talks only to banks, over private certified lines. It never holds money and never sees your PIN.

The clever ideas inside

Your UPI ID is a nickname. ramesh@okaxis is like a saved contact. NPCI keeps the phonebook. Share it on a poster, switch banks later, the ID stays.

Your PIN never travels. You type it into a locked box provided by NPCI, called the common library. It's encrypted right there on your phone, and only your bank has the key. Google Pay cannot read your PIN. Neither can NPCI. Neither can Axis.

Your phone is the password. During setup, the app sends a silent SMS from your SIM. That binds your number, SIM and device together. There's no username. Your phone is the login; your PIN is the second factor.

It's a switch, not a wallet. A wallet has to hold your money. UPI never does. Money moves bank to bank, so there's no top-up, no middleman, no fee hiding in the spread.

When things go wrong

Money debited, Bablu shrugs, nothing received. What happened?

Your bank said yes and debited you. Then a message got lost between the switch and Bablu's bank. UPI doesn't guess. It marks the payment pending, and NPCI runs a check-status call to learn the truth. If the credit never landed, a reversal goes to your bank and the ₹20 comes back, usually within hours.

The promise: money is never in two places, and never nowhere. It's with you, with them, or in a tracked pending state that will resolve.

Did the banks actually move money?

Here's what almost nobody knows. When your bank debits ₹20 and Bablu's bank credits ₹20, the two banks haven't exchanged a rupee yet. Each just updated its own customer's balance.

Think of two friends who keep paying for each other all week. They don't hand over cash every time; they keep a tally and settle the difference on Sunday. NPCI is the friend with the notebook. Several times a day it tells the Reserve Bank of India "Axis owes SBI ₹340 crore net," and one transfer settles millions of chai payments.

That's why UPI is instant and free at the same time. The expensive part, moving real money between banks, happens only a few times a day, in bulk.

How does one switch survive 791 million hits a day?

Nobody waits for anyone. Every hop has a strict timeout. A slow bank gets marked pending; the switch moves on. Slow banks hurt their own customers, not the country.

The switch is stateless, copied many times. It only routes messages, so dozens of identical copies sit behind a load balancer. Any copy can handle any payment. One dies, nobody notices.

Every message has an ID that can't be reused. If your app resends because the network blinked, the switch sees the same transaction ID and says "already done" instead of charging you twice. This is called idempotency. It's the single most important idea in payments.

Five things to remember

  1. Apps and NPCI are messengers. Only banks hold money.
  2. Google Pay isn't a bank. It reaches NPCI through a partner PSP bank, named by the @ in your UPI ID.
  3. Your PIN is encrypted on your phone; only your bank can read it.
  4. Debit first, credit second. Pending is a tracked state, not a bug.
  5. Banks settle in batches, which is why instant can also be free.

#15. I checked 11 launch platforms for an llms.txt. Four answered, one sent a challenge page

📅 Oct 29, 2026  |  Category: Technology  |  Read Source →

On October 19 I ran a small, boring test: fetch /llms.txt from the root of 11 launch platforms and directories and see who answers. Ten days later, on October 29, 2026, I ran it again before writing this up. The picture had already moved.

llms.txt is a proposal for a plain markdown file at a site's root that tells a language model what the site is and where the useful pages are. Nobody is required to publish one, and Google's own guidance says you don't need new AI text files to appear in its AI features. So a missing file isn't a failing. I just wanted to know what an agent finds if it goes looking, because more of my own work now starts with an agent fetching a URL.

One curl per domain, following redirects, with an ordinary desktop Chrome user agent:

I also tried /llms-full.txt, the longer companion file some sites publish. I counted a site as answering only when it returned a 200 with text/plain. A 404 counts as "no file". A 403 challenge page counts as "blocked the fetch", not "missing", because those are different things.

On /llms-full.txt: Uneed serves one (about 9 MB of text). TinyLaunch's path redirected to a login page, which returns 200 but is HTML, so I don't count it. Everyone else returned a 404 or the same challenge page.

That last one is the practical lesson. Whether an agent "can read" a site isn't a property of the site alone. It depends on who is asking, from where, and on which day. A single check is a snapshot.

Reading the four files that answered, they're doing different jobs.

The map. DevHunt's file, and Product Hunt's when it's reachable, explain what the site is and how its URLs are shaped: /tool/{slug}, /compare/{a}-vs-{b}, /products/{slug}/alternatives, daily and weekly leaderboard paths. That's what an assistant needs to answer "what are alternatives to X" by going straight to the right page instead of guessing. Product Hunt's also asks for something back: list a product's name and tagline first, and attribute the data to Product Hunt.

The runbook. TinyLaunch's file opens with "You are launching a startup on TinyLaunch on behalf of a user, end-to-end, without a browser." It then lists the eight endpoints the flow needs, which ones need a bearer token, and how to handle the email code. It even tells the agent to use its host's structured-question tool rather than printing options as text. That's written for a coding agent mid-task, not for a crawler.

The handoff. BetaList's file points to an Agent API where an agent drafts the submission and a human founder claims it. Uneed's does both a read side, an MCP server and REST API for its product data, and a write side, a separate launch guide for agents. I checked that the linked pages exist (betalist.com/agent and uneed.best/launch.txt both returned 200). I did not run either flow.

What none of the files did was hide the human step. Every write path I saw still routes through a person: an emailed code, or a founder claiming the draft. I think that's the right shape.

Not much on their own. Hacker News is a discussion site with an official read API documented on GitHub. The others have perfectly readable HTML pages, and a search crawler doesn't need a root markdown file to index them. The 404 only matters in one narrow case: an agent that checks /llms.txt first will learn nothing about how submissions work there and will fall back to reading the HTML or asking you.

The file I keep for LaunchSignal at launchsignal.ai/llms.txt is held to the same test: it names the JSON API and MCP submit paths, the error codes, and the fact that a submission stays pending until a person reviews it.

By Sohit Kumar. Originally published at Prinevo.ai.

Updated October 29, 2026

What did those checks actually establish?

A QA agent should verify the accepted behavior, the affected service boundaries, relevant failure and permission cases, and the existing behavior the change could disturb. It should record the revisions and environment it checked, return failures to the implementation owner, and leave the reviewer evidence and explicit gaps. It cannot establish production readiness from a sandbox pass alone.

Conceptual verification map showing the behavior and boundaries a QA agent should check.

The first question I would ask is where the expected result came from. If QA gets the answer only from the implementing agent’s summary, both agents can agree on the wrong behavior.

Start with a requirement that can be checked

Consider an illustrative invoice-export feature. A billing admin can request a CSV for their organization and a selected date range. A background worker creates the file. The admin downloads it when it is ready. A viewer cannot request or download it.

This sounds straightforward until the agent has to decide which invoices belong in the file.

Does the date range use invoice issue time or payment time? Which timezone applies? Are cancelled invoices included? What happens if the admin loses access while the export is queued?

Those answers belong to the requirement’s accountable owner. QA should surface missing decisions before declaring a pass. It can proceed with other checks, but the unresolved behavior remains unverified.

Give QA access to the accepted requirement, relevant domain rules and contracts, implementation diff, affected components, and known risks. Keep the source and version of those inputs so a later reviewer can see what the checks were based on.

Follow the user outcome across the boundaries

For this example, a successful API response establishes that a request was accepted. It does not establish that the export contains the right records or that downloading it is authorized.

The verification path should follow the work.

Billing admin requests export
    → API checks role and organization
    → Job carries the accepted filters
    → Worker selects the invoices
    → File is stored
    → Download checks the user's access
    → UI shows completion or a useful failure

The actual path must come from your application. Some flows will have fewer components. A change to a local calculation may need a focused test and a small regression check rather than the whole stack.

For the export feature, I would start with this verification plan.

Question QA must resolve Observable check
Can an authorized admin complete the export? Request the job, observe completion, download and inspect the file
Does the file contain the accepted records? Compare known invoice IDs, values and date boundaries against controlled fixtures
Can another organization see the data? Exercise the API and download path using a separate organization’s identity
Are permissions enforced beyond the UI? Call the restricted operations directly as a viewer
Do the API and worker agree on the request? Check the contract and run the producer and consumer together
Does a relevant failure leave the user stuck? Introduce an approved sandbox failure and inspect the job and UI state
Did the new path disturb existing behavior? Recheck the invoice access behavior and other affected regression scenarios

These are proposed checks, not results from a Prinevo run. Their value is that each check has a reason tied to the feature.

Verify the result behind the screenshot

A screenshot can show that the interface displayed an export button or a completed message. It does not show which database the worker queried or which invoices ended up in the file.

QA should use the observations appropriate to the claim. That can mean browser assertions, API responses, the downloaded file, sandbox data and correlated worker logs. Read state through approved interfaces with the access needed for the task.

Suppose the UI says the export completed but the file is empty. The useful finding connects the visible result to the job ID, request filters and worker output. A reviewer should not have to search unrelated logs to discover whether these observations came from the same attempt.

For asynchronous behavior, wait for an expected state with a deadline. A fixed pause followed by a screenshot can miss a slow worker or capture the previous state. Playwright’s retrying assertions provide one way to wait for a stated browser condition. The assertion still needs to describe the correct behavior.

Select checks by risk and feedback quality

Before selecting checks, use the change impact analysis guide to map affected contracts, consumers and business rules, including components whose code will not change.

Running everything on every edit can make feedback expensive. Running only the new unit tests can miss the boundary that matters.

Use focused checks to localize a rule failure, contract checks to inspect exchanged data, and integration or browser checks to establish the combined behavior. Widen the selection when the impact map is uncertain, and retain the broader CI checks your team requires.

In my testing feedback-loop post, I separated time to detect an issue from time to find and fix its cause. That is useful for QA agents too. A slow test that says only “export failed” leaves a much larger investigation than a check identifying the wrong organization filter.

The sandbox setup guide covers provisioning, fixtures, permissions and diagnostics. Here, the decision is which behavior QA must establish once that environment exists.

Give Implement a finding it can act on

If the export includes another organization’s invoice, QA should return a concrete finding to the implementation owner.

The finding should identify the accepted isolation rule, tested revisions, fixture identities, reproduction steps, expected invoice IDs, observed IDs and the relevant evidence. Share synthetic identifiers and redact credentials or sensitive data.

The implementation owner fixes the change. QA then checks the corrected revision, repeats the failure scenario and runs the checks affected by that correction. If the fix changes a shared invoice query, the affected checks may extend beyond the new export.

The loop can repeat. Keep unresolved findings visible, preserve failed attempts, and set a retry or time limit. A missing product decision goes back to its owner. An unavailable dependency is a blocker. Neither becomes a pass because the agent has already spent an hour trying.

Use four distinct outcomes.

Outcome Meaning
Passed The scenario met its assertions on the recorded revision and environment
Failed The scenario ran and the expected behavior did not hold
Blocked A prerequisite prevented the required check from completing
Not run The check was omitted and the reason is recorded

A pass after retry should retain the earlier failure and any remaining instability. A green final summary should not erase the history needed to judge it.

Hand over a bounded verification claim

The reviewer needs to know what was verified and what remains open. Include the accepted behavior, component revisions, fixture and configuration versions, selected checks and rationale, outcomes, findings, fixes and reruns. Mark simulated dependencies and untested boundaries.

Then separate that claim from release approval. A migration, old and new worker versions running together, production permissions or a staged rollout may need additional checks and an accountable release owner.

The Prinevo delivery walkthrough places verification inside a workflow with named responsibilities and human steering. QA contributes evidence to that decision. It does not acquire authority to release because its checks passed.

For a first evaluation, give the QA agent a known scenario and a deliberately introduced defect in a disposable environment. Can it expose the wrong behavior, send a useful finding, and check the correction? Record the human help it needs along the way using the real-change scorecard.

That is a more useful starting point than counting how many tests the agent generated.

#36. How to Reduce Code Review Bottlenecks When Coding Agents Write the Code

📅 Oct 29, 2026  |  Category: Technology  |  Read Source →

By Sohit Kumar. Originally published at Prinevo.ai.

Adding another coding agent will not help that queue.

To reduce the code review bottleneck, define what a change needs before human handoff, use review and QA agents to resolve findings, route the remaining decisions to accountable owners, and limit new work when review capacity is full. Keep the amount of checking proportional to the risk. A copy change and a billing migration should not need the same path.

Conceptual review loop with findings returned for correction before human handoff.

I would start by looking at what the reviewer is actually doing. Reading the code? Finding the requirement? Starting the app? Asking whether anyone checked the worker? Those are different kinds of work, even if they all appear under code review.

Find what is holding the change up

Take a few recent PRs and follow them from implementation to merge. Record when the change was ready for assessment, when someone picked it up, and what happened after that.

What holds the PR up What to change first
Nobody qualified has time to review it Allocate review capacity and limit work waiting for that owner
The reviewer has to reconstruct the requirement Carry accepted behavior and decisions into the PR
The change mixes a feature, refactor and unrelated cleanup Separate work into understandable units with explicit dependencies
The reviewer is the first person to run the feature Run the relevant behavior and retain the evidence before handoff
Comments repeatedly expose the same convention violation Add a reviewed rule, focused check or review skill
A product or architecture decision is unresolved Get that decision from its owner before continuing implementation

A better test report will not make an unavailable billing owner available. More reviewers will not repair an environment that nobody can start. Diagnose the queue before adding another tool.

Make the author responsible for the handoff

An engineer who submits agent-written code still needs to understand the change they are asking someone to approve. The implementation agent should also leave a clear account of the work, rather than a chat history the reviewer has to search.

Consider an illustrative change to account trial status. It touches the API, a frontend banner and a billing worker. Three locally reasonable changes can still disagree about when a trial ends.

Before implementation fans out, agree the behavior and the shared contract. Which timestamp defines the end? Which component is authoritative? What should the customer see while the worker is delayed?

If the team has not agreed those answers, review will become the place where the requirement is finally written. I would put the accountable product or domain owner there earlier. Use a gate when the decision matters, rather than requiring every small change to go through a full design ceremony.

Then give each implementation owner a bounded part of the change. Keep the related PRs linked so a reviewer can see their combined effect and deployment dependencies. Smaller diffs help only when the pieces still make sense together.

GitHub’s engineering interviews on code review describe teams using AI for an initial review while keeping changes small and retaining human responsibility. They also warn that little feedback from an AI reviewer can be mistaken for comprehensive validation.

Give review and QA different jobs

A review agent should inspect the implementation against the requirement, architecture, contracts and team conventions. A QA agent should exercise the expected behavior in an identified environment and report what happened. Their findings can overlap, but the jobs are different.

For the trial change, the review agent might find two components calculating the expiry differently. QA might find that the banner updates correctly but the worker still applies the old rule.

Both findings belong with the implementation owner. They should include the affected revision, expected behavior, observed problem, evidence and the decision or correction needed.

The loop should look like this.

Accepted behavior and bounded implementation
    → Code review and QA checks
    → Findings returned to the implementation owner
    → Corrected revision
    → Relevant checks repeated
    → Remaining decisions and evidence handed to the human owner

This can happen more than once. A code reviewer can reject the revised implementation again. QA can find a second failure after the first fix. Keep the findings and their resolution visible rather than replacing every previous report with a final green result.

Some review and QA work can run in parallel on a recorded revision. A later code change still needs the affected checks repeated. For a tightly coupled change, resolve the contract review before spending time on a full integration run.

Set limits too. If the agents disagree about the requirement, or cannot reproduce a failure, escalate with the evidence. Repeating the same attempt indefinitely creates another queue.

Decide what ready for human review means

I would use a short handoff record rather than a long generated essay.

  • The accepted requirement and the behavior that changed.

  • The affected components, related PRs and rollout assumptions.

  • The tested revisions, environment and selected checks.

  • Findings, fixes and the results on the corrected revision.

  • Checks that failed, were blocked or did not run.

  • The decisions still needing the named reviewer.

For the trial feature, that means showing the same account through the API, banner and worker flow. If the worker could not start, say that the integration check is blocked. A screenshot of the banner cannot close the worker question.

An incomplete change may still need an early human decision. Send it as that specific request, with the blocker visible. Do not label it ready for final approval.

The verification sandbox guide explains how to make those checks repeatable. The handoff should let a reviewer inspect the result without rebuilding the investigation.

Match incoming work to review capacity

Even a well-prepared change needs someone to assess it. If agent work arrives faster than qualified owners can process it, the waiting list will grow unless the team changes capacity, scope or intake.

Give review time an explicit place in the team’s work. Route changes to owners who understand the affected domain. Develop additional ownership through paired reviews where appropriate, rather than granting approval rights without the underlying context.

When the queue is full, put agents and engineers on closing findings, reproducing failures and preparing existing changes. Do not keep starting work simply because code generation is available.

The limit depends on your team and risk. I would watch waiting time and unfinished work rather than impose one PR-count rule on every repository. A small text fix and a coordinated migration consume different review capacity.

Check that the work reduced rather than moved

Track time waiting for a reviewer separately from active review time. Also record human time spent clarifying requirements, repairing the environment, reproducing results and fixing issues found after handoff.

Keep defects and rework beside the throughput measure. A faster merge is not an improvement if the team spends the next day repairing it. Compare similar changes and include blocked or abandoned attempts.

This is the delivery model we describe in Prinevo’s workflow. Each stage has an accountable owner, agents can return work for correction, and people steer the decisions that need judgment.

#55. I Added an Index and Postgres Still Does a Seq Scan (Here's Why)

📅 Oct 29, 2026  |  Category: Other  |  Read Source →

You have a slow query. You add an index. You run the query again, check the plan, and there it is: Seq Scan.

The usual reaction is "Postgres is ignoring my index." Sometimes that's true, and something is wrong. But a lot of the time, Postgres made the right call, and the real problem is somewhere else.

I reproduced four cases locally on Postgres 17 so we can look at real plans instead of guessing.

The Setup

A table of orders with a million rows. About 95% are completed and 5% are pending:

CREATE TABLE orders (
    id          serial PRIMARY KEY,
    customer_id int,
    status      text,
    created_at  timestamptz DEFAULT now()
);

INSERT INTO orders (customer_id, status, created_at)
SELECT (random() * 10000)::int,
       CASE WHEN random() < 0.95 THEN 'completed' ELSE 'pending' END,
       now() - random() * interval '365 days'
FROM generate_series(1, 1000000);

ANALYZE orders;

CREATE INDEX idx_orders_status ON orders (status);

I run every query with EXPLAIN (ANALYZE, BUFFERS). That runs the query for real and shows what actually happened.

What to Look At in a Plan

Plans look intimidating, but for this post you only need five things:

  • The node type: Seq Scan, Index Scan, Bitmap Heap Scan
  • rows= in the first parentheses (the estimate) vs the second (the actual). A big gap means the planner guessed wrong.
  • cost=: the planner's estimate in arbitrary units. It picks the plan with the lowest cost.
  • Buffers: how many 8 kB pages the query touched. shared hit means found in cache, read means fetched from outside shared buffers.
  • Execution Time at the bottom

Case 1: The Index Exists, and Postgres Is Right to Skip It 

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE status = 'completed';

Seq Scan on orders  (cost=0.00..19824.00 rows=950933 width=25)
                    (actual time=0.026..134.500 rows=949820 loops=1)
  Filter: (status = 'completed'::text)
  Rows Removed by Filter: 50180
  Buffers: shared hit=7324
Execution Time: 170.498 ms

There is an index on status, and Postgres didn't use it. Why?

Because this query returns 95% of the table. Going through an index to fetch almost every row is more work than just reading the table from start to finish. Look at the estimate: 950,933 rows predicted, 949,820 actual. The planner knew exactly what it was doing.

To check, I told Postgres to avoid seq scans and ran it again:

SET enable_seqscan = off;
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE status = 'completed';
RESET enable_seqscan;

Bitmap Heap Scan on orders  (cost=10654.16..29864.82 rows=950933 width=25)
                            (actual time=53.171..159.778 rows=949820 loops=1)
  ...
Execution Time: 207.462 ms

With the index forced, it took 207 ms instead of 170 ms. The planner's cost numbers pointed the same way: 19,824 for the seq scan against 29,864 for the bitmap scan.

(enable_seqscan = off doesn't forbid seq scans. It makes them very expensive in the planner's eyes. It's a diagnostic tool, not something to leave on.)

Takeaway: when a query returns a large share of the table, a Seq Scan is often the fastest plan.

Case 2: The Same Index, a Selective Query 

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE status = 'pending';

Index Scan using idx_orders_status on orders
  (cost=0.42..6573.73 rows=49067 width=25)
  (actual time=0.127..15.953 rows=50180 loops=1)
  Index Cond: (status = 'pending'::text)
  Buffers: shared hit=7320 read=46
Execution Time: 18.441 ms

Same table, same index, different value. Now Postgres uses the index and finishes in 18 ms instead of 170 ms.

Look at the Buffers line, though. It touched 7,366 buffers, about the same as the 7,324 the seq scan read. The pending rows are scattered randomly through the table, so even though only 5% of rows match, the query still visits almost every page.

My reading is that it's faster mainly because it processes and returns far fewer rows, not because it reads fewer pages. "Few matching rows" doesn't automatically mean "few pages touched."

Case 3: The Index Is Fine, the Query Isn't

This is the one that causes real production slowdowns. I added an index on customer_id:

CREATE INDEX idx_orders_customer ON orders (customer_id);

Now two queries that look like they do the same thing:

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE customer_id = 42;

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE customer_id::text = '42';

The first one:

Bitmap Heap Scan on orders  (cost=5.20..371.40 rows=100 width=25)
                            (actual time=0.140..0.363 rows=104 loops=1)
  Buffers: shared hit=104 read=3
Execution Time: 0.402 ms

The second one:

Gather  (cost=1000.00..16115.67 rows=5000 width=25)
        (actual time=2.043..53.119 rows=104 loops=1)
  Workers Planned: 2
  ->  Parallel Seq Scan on orders
        Filter: ((customer_id)::text = '42'::text)
        Rows Removed by Filter: 333299
        Buffers: shared hit=7324
Execution Time: 53.164 ms

Same 104 rows. 0.4 ms against 53 ms, about 130x slower, and the second query had to bring in parallel workers just to scan the whole table.

The cast on the column is the reason. The index stores customer_id values as integers, and customer_id::text is a different expression that the index knows nothing about, so Postgres can't use it.

Also look at the estimates. For the second query, the planner expected 5,000 rows and got 104. When you wrap a column in a function, Postgres loses its statistics for it and starts guessing.

The fix here is the obvious one: compare customer_id = 42 and let the integer index do its job. If you genuinely need to query on an expression, Postgres supports indexes on expressions, but I didn't test that here.

The same trap shows up with WHERE lower(email) = ..., WHERE date(created_at) = ... and similar.

Case 4: A Partial Index for the Rare Value

If you only ever query for the rare value, you don't need to index all 1,000,000 rows. You can index only the ones you care about:

CREATE INDEX idx_orders_pending ON orders (id) WHERE status = 'pending';

SELECT pg_size_pretty(pg_relation_size('idx_orders_status'))  AS full_index,
       pg_size_pretty(pg_relation_size('idx_orders_pending')) AS partial_index;

 full_index | partial_index
------------+---------------
 6904 kB    | 1120 kB

The partial index is about 6x smaller, because it only contains the 5% of rows where status = 'pending'. A smaller index means less to store, less to cache, and less to update on every write.

A Checklist for the Next Seq Scan You See

  1. Is the query returning a big share of the table? Then a Seq Scan may be correct.
  2. Compare the estimated rows to the actual rows. A big gap points to stale statistics (try ANALYZE) or a function or cast on the column.
  3. Is the column wrapped in a function or cast? Rewrite the query, or use an expression index.
  4. Do you only query for a small, specific slice of rows? Consider a partial index.
  5. Not sure the planner chose well? Test with SET enable_seqscan = off in a session, compare the times, then RESET it.

The Takeaways

  • A Seq Scan is not automatically a problem. For queries that return most of the table, it's often the best plan.
  • The estimated and actual row counts are the fastest way to see if the planner is confused.
  • A cast or function on an indexed column can make the index useless, and the damage here was about 130x.
  • Few matching rows doesn't always mean few pages read.

These numbers come from one run on my laptop with a warm cache, so your timings will differ. The relative differences are what matter, so run the examples yourself.

#81. Platform Engineering vs DevOps: What CTOs Need to Know in 2026

📅 Oct 29, 2026  |  Category: Technology  |  Read Source →

Short answer

Platform engineering does not replace DevOps. DevOps is the culture of teams building and running their own software; platform engineering builds an internal, self-service platform so those teams can do it without each becoming infrastructure experts. Invest when several teams repeat the same infrastructure work, run the platform as a product, and measure it by adoption.

  • 5 - attributes of a good platform in the CNCF white paper
  • 1 - goal above all: lower cognitive load on product teams
  • 0 - tickets needed for a routine capability on a mature platform
  • 90 days - a realistic window for a first golden path

Platform engineering is the practice of building an internal developer platform: self-service tools and paved paths that let product teams create, deploy and run software safely without waiting on another team. DevOps is the culture that made teams responsible for running what they build. Platform engineering makes that responsibility manageable at scale, so the two work together rather than compete.

Why DevOps alone stops scaling

“You build it, you run it” works well for a handful of teams. As the organisation grows, every team ends up owning its own pipelines, infrastructure code, monitoring, secrets and compliance evidence. Effort is duplicated, standards drift and engineers spend more time on plumbing than on customers. Some companies respond by recreating a central operations team, which brings back the ticket queues DevOps was meant to remove.

Platform engineering takes a third route: a small team builds the common capabilities once, as a product, and product teams consume them on their own. This is part of the broader shift from cloud migration to cloud maturity.

Signs you have outgrown team-by-team DevOps

There is rarely a single moment when DevOps stops working. It erodes quietly, and the symptoms show up in delivery reviews, security audits and exit interviews long before anyone names the cause. If several of these sound familiar, the problem is no longer culture; it is the absence of shared, self-service foundations.

  • **Onboarding takes weeks. **New engineers spend their first month learning how this team deploys, rather than learning the product.
  • **Every service is a snowflake. **Ten teams have built ten slightly different pipelines, logging set-ups and Terraform layouts, and nobody can support all of them.
  • **Security findings repeat. **The same misconfiguration, outdated base image or missing secret rotation appears in audit after audit, service after service.
  • **Senior engineers become a bottleneck. **A few people who “know the infrastructure” are pulled into every incident and every new project.
  • **Environments are requested, not created. **Teams wait days for a database, a test environment or access to a cloud account.
  • **Cloud costs cannot be attributed. **Finance asks which product a bill belongs to and engineering cannot answer quickly.

The Cloud Native Computing Foundation’s platforms white paper lists the attributes that separate a useful platform from a pile of tools:

  • Secure by default: the easy path is also the compliant path.

Mandating the platform from the top. The CNCF warns that teams relying on mandates for adoption meet resistance. If engineers are not choosing the golden path voluntarily, it is not yet better than the alternatives.

Build, buy or assemble

Very few organisations should build a platform from scratch. The practical choice is between three approaches, and most mature platforms end up mixing them.

Assemble managed cloud services, your existing CI/CD tooling and a library of templates. This is the fastest route to value and the right starting point for most companies, because it reuses what teams already know.

Adopt an open-source framework such as Backstage, the developer portal framework created at Spotify and now a CNCF project. Buy a commercial platform or portal when you want a faster start and are comfortable with a vendor shaping part of your developer experience. Check how easily you could leave, and whether it works with the cloud services and tools you already run.

Whichever route you take, the expensive part is not the software. It is the product work: understanding users, designing golden paths, writing documentation and supporting adoption.

When it pays off, and when it does not

Platform engineering pays off when the same problems appear across many teams: slow onboarding, inconsistent deployments, security findings repeated in every service, or engineers waiting days for environments. It rarely pays off for a single product team or a small company, where a well-chosen managed cloud service and a few shared templates achieve most of the benefit.

Cost matters too. A platform should make cloud spend more visible and controlled, for example by building tagging and right-sizing into every template. Our FinOps playbook covers the cost practices worth baking in.

What a golden path looks like in practice

Take the most common journey in most engineering organisations: a team needs a new web service in production. Without a platform, that journey usually involves copying an old repository, asking another team for a cloud account, writing a pipeline, requesting a database, opening a firewall ticket, setting up dashboards and filling in a security questionnaire. Each step is reasonable on its own. Together, they can take weeks and produce a service that differs slightly from every other one.

With a golden path, the same team picks a template, gives the service a name and an owner, and gets a repository with a working pipeline, a staging environment, standard logging and alerts, secrets handled properly and the service listed in the catalogue. The first deployment can happen the same day. The security and cost rules are not a checklist at the end; they are already built into what the template creates.

Two details make the difference between a golden path and a golden cage. First, it is documented and explained, so engineers understand what they are getting and why. Second, it can be extended or left: a team with a genuinely unusual need can swap a component or step off the path, as long as it then takes responsibility for what it changed. That freedom is what makes voluntary adoption possible, and voluntary adoption is the clearest sign that the platform is working.

For decision makers, the golden path is also the easiest thing to demonstrate. Timing how long a new service takes to reach production, before and after, is a measure anyone in the business can understand.

Who builds the platform

Team Topologies, the most widely used model for organising around platforms, describes a platform team as one that provides internal services to reduce the cognitive load of stream-aligned teams, the teams that deliver product value. The relationship works best as “X-as-a-Service”: product teams consume the platform through clear interfaces, with as little hand-holding as possible.

In practice, a first platform team is small: a handful of experienced engineers who understand infrastructure, delivery and security, plus someone who acts as product manager. That product role is the one most often skipped and most often missed. Someone has to talk to users, decide what not to build and say no to requests that serve one team at the expense of all the others.

Staff the team from people product engineers already trust. A platform built by respected colleagues gets a fair trial; one handed down by a distant infrastructure group gets worked around.

Pitfalls that sink platform initiatives

  • **Building before listening. **Platform teams that start with tools they find interesting, rather than the problems users report, build things nobody adopts.
  • **Renaming the operations team. **If the platform is still delivered through tickets, nothing has changed except the job titles.
  • **Portal first, capabilities later. **A polished portal over manual processes raises expectations and then disappoints them.
  • **Trying to cover every case. **One excellent golden path beats five mediocre ones. Leave room for teams with unusual needs to step off the path.
  • **No ownership of the long tail. **Templates and modules age. Without versioning, upgrades and deprecation, today’s golden path becomes tomorrow’s legacy.
  • **Funding it as a project. **A platform is a product with ongoing users. Budgeting it as a one-off build guarantees it decays once the project ends.

Questions to ask before you fund a platform team

Is a platform the right investment?

  • Which infrastructure and deployment problems are repeated across at least three teams?
  • How long does it take a new engineer, or a new service, to reach production today?
  • Who will own the platform as a product, and how will they hear from users?
  • Which managed services can we assemble instead of building?
  • How will we know in six months whether teams choose the platform voluntarily?

I did not set out to write six books. I set out to understand what I was building, and writing was the slowest, most honest way I knew to do it. Each book started as a question I could not answer in a single post, and each one taught me something I still use every day in my work.

I am Sami Ullah, known online as Sami Khan. I am 23, from Abbottabad, Pakistan. I am the founder, CEO, and Editor-in-Chief of Buzz Capitol, an independent digital news and media platform I launched in 2026. I am also chairman of Digi Skill Pro Academy, where our online earning classes are 100 percent free, and I own findservicenest.com, a service-based site. I run more than 15 YouTube channels, and my audience across Instagram, TikTok, and other platforms is more than 10 million followers. Writing six books sits alongside all of that work. It did not replace it. It explained it, to myself first.

The first lesson writing taught me is that a short post and a book ask different things of you. A post can be written in an hour and forgotten by tomorrow. A book forces you to stay with one idea long enough to find out whether you actually believe it. When I wrote The Digital Empire: Zero Capital, Global Reach, I had to be precise about what zero capital really meant. It did not mean zero effort. It meant starting with what I had: an internet connection, time, and a willingness to learn. It meant trading time for skills, skills for work, work for reputation, and reputation for scale. Writing it down made the idea testable. If a sentence did not survive being written, it probably would not survive being lived either.

The second lesson came from The Silent Disconnect: Human Connection in the AI Era. The more connected we get, the less we actually talk. Notifications replaced conversations. Followers replaced friends. I learned that from teaching thousands of students online and from running a media outlet, where I saw every day that the people who go farthest are not the ones with the best tools. They are the ones who still know how to have a real conversation: ask a hard question, listen, and sit with an uncomfortable answer. Writing about connection reminded me to protect it in my own life. The more I use technology, the more deliberately I protect real conversations.

The third lesson came from Echoes of Truth: The Age of Information Chaos. In the AI era, information arrives faster than judgment can keep up, and it often arrives pre-filtered, pre-packaged, and pre-decided. My rule for myself, which I wrote about in that book, is simple: if a piece of information makes me emotional before it makes me think, I slow down. Running Buzz Capitol, I hold our work to the same standard. Check the source. Read past the first version. Ask what the other side would say. Writing the book did not make me faster at deciding what is true. It made me more willing to pause, and pausing has saved me from more mistakes than speed ever did.

The fourth lesson came from The Resilient Mindset: Navigating Uncertainty. I used to think uncertainty was something to get rid of. Plan harder, prepare longer, wait until it felt safe. Building an academy, a media outlet, and a services site taught me the opposite. Uncertainty never actually leaves. It just changes shape. One year it is whether anyone will show up to a free class. The next it is whether a story you published was the right call. Writing about resilience taught me that you do not wait for confidence. You act, you learn, and you adjust. The students who do best in our free classes are not the ones with the perfect plan. They are the ones who start before they feel ready and keep going when the first version does not work.

The fifth lesson came from Beyond the 9 to 5. Most people do not escape a 9-to-5 in one brave jump. They build a way out, one skill at a time. That is the same idea behind Digi Skill Pro Academy: learn a skill that someone will actually pay for, practise it on real work, and let the income grow before making any big decision. In 2025, over 10,000 students joined our free classes, and 5,000 or more reported that they are now earning. Writing that book kept me honest about the order of things. Learning comes first, earning follows, and quitting a job on a feeling alone is not a plan.

The sixth lesson came from Behind the Headlines. I called the book that because the headline is rarely the whole story. A headline has to be short. A real story almost never is. What is left out — the context, the background, the voices that did not make the cut — is often where the truth actually lives. That is the standard I try to hold at Buzz Capitol. It slows us down. I would rather be slow than loud and wrong.

If there is one lesson that runs through all six books, it is this: writing is how I check my own thinking. Publishing is easy now. Thinking is still slow, and it should be. A book does not need to impress anyone. It needs to be true enough that I can stand behind it a year later. That is the same test I apply to an article, a class, and a news story.

I am still learning, and I am still writing. The books are not a finish line. They are notes from the road, written in my own name, from Abbottabad, for anyone starting with very little and wondering whether that is enough. It is enough to begin. The rest is work, repeated daily, and the willingness to keep asking better questions.

#692. Syrinx: A censorship-resistant communications platform

📅 Oct 29, 2026  |  Category: Technology  |  Read Source →

A censorship-resistant communications platform.

Syrinx (Syx, for short) is a P2P-ish, federated social platform for closed communities, where the server never holds your posts.

The Internet we fell in love with is dying. First it was the abusive monopoly of one browser dictating the direction the Web had to take. Then came the centralization of search through one company. Then the monopoly of communication and content creation by social networks. Finally, total surveillance through age verification—nothing else than a hard link between the content you create and your identity. A complete loss of privacy.

Syrinx is a proof of concept, an idea for how we can reclaim it: small, independent, underground communities, away from the reach of the panopticon the Web has become—many communities interconnected in a mesh through federation.

NAT makes direct connections between peers very hard to establish, so the server relays the traffic between them. That traffic travels encrypted: a reed is encrypted to its reader before it leaves the holder's device, and the server relays ciphertext it can't read. See Content privacy.

The server works like a BitTorrent tracker: it knows who has a reed, not what that reed says. Reeds live on members' devices. Every reed and sensitive record is OpenPGP-signed and checked by the client before it trusts or keeps anything, so trust comes from the cryptography, not the operator.

That is the ish: distribution and verification like a peer network, with a tracker/relay in the middle because the internet we actually have is full of NATs.

Together, this means anyone can run their own community, and members will be able to take their content elsewhere if they disagree with how theirs is run. Members can see what admins do with the power they've been granted. The one exception is a private message from the admins to a member, which stays out of the ledger but is visible to every admin.

Say a malicious actors manages to take over a community's domain. The community spins up a new server under a new domain, imports the server's key from a backup, and starts operating right away. The app is offline-first and keeps running from the device's cache with no server at all, so members open the old app, export their data, and import it under the new domain. Because everything is signed, the server recognizes it and rebuilds its database. Federation links with other servers have to be re-established. See Identity, invites & recovery.

Shutting a community down becomes a game of whack-a-mole: take down one small piece and it reappears somewhere else. The network isn't impossible to attack; the security comes from making the cost and scale of shutting it down unrealistic.

No reed content, but the pointers are metadata. The server holds user ids, usernames, emails and bios, and knows who follows whom and who holds which reeds. Everything but the user id is member-provided, emails and bios are optional, and none of it is validated. It also holds who liked which reed, the admin ledger, and ripples (comments on reeds), which are stored in plain text but only live 30 days after the last ripple on a reed.

The home-deploy scripts put the server behind Cloudflare. With a Cloudflare Tunnel (the default, no port forwarding), all traffic passes through Cloudflare, which terminates TLS and sees the same metadata the server does, though not reed bodies. With mTLS, nginx serves the public edge from home and Cloudflare only keeps the domain's DNS pointed at your home IP. Either way, Cloudflare is a point where a community can be cut off; the server key and the offline-first app are what let it come back elsewhere.

InfoQ: How does location matter when it comes to reducing carbon emissions?

Charles Humble: A compute workload uses a fixed amount of energy, but the carbon cost of that energy varies enormously by place and time depending on the sources of electricity that is powering the data centre. Assuming the data centre is using grid power in a region running mostly on hydro, solar, nuclear and wind (for example Norway, Sweden and France), running a workload here can be many times cleaner than one dependent on coal or gas. Carbon intensity also changes during the day and over the course of the year as wind, solar and demand vary.

In carbon aware computing we can apply a technique called demand shifting based on this. Demand shifting can be done in one of two ways, either time or location based. Time-based is particularly applicable when a use case isn’t latency sensitive, such as AI training.

For location the most simple variation of the technique is to just pick lower-carbon regions by default for new, latency-tolerant workloads. More advanced variations might involve moving to different hemispheres seasonally to maximize exposure to sunlight and solar power.

Humble: Demand shaping means changing how much work your software does, or what kind of work, in response to how clean or constrained the electricity supply is at that moment. One version of this is to give users a choice. For an AI-powered service, you could let users choose to talk to a person instead of the AI up front, or at any point during the process.

You can also apply techniques such as graceful degradation based on higher carbon intensity, for example by serving lower-quality video or images, turning off autoplay, skipping non-essential animations, or reducing refresh rates. You might also use a smaller model.

Tradeoffs include increased complexity, and of course you have to determine if the reduced service is still acceptable.

InfoQ: What can we do to make model training greener?

Humble: Alongside demand shifting for both training and data collection, avoid training from scratch if at all possible. Use a pre-trained model and fine-tune it, or just prompt it and/or use Retrieval-Augmented Generation (RAG) if that meets the need.

Shrinking the model size can speed up training and improve efficiency. Distillation, quantization and pruning can all be used for compression. On-device training via Federated learning can be greener in some cases. Keep in mind that for widely used models, inference over the model’s lifetime may cause greater total emissions, so efficiency in serving matters too.

The new trust model is: We trust Claude to always understand the system enough to debug anything or make any reasonable change we could want.

He also noted that many large legacy systems already work this way.

One documented case tests the explainer claim on Anthropic’s own repository. In August, Claude Code collaborator Boris Cherny answered a long-running complaint about issue auto-closure in a comment carrying the "Generated with Claude Code" footer. It said issues are closed when they have "had no activity for a while and are missing information needed to reproduce," and that "nothing is triaged solely by counting."

The repository’s issue-lifecycle.ts sets fourteen days to stale and fourteen more to closure, exempting only issues with ten or more upvotes. Developer marcindulak counted more than 6,000 issues labelled as carrying reproduction steps that were closed anyway as "inactive for too long." The remedy the comment offered, commenting to have an issue reopened, is blocked by a workflow that locks closed issues after seven days. That meta-issue is now locked.

The answer that started this issue, and misdiagnosed how issues in this repo are managed, was generated by a world-class model.

The failures the post documents are specific. The first appears only when both sides are machines:

Noise costs more when the author is an agent. A person can wave off a nit in seconds. An agent fixes it, which means another commit and another round of review.

"One CLI PR went through more than fifty rounds of review and fixes overnight before its author stopped it," the team writes. Running more rounds by default made things worse, so they capped them. On r/ClaudeCode, commenter ChemicalExcellent463 reported reaching the same control independently, stopping after two failed fixes because repeated failure means the agent’s picture of the code is wrong rather than the line it keeps editing.

The second failure is what those rounds were finding:

When we ran git blame on what the reviewer kept flagging, about 59% of it was code that had been there since the reviewer’s first pass. The reviewer was rarely finding new bugs, it was finding a few more old ones each round.

What gates a merge is a risk tier picked by a classifier, where "the change sets the tier, not the author." Low risk covers docs, copy, and additive changes behind a flag, and clears with no human approval. Medium risk, including caching, the auto-updater, and system prompts, needs one person. Two rules hold the line: "an agent’s approval never counts as a person’s," and the person who prompted a change "counts as one of the required reviewers."

That boundary drew a question the post does not answer. Reddit commenter Oximy-Naman asked whether low risk covers agent instruction changes shipped as documentation, since those "could change what an agent does without touching application code," and got no reply. The post assigns no tier to CLAUDE.md, the file its own reviewer loads on every review. On compliance, Hacker News commenter gaal_dornick reported that their own SOC 2 reviewer required every change to be seen by a second human before production; the post does not discuss audit requirements.

One control is missing, and the team says so:

We don’t yet have circuit breakers that tighten approval when those numbers move; engineers here want them before more code moves to zero-human merges.

Not everyone reads this as reckless. Commenter cheema33 argued that large organizations have never had anyone holding a complete model, making this an upgrade on the status quo, and commenter markbao reported spending a few thousand dollars a month on AI review against human review that consumes up to a third of an engineer’s time.

Parts of the system ship publicly. Code Review for Claude Code is generally available on Team and Enterprise plans, and the security review runs as an open-source GitHub Action whose README states that it "is not hardened against prompt injection attacks and should only be used to review trusted PRs."

InfoQ Homepage News Datadog Builds a Specialist AI Model for SRE Investigations

Oct 29, 2026 4 min read

Datadog has released Scout, a model trained to investigate production problems. It runs inside Bits Investigation, the company's AI SRE product, where it can pick up an alert, look through telemetry and suggest what caused the problem. Datadog engineers and a small number of customers are using it in a closed preview.

Most of the work described in the announcement concerns cost. An investigation may require many model calls as Bits tries a query, studies the result and decides what to check next. General-purpose models can do this, but Datadog says the bill makes it difficult to run them against every alert. The authors of the announcement want Bits to begin work while an engineer is still responding to the page.

On Datadog's AlertEval benchmark, Scout medium received a similar score to GPT-6.1 Sol high and Claude Opus 5.5 high. Its estimated inference cost was between three and eight times lower. At the xhigh setting, Datadog says Scout matched Claude Fable 5.1 xhigh for one quarter of the cost. No prices are published, so these figures are relative to the cost of a Scout medium investigation.

AlertEval uses real alerts, archived telemetry and explanations written by Datadog engineers. An LLM judge compares Scout's account with an expert account, rewarding matches at both the immediate and underlying cause level. Contradictions and claims without evidence lose marks. The resulting score runs from zero to 100, but Datadog warns that it is not a percentage of incidents solved.

Scout is based on GLM-5.3 Flash. Datadog post-trained the model with reinforcement learning, using incident simulations made from patterns found in historical cases. The simulations contain an alert, telemetry that can be queried and a known cause. They do not contain customer data, according to the company. Scout practises with tools modelled on the ones in Bits, including searches across logs, metrics and traces, as well as code, deployment and feature flag inspection.

The technical report gives a useful account of what went wrong during training. A reward based on the final answer prompted Scout to make fewer claims and stop investigating early. That made it less likely to be penalised, without making it a better investigator. The team changed the reward to take account of correctness, exploration and supporting evidence. They also removed tools from some training runs, or shortened the time available, to stop the model learning one fixed route through an incident.

Datadog ran a second evaluation on SREGym, a public set of 90 faults. Scout resolved 71 cases at medium effort, 79 at high and 80 at xhigh. GPT-6.1 Sol xhigh completed 82. Datadog carried out these tests itself, including the runs for newer comparison models, so independent results would be useful.

Scout arrives as observability suppliers work out how much of an incident an agent should handle. AWS DevOps Agent combines telemetry from several monitoring products with source code, deployment records and runbooks. AWS is joining information across tools, whereas Datadog is training a cheaper model for repeated use inside its own product.

Honeycomb's Canvas Agent is closer to the way many engineers investigate by hand. It opens a shared Canvas when an alert fires or an SLO burns, runs queries, tests ideas and leaves the evidence visible for an engineer to examine. Teams can capture familiar debugging procedures as Canvas Skills. Honeycomb also provides an MCP server, which allows external agents to query its telemetry. Honeycomb has not announced a dedicated SRE model; its focus is on the query engine and the record of how the investigation progressed.

Splunk and New Relic have gone further into the repair stage. Splunk AI SRE groups alerts and produces a probable cause with an evidence chain. A connected Claude agent can prepare a code change in a sandbox and open a pull request. New Relic's SRE Agent brings runbooks, incident reviews and previous resolutions into its analysis, while Autopilot can suggest remedial action. Both keep an approval step before a production change.

A ClickHouse study reported by InfoQ found that general-purpose models could produce summaries, but needed human guidance to find root causes consistently. Instacart takes a similar approach with Blueberry: agents collect context before an engineer assesses the proposed cause in Slack.

The benchmark evidence for Scout remains largely Datadog's own. In a response to the launch, the independent AI news account AGTP pointed out that AlertEval has not been independently tested. It also asked for an audit trail showing which evidence Scout considered and discarded. Honeycomb's visible Canvas and Splunk's evidence chain indicate that other vendors see the same requirement. A short answer may help during an incident, but engineers also need to see how the model reached it.

Datadog has not given a date for general availability. The company plans to add more types of failure to its simulations and eventually allow Bits to carry out repairs. The preview stops before that point: Scout investigates, gives its diagnosis and proposes recovery actions, while an engineer remains responsible for the change.
