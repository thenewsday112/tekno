#324. Cutting our inference bill by 68% by being obsessive about optimization

📅 Oct 19, 2026  |  Category: Technology  |  Read Source →

When we previously blogged about our AI code reviewer in April, an average review cost a palatable $1.19. By the end of August, that figure had shot up to about $2.46. We hadn't made any significant architectural changes: the coordinator was still handing work to the same set of specialist reviewers, and the same risk tiers decided how intensive of a review we gave.

Around mid-September we tasked our agents with working out where those tokens were going and cutting them â aggressively. With code quality at high effort, the average review now costs just $0.77, down 68% from the $2.43 it averaged over our two most expensive weeks before we started. Our main goal was to cut costs, but as part of this work we also managed to optimize the reviewer, so that the median review now takes just 1m 32s instead of the 4m 09s it took before.

About 40% of the savings came from changes and optimizations to the reviewer's code, and the rest from experimenting with which models we use and how much effort they put in.

The chart below shows the cost of an average review on each weekday since March. It holds the mix of review tiers fixed, so a day with more large reviews doesn't skew the data.

The cost per review steadily rose from $1.22 (March) â $1.44 (June) â $1.74 (July) and finally, to $2.32 (August). A small part of that is that more reviews landed in the most expensive tierÂ (59% of reviews in March and then 65% in August). We believe thereâs a simple answer for why: models are getting much better, and much more capable. Naturally, engineers are producing bigger, more complex changes which means more of them fall into our âfull reviewâ tier. We found that most of the cost increase actually came from model changes over those months, though.

At the start of August we moved every reviewer onto Anthropic models, which raised the cost per job from $1.38 to $2.03. We made this choice because we found that during our evals, Anthropic models performed better on this specific workload than other models.

Our internal standards reviewer, Codex, ended up on Claude Opus 4.7 due to a mix of performance and reliability. That took it from about $0.25 per review to $0.88 in August, which made it more expensive than the coordinator agent itself.

The cache hit rate also increased, going from 85.7% in April to 97% by September, while the number of tokens per review more than tripled, from 0.91 million to 2.99 million. A high hit rate on three times as many tokens still costs a lot more, even with the low cache read cost.

One of the biggest changes is that the reviewer now runs on OpenCodeÂ v2, which is a ground-up rewriteÂ from v1. Before switching all reviews over from v1 to v2, we ran every review in every canary repo on both v1 and v2 in a comparative shadow mode. The two agreed on the approval decision in 98% of the merge requests we tested, so we moved everyone over in one go in early October and removed the v1 code. Comparing two days with the same models, full-tier reviews on v2 finish about 13% faster. Weâre also currently experimenting with other ways to run our internal AI reviewer, including solely on Durable Objects using pi-durable. Weâre hopefully going to have more on this coming soon, so keep an eye out!

Right before we started focusing on cost optimization, our AI review spend was split by: output tokens making up about 23%, Â cache writes cost 43%, and cache reads cost 34%. This means that Â most of the money was going on context the model had already seen or was about to see again.

That makes complete sense when you look into a single session. The code quality reviewer made 16.6 large language modelÂ (LLM) calls per review on average and over those calls it wrote 72k tokens to the cache and read back 1.08m, because each call sends the whole conversation as context. A session's cost grows with both the number of calls and the size of the context, and over the last few months we had slowly increased both.

Itâs worth taking a few minutes to read about how Anthropic's prompt cacheÂ works. It works by caching parts of the prompt that have already been computed by the large language model (LLM). These are known as prefixes, because they only work on the messages at the start of the conversation, not mid way through or the end. This means that a future request can reuse an earlier prefix, up to the part of the conversation that changes from whatâs been cached. In our case, the harness tools, system prompt and messages at the start of our AI reviewer sessions rarely change, so theyâre a great candidate for prefix caching. A prefix is only stored where a cache breakpoint ends it. Writing to the cache costs 1.25 times the normal input price and reading costs 0.1 times, and an entry expires after five minutes unless something reads it.

That means we had two things to work on: make the first request of each session read from the cache instead of writing to it, and make each session use fewer calls.

Beginning September 14, the reviewer recorded the token usage of each reviewer's first LLM call, plus a hash of the first system block exactly as it was sent to the provider.

The data showed that the first request of a session found a cached prefix only 14% to 26% of the time. Every session starts with the same tool definitions and the same agent prompt, between 11k and 21k tokens that are identical in every repository we review, so almost all of them should have been cache hits.

The problem ended up being in how OpenCode v1 constructed the system prompt: It built one block containing our agent prompt, followed by an environment section with the working directory and the date, and placed the only cache breakpoint at the end of that block. The shared part was never stored on its own, so a review in one repository could never reuse what a reviewer ran in another repository had written.

On September 16, we added a marker to the end of every agent prompt and a plugin hook that split the block in two at that marker. The first half now ended on bytes that every job shares, and got its own breakpoint. To keep it that way we had to remove anything repository-specific from in front of it, so the list of available skills is disabled and tool descriptions can't change between jobs.

The same day we also moved our internal standards (Codex) reviewer's reference index (a table of internal standards, a skill file and a list of reference files) into its prompt. Until then every session had spent its first three turns reading those files with tool calls. Its LLM calls per run decreased from 15.9 to 9.6, and its cost per run dropped from $1.12 to $0.72.

Together these took the cost per review from $2.47 down to $2.02, and the drop was noticeable as soon as we kicked off the release.

The next set of changes went out on September 21 and 23. None of them were particularly impressive by themselves, but together they took about $0.20 off every review.

Removing tools that reviewers couldn't use

Sub-reviewers could see the tool that posts the final review comment. In 57% to 76% of sessions they tried to call it, were rejected by a check on the server, and spent another call recovering.

One wasted call gone, and about 2.9k fewer tokens of tool definitions in every sub-reviewer request

In 64% of the code quality reviewer's turns, the model made exactly one tool call, usually to read a single file.

Reviewers read the shared context and all of their patches in their first response, up to 150 KB

About two-thirds of our jobs are a second or later review of the same merge request, and often three of the reviewers have nothing new to look at.

On full-tier re-reviews, AGENTS.md reviews are skipped 56% of the time, performance reviews skipped 23% and documentation reviews skipped 13%.

OpenCode passed the result back to the model for one more turn, which read the entire conversation again to write a summary nobody saw.

Treating a slow reviewer differently from a broken provider

A reviewer that hit its time limit was treated like a provider failure and started again with the same time limit.

Together with longer time limits and lower effort, security reviewer timeouts went from 1.8% of runs to almost none

The most involved change was sharing one prefix between three reviewers. The code quality, security, and performance reviewers now send identical first requests with the same tools, a shared rules file, then the merge request with every patch included. Each reviewer's own instructions follow after that, and we make sure that one of them writes the cache and the other two read from it.

A cache entry can't be read until the response that wrote it has started streaming, and the three reviewers start at the same time. So the second and third wait for the first one's response to begin, for up to 20 seconds, before sending their own first request. It slows them down slightly and saves about nine cents per reviewer.

The coordinator had been running three model and effort combinations since August. On the same model, full-tier jobs on medium effort finished 20% sooner, so we dropped the other two. In a later randomized split, Opus 5.5 at medium showed no measurable change in review outcomes or critical findings compared with Opus 5, so we switched. Opus 5.5 at high effort cost more than Opus 5.5 at medium while not producing a meaningful increase in findings.

Opus 5.5 is cheaper per token than Opus 5, but price is only responsible for about $0.20 of the drop. The rest comes from sending and generating fewer tokens. Since the start of September cache reads per review are down 82%, cache writes down 54%, and output down 67%.

The most recent change was a new model. On October 3, we split every Sonnet reviewer 50/50 between Sonnet 5 and Sonnet 5.5. After two and a half days, Sonnet 5.5 was 62% cheaper per run for code quality, 58% for performance and 47% for security. The two models cost the same per token, so all of that comes from using fewer tokens. On full-tier reviews, the 5.5 reviewers posted about as many critical and warning findings as the Sonnet 5 ones, so on October 5 we moved all of them to 5.5.

On Sonnet 5.5 at medium effort, the code quality reviewer makes 1.7 LLM calls per run instead of 6.2, and more than half of its runs finish in a single call, which means they don't open any other file in the repository. At high effort it makes 3.4 calls per run. We were concerned that this made reviews shallower, which we cover in the quality section below.

To see whether more effort brings findings back on the larger tiers, the code quality reviewer has been split 50/50 between medium and high effort on 5.5 since October 5. After one day, high effort costs 61% more per run and posts 58% more critical and warning findings. That's about two cents per review, and the quality section below shows those extra findings are worth having, so we're moving code quality to high effort. The cost figures in this post assume that.

We weren't aiming to make reviews faster, but fewer calls also means less waiting, which means faster reviews and happier engineers.

The slowest reviews improved the most. In the four weeks before September 14, 37.9% of reviews took longer than five minutes and now just 0.7% do. The 99th percentile today is faster than three quarters of reviews were in April. Every tier got faster along the way with the median full-tier review going from 5m 16s to 1m 54s, lite from 2m 58s to 1m 14s, and trivial from 77 seconds to 30.

By August, the median review was 14% slower than what we reported in April and the 99th percentile 48% slower, so a good part of this work just got us back to where we had been.

A cheaper review isn't worth much if it also finds fewer problems, and the first chart here looks like that's what happened.

With code quality on Sonnet 5.5 at high effort, it posts 40% fewer critical and warning findings than it did in late August. Security and performance, which stay at medium effort, post 56% and 71% fewer. A fall in severe findings doesn't tell you on its own whether real problems are being missed or noise is being cut, so we looked at it from two directions.

First, we checked whether authors act on what the reviewer flags. For samples of critical and warning findings, we compared the commit that was reviewed with the author's next push, and counted a finding as acted on if the lines it pointed at had changed. Lines 30 to 40 away from each finding changed about 15% of the time in every period, which gives a baseline for edits that happen by coincidence.

Before the changes, authors acted on 34% of the code quality reviewer's serious findings. Now it's 59%. The reviewer flags fewer things, but those it flags are much more likely to lead to a change, so the number of findings that led to a change per 1,000 reviews is about the same. We now saw 132 against 145 before, which is within the margin of error. Across all four reviewers, serious findings that led to a change went from 229 to 321 per 1,000 reviews.

Second, we had two models from different providers judge a blinded sample of 657 findings from the three Sonnet reviewers, with the diff each one referred to and without knowing which period it came from. Disagreements went to a third model. Each finding was labelled important, minor, duplicate, wrong, or unverifiable, and its severity was marked as fair, too high, or too low.

Most of what disappeared was minor findings, plus some duplicates and findings the judges couldn't verify from the diff. Important findings per review went from 0.28 before to 0.30 now, and the intervals overlap. The bigger change was in severity. Before, the judges rated 0.46 critical or warning findings per review as more severe than they deserved. Now that's 0.14, a 70% drop and the clearest result in the research. Much of the drop in critical findings is the reviewer no longer calling minor things critical.

So the answer depends on the reviewer. For code quality at high effort, what disappeared was mostly noise and inflated severity, and it still finds about as many real problems as before. Medium effort did lose real findings. In the randomized split, code quality at medium led to roughly a quarter as many acted-on findings as at high, which is why we're moving it to high. Performance also lost real findings: the judges found about 64% fewer important performance issues per review, which in practice is about one fewer important finding every 24 full-tier reviews. Security fell by about a quarter, though that isn't statistically significant. Both are still at medium effort, and testing them at high is next.

Neither method is perfect. An author changing the flagged lines shows they did something, not that the finding was right. The judges are models too, and there are only 35 to 66 findings in each group. The "now" window is also only a day long. Even so, the two methods agree with each other, and neither suggests that code quality is finding fewer real problems.

Reliability has held up as well. Reviews that end without a verdict went from 0.79% to 0.27%, and security reviewer retries from 3.5% to 0.04%.

An average review now costs $0.77 instead of $2.43, and the median one finishes in 1m 32s instead of 4m 9s. The biggest single saving came from checking what actually reached the provider on each sessionâs first request, and finding a way to order those messages in a way that was as consistent as possible across commits, merge requests and repositories. The remaining cost savings came from relentlessly experimenting with different models and effort mixes, while making sure we put any preconceived bias for particular models aside.

Lower cost reviews didnât automatically mean worse quality, but it didnât automatically mean fine either. Code quality at high effort finds about as many real problems as before, with much less noise and far fewer inflated severities. Performance lost real findings at medium effort, and security may have, too, so testing both at high effort is next. If you run agents at any kind of volume, the two things weâd check first are whether each sessionâs first request actually reads from the cache, and whether your reviewers still find real problems at the effort level youâre paying for.

#479. The Thin Orchestrator: How We Made Our AI Agents More Reliable by Giving the Router Less to Do

📅 Oct 19, 2026  |  Category: Technology  |  Read Source →

We built a 1,300-line orchestrator that routes 20+ workflows to 14 specialized AI agents. It performs zero domain work itself. That’s the point.

When we first deployed AI agents to automate data column onboarding across Meta’s recommendation systems — a process spanning three code repositories, three programming languages, and up to six pipeline stages that must stay in sync — we did what most teams do: We built one smart agent that knew everything.

It worked in demos. In production, it started hallucinating.

The fix wasn’t better prompts or a bigger context window. It was giving the central agent less to do. We call this the thin orchestrator pattern: a router that owns sequencing and reliability checks, and leaves every domain decision to specialists.

Our pipeline is config-as-code: Python configurations drive C++ code generation, which feeds data processing services, which populate analytics systems. Onboarding a single data column requires coordinated changes across configuration registries, backend services, and data pipelines, and each column moves through up to six stages before its data arrives.

Our first approach was a single AI agent loaded with all domain knowledge, configuration schemas, code generation rules, pipeline routing logic, validation requirements, and population patterns for 10+ data sources.

The agent had everything it needed. That was the problem.

Past a certain context threshold, additional knowledge degraded rather than improved performance. The agent would cross-contaminate concepts, applying field naming conventions from one subsystem to another, or using a code generation pattern meant for one data source when populating from a different one. A preprint from the Windreich Department of Artificial Intelligence and Human Health at Mount Sinai found that orchestrated multiagent systems held 65.3% accuracy at 80-task batches where single agents fell to 16.6%, while reducing token usage up to 65-fold. The authors attribute this to the design’s isolation of tasks, which prevented context interference. We were experiencing the inverse, a single agent drowning in its own knowledge.

We also evaluated an alternative single-agent approach. Its success rate was 70-80% with manual prompt engineering per task: An engineer had to craft a custom system prompt for each specific job. Without that handholding, success dropped to 10-20%. This wasn’t a prompt engineering problem. It was an architectural one.

Our network is designed to match this hierarchy, with low-latency, high-bandwidth fabrics within buildings and an aggregation network connecting the building fabrics.

We work closely with Meta Superintelligence Labs to ensure the parallelism design, traffic patterns, and communication algorithms and software are optimized to minimize exposure of any network communication. This keeps the GPUs as busy as possible and not waiting on the network.

Both DSF and NSF are based on Meta’s FBOSS networking stack, giving us the control to rapidly iterate on and optimize the fabrics in Prometheus, and the visibility to operate these clusters at scale.

The Backend Aggregation (BAG) network is a multi-layer hub-and-spoke network that connects building-level fabrics across the Prometheus cluster, spanning 2 km to over 100 km. While Meta optimizes scheduling and infrastructure, NVIDIA addresses firmware, signal diagnostics, and memory handling. This transparency eliminates ambiguity and drives faster fixes across both organizations.

The transition from the H100 generation’s NVL8 architecture to NVL72 has fundamentally redefined our approach to infrastructure resilience. In the NVL8 era, the scale-up domain — the group of GPUs tightly coupled via NVLink for tensor parallelism — was limited to eight units. With NVL72, that domain expands to 72 GPUs, increasing the fault blast radius by 9X.

The larger scale-up domain is what gives NVL72 its bandwidth advantage, but it also makes the 72-GPU rack the unit of allocation we plan capacity around. Training parallelism maps most efficiently onto power-of-two group sizes, so each NVL72 domain runs a 64-GPU slice and keeps its remaining eight GPUs as in-rack spares. When a GPU fails, a spare takes its place immediately, so the job restarts from its last checkpoint instead of waiting on hardware repair, and the rack stays in the job. The in-rack redundancy pushes the effective rack fault rate down to the floor set by failures that can remove an entire pod; for rarer whole-rack faults we hold roughly 2% additional racks in reserve. For a 32,768 active-GPU training run, this means provisioning 523 NVL72 racks, or 37,656 GPUs, about 13% above the active footprint. Most of that margin (11%) falls out of the 64-of-72 slice geometry rather than being an absolute reliability tax.

Physical complexity further intensifies these reliability requirements. A single NVL72 domain incorporates 5,184 tuned differential-pair signaling links operating at 200 Gbps, each traversing multiple potential points of failure, including GPU SerDes, compute tray PCBs, cable cartridges, and switch tray interfaces. Maintaining consistent signal integrity across this dense fabric — at 200 Gbps per lane — represents an unprecedented engineering challenge at this scale.

Fault recovery addresses how we react to faults to minimize the impact on training time. Depending on the scope (i.e., blast area) of a fault we address it through two mechanisms:

Parallelism-Aware Fault Tolerance (PAFT): When a fault can be isolated to a data-parallel model replica, we reduce the impact of a hardware failure by allowing a single faulty replica to be taken offline, while the remaining cluster repeats that step and continues productive training. The compromised slice simply restarts on available spare hosts and resynchronizes, converting a potential total system halt into a minor, temporary reduction in aggregate throughput.

Checkpointing: When a fault blast area is larger than a data-parallel model replica, the entire job is restarted back to the last checkpoint; frequent checkpointing reduces the amount of work lost in these events. Our distributed checkpointing architecture asynchronously saves the model state — including gradients and optimizer data — to multi-tier storage. We use delta checkpointing and in-memory staging to ensure these saves happen with minimal impact on training throughput.

These two fault recovery mechanisms combine with a sparing strategy that utilizes pre-allocated spare GPU trays within a rack, as well as spare racks, to minimize the time to bring up replacement hardware and reduce the amount of work lost to hardware failures

When training frontier models, infrastructure reliability requires a perspective beyond simple availability. The fundamental challenge lies in maintaining training momentum without frequent system halts. Within Prometheus, we classify an interruption as any fault — from GPU silicon defects and network fabric anomalies to storage bottlenecks or thermal limits — that forces a job to pause and initiate a recovery cycle.

These interruptions introduce a large operational overhead because our workloads are tightly interdependent; a single fault within a 72-GPU domain can affect the entire cluster’s aggregate throughput. This performance loss directly impacts our engineering iteration speed, resulting in less effective compute and longer timelines for delivering advanced AI experiences to billions of people.

During the initial phase of Prometheus in mid-2025, our interruption rates reached a peak of nearly 1,000 events per 8K GPUs daily. Through a year of rigorous cross-functional engineering, we have achieved a 99% reduction in interruptions, enabling the cluster to sustain multiple training jobs of tens of thousands of GPUs in parallel.

Attaining this stability required a granular decomposition of every interruption source, followed by the deployment of targeted engineering solutions for each failure category:

NVLink Signal Integrity: initially the primary bottleneck for GB200 deployments. With over 600,000 NVLink connections, even marginal signal degradation triggers frequent NVLink recovery cycles. We implemented continuous telemetry and automated flagging, utilizing L11 diagnostic burns to isolate weak links before production. Our classification tools distinguish transient faults from persistent signal integrity failures, guiding targeted repairs and component replacement, and we validate repaired systems before returning them to production.

Memory Reliability (HBM and LPDDR): Memory-related faults became a major source of interruptions as we scaled GB300 with higher memory capacities. Working closely with NVIDIA, we used fleet telemetry and detailed error analysis to identify recurring failure signatures, which are mitigated via refined HBM firmware settings, memory scrubbing, an improved error correction algorithm for LPDDR, and pattern-based predictive detection to retire degrading devices before they impact job throughput. We are deploying these changes across the fleet and measuring their impact on interruption rates and hardware replacement demand.

NVLink Switch and Fabric Health: A single switch fault can compromise an entire NVL72 domain. We monitor fabric health at millisecond resolution, utilizing automated recovery paths to isolate faulty components and rebalance traffic across the remaining infrastructure without a job interruption.

Backend Network Events: At the BAG super-spine layer, link events are managed transparently via hardware-based fault detection. Our planar topologies ensure that individual fiber or port failures are rerouted without interrupting the synchronized GPU traffic bursts.

Sustained improvement is driven by our operational infrastructure: A colocated triage team at the New Albany site, a comprehensive stability sprint in March that synchronized fixes across the stack, and a rigorous attribution-driven accountability framework. Every repair undergoes a mandatory quarantine to validate system integrity before returning to the compute pool.

At Spotify, every surface and interaction is personalized to you as a user: the content on the Home page, the next song that plays, and more recently the ability to talk to Spotify.

Traditionally, this content is provided by recommendation systems that require multiple steps for candidate retrieval and ranking, and perhaps individual systems per surface. Generative AI is fundamentally changing this. We have been exploring how to provide recommendations via a Large Personalized Language Model in real time, across multiple surfaces.

This shift, however, presents unique engineering challenges, particularly when moving from a proof of concept to a scalable, production-grade inference architecture.

In January 2026, Spotify introduced LLM-powered technology to its podcast recommendations. The work is grounded in recent advancements in generative recommendation architectures, specifically the foundational methods introduced in the PLUM paper . At Spotify, we have applied these concepts to build a specialized generative recommendation system for podcasts, aimed at delivering deeply personalized listening experiences. Our specialized architecture, detailed in our "Deploying Semantic ID-based Generative Retrieval for Large-Scale Podcast Discovery at Spotify" paper  employs beam search to explore multiple token sequence paths simultaneously for candidate generation.

Beam search is a technique that allows exploration of an LLM’s output space with the goal of identifying highly probable token sequences. This technique navigates a decision tree of potential recommendations by keeping the most promising 'beams' or sequences active at each step, with the goal of identifying the highest-scoring podcasts for personalization. For this reason, these top sequences constitute semantic IDs that are then translated to catalog items to serve recommendations to users.

Our initial release relies on vLLM as an inference engine. vLLM is one of the most widely adopted open source inference engines, particularly strong at supporting modern model architectures for high-throughput  inference deployments. However vLLM’s support for beam search is limited compared to traditional completion requests – its beam search implementation doesn’t extract the maximum performance from GPU devices.

Specifically, vLLM's beam search implementation operates outside the core GPU engine, which introduces CPU-side bottlenecks and additional GPU work due to the recomputation of partially filled KV blocks.

For our January launch, these limitations meant we couldn't fully utilize high-end GPUs, so we opted for lower-tier accelerators to manage costs while keeping the system at a more optimal load point.

Another inference technique we’ve been exploring is candidate scoring. Candidate scoring uses a model's log probabilities to evaluate and rank a set of candidates.

A naive way to perform this type of inference is to adopt a “fan-out” approach and run inference on each candidate separately, for each request then we extract the related logprobs, before aggregating them to achieve the desired ranking operation.

This type of inference is generally available in most open source inference engines, however a more efficient technique has found its way into SGLang, thanks also to work from Linkedin’s engineering team. For this reason we’ve been utilizing SGLang as well to access this feature at inference time with an efficient candidate masking technique that allows us to score multiple candidates in a single request.

The most important part of Spotify recommendations is our ability to personalize based on user preferences and interactions. In our traditional recommendation systems, we have used dense user embeddings to accomplish personalization at scale. As we have experimented with LLM-based recommendations, we have explored a few approaches to enable personalization in this new paradigm.

This approach entails converting user listening and interaction history to text to place in the prompt for the LLM. The major issue with fully text based user history is the amount of text required to accurately represent the user. Prompts become extremely large, resulting in large inference latency that is too long for our request budget as well as higher GPU usage. Plain User Text is used sparingly, generally for smaller cases like the user’s most recent real time streams.

Similar to the PLUM paper mentioned earlier, we explored representing user history as a semantic id. This approach extends the model vocabulary with user semantic id tokens, which are easily added to prompts using a handful of text tokens, keeping prompts short and easily servable with no custom inference requirements. The LLM was fine tuned using the user semantic id space and extended vocabulary, and at inference time, a user semantic id is added to the prompt. While early results were promising, this approach requires further experimentation and research before it's ready for production.

The most successful method we have used for personalizing LLM requests is based on our existing user embeddings. The general approach is outlined in a white paper called Embedding to Prefix created by Spotify Research. Overall, the idea is to learn a projection from an existing embedding space into an LLM’s embedding space as a single soft token.  The LLM is fine tuned using a subset of the weights to be able to use this soft token to personalize recommendation outputs. At inference time, a user vector is projected into the LLM embedding space and inserted into the prompt before executing the initial forward pass. We have used this approach successfully for podcast recommendations and are currently integrating and evaluating it for various tasks with our internal LLM model.

The successful rollout of our first LLM-powered recommendation system, along with continued internal experimentation, has grown into a broader effort to bring generative recommendation capabilities across Spotify, powering our listening experience across catalog offerings and driving user interactions across surfaces. As this work moves toward production, an efficient and manageable inference stack becomes increasingly important. This is where our collaboration with NVIDIA began.

We kicked off our collaboration with NVIDIA with a clear goal: unify the inference features that we require (efficient beam search, scoring, and user soft tokens) into a single engine.

To address these challenges, we looked to TensorRT LLM (TRT-LLM) together with NVIDIA engineers. While TensorRT LLM offered superior hardware utilization for beam search, it initially lacked the specific "Score API" functionality available in our SGLang-based setup, as well as the ability to inject soft tokens and return sequences for multiple beams in beam search available in vLLM. With the NVIDIA engineering team—including Marek, Martin, Stefan, and Alexander—our goal was clear: close the feature gaps in TensorRT LLM.

This work resulted in several additions to the project to aid Spotify’s application of LLM in recommendation systems, specifically

support for returning multiple sequences in beam search (v1.2.0rc3)

support for out-of-tree models in trtllm-serve (v1.2.0rc4)

support for passing multi-modal embeddings via “image_embeds” (v1.3.0rc0)

support for multi-item scoring via the Python API (v1.3.0rc20)

general bug fixes and performance improvements

Beam search in TensorRT LLM is implemented as part of the sampler, which reduces host overheads and, combined with overlap scheduling, ensures good GPU utilization. Moreover, the C++-based sampler in TensorRT LLM has been replaced with a more flexible design relying more heavily on PyTorch. The beam search support implemented in this new sampler provided a notable performance uplift compared to the previous implementation.

With NVIDIA’s help and review, we used TensorRT LLM’s out-of-tree model support to implement a customized Qwen3 extension plugin to implement our soft token approach. The multi-item scoring extensions to TensorRT LLM’s Python API enable functionality equivalent to SGLang’s scoring API. Currently, a custom serving layer implementing efficient tokenization and request batching is required. However, TensorRT LLM is continuously evolving and has, e.g., recently added support for serving prefill-only embeddings. Multi-item scoring is an important performance optimization, because it avoids the overhead of a single request per candidate, while retaining a computational effort linear in the number of candidates.

When editing code in a modern IDE or editor, developers rely on its refactoring features to automate common transformations. Today, we are excited to introduce interactive refactoring in gopls, powered by a new capability we are proposing for the Language Server Protocol (LSP) that brings dynamic, multi-step dialogs directly into your favorite editor. Crucially, we designed this capability (in collaboration with the Dart team) not just for Go, but as an open standard for all programming languages and editor ecosystems. Working support is already available in gopls v0.24.0 and the official Go extension for VS Code v0.56.0.

The LSP is an open standard that decouples language-specific features from specific text editors. As you navigate and edit code, your editor (such as VS Code, Neovim, or Emacs) and a language server (like gopls) engage in a continuous JSON-RPC exchange to provide features like autocomplete, hover documentation, diagnostics, and code actions.

Today, almost every code transformation in the LSP is like a function of no parameters: you trigger the operation, and the server immediately computes the edits. (Renaming a symbol is the sole exception: because it is a function of one parameter, the desired new name, it required its own dedicated PrepareRename RPC in the protocol.)

The language server must deduce the user’s intent from context alone, namely the cursor position and the enclosing syntax tree. When that context is not enough, the server is forced into one of two choices: apply a one-size-fits-all default, or refrain from offering the transformation altogether. The limitation lies not in gopls’s ability to compute the necessary edits, but in the LSP’s lack of a mechanism for language servers to ask the user for input.

For many transformations, this parameterless model works well. But many others need additional input from the user: which struct tags to add and in what naming convention, which interface to implement, which file to move a declaration to. Without a way to ask, gopls could only guess—“Add struct tags”, for example, always produced json tags in camelCase—or not offer the refactoring at all. With interactive refactoring, language servers can now easily provide new operations with one or more parameters.

While some language extensions have worked around this limitation by embedding custom, language-specific dialog logic directly into individual editors, doing so leaves behind other editors (such as Neovim and Emacs) that stick strictly to the LSP with minimal custom client code. More importantly, editor-specific workarounds go against the fundamental purpose of the LSP: to decouple language-specific features from editors so that each server improvement benefits every client.

#56. Is Your Organization Messing Up AI Adoption?

The way I see most organizations roll out AI feels more like a farce than a strategy. If it were turned into a movie, reviewers would say it was unbelievable. Nobody could be that stupid.

Yet here we are. And what makes it all the more frustrating is that we have been here before.

Back in 2014, I wrote a book for Smashing Magazine called Digital Adaptation, looking at the mistakes being made in how organizations were approaching digital transformation and what they should be doing instead. The similarities between then and now are striking.

So in this post, I want to look back at Digital Adaptation and see how the lessons in that book apply to the AI era and what we can learn from the past to help us navigate the challenges of AI today.

The biggest mistake, both then and now, is approaching each as a technological challenge.

Sure, both digital transformation and AI are technological advances, and yes, some level of technological implementation is required. But that is the tip of a very large iceberg.

Back in the midst of the digital transformation era, IT departments were rolling out CMSs, CRM systems, intranets, and so on. Meanwhile, on the customer-facing side, organizations were rolling out websites, apps, and personalization. But they were putting almost no emphasis on how people were going to use these systems.

Internal systems were hard to use, and customers either didn’t care what was being built or wanted something else entirely.

The same is happening with AI. Senior management are buying into the hype, and IT teams are rolling out Copilot Studio licenses company-wide and considering the job done. Sure, there is a bit of organization-wide generic training, but that’s about it.

Just like before, staff are left wondering what to do with these new systems and feeling under pressure to use them and deliver results.

After all, this time around, it is even worse, because this time, staff fear for their jobs. They have read the same headlines that you have, and no amount of promises from senior management is going to make them feel any better.

I mean, think about it from a staff member’s point of view. AI offers them very little personally, even setting aside the fact that management may be intending to use it to replace them.

The main reason senior management are excited about AI is that it provides additional productivity. People can do more in less time. But that does not benefit staff. They are still required to work 9 to 5, but now they are expected to do more in the same time. They don’t get any time back, and they don’t get paid more, so why would they embrace AI?

One strategy is to help staff identify the parts of their job they hate and how AI can help them do those tasks more quickly and less painfully. People tend to be a lot more receptive to change when it is presented as an opportunity to improve their working lives.

But, that should just be the beginning. Organizations may need to consider providing incentives for staff to adopt AI in terms of career progression, compensation, or shorter working hours.

Also, adopting AI is not a simple task. It involves challenging every working practice they have built up over (in some cases) decades. All of that procedural knowledge has to be rebuilt. That is a lot to ask of anybody in even the best of circumstances, and most employees do not find themselves in the best of circumstances.

Most are overworked and struggling to stay on top of their to-do lists. They don’t have time to sit down, learn a new tool, and figure out how it fits into their workflow.

That doesn’t just take time. It also takes a lot of consideration and experimentation. It is not enough to just send a member of staff on a training course and expect them to be able to use AI to its full potential.

At a minimum, staff need training specific to their roles, such as the AI training I provide to UX teams. But organizations should be going even further.

They need to develop sophisticated training programs that help staff from different departments understand how to use AI in their specific roles. They need ongoing support and the time to experiment with AI to find the best ways to use it.

But formal training will only take you so far. In my experience, the most effective support comes from colleagues, which is why I would start with the enthusiasts rather than the resisters. Every organization has a handful of people who are already experimenting with AI, often without anybody asking them to. Bring those people together, give them the time and space to share what is working for them, and let their enthusiasm spread to everyone else.

I saw this work during the digital transformation era too. In Digital Adaptation, I described an internal conference where staff showed their colleagues what they had built, and it did more for adoption than any memo from the top ever could. People are far more likely to try something when they see a colleague in a similar role using it successfully than when they are told to by senior management.

Unfortunately, experimentation comes with a big downside… mistakes will be made.

Many organizations have, to be frank, a culture of fear where mistakes are seen as a sign of incompetence. However, by its very nature, learning a new tool like AI will involve making mistakes, and this can be a massive barrier to adoption.

I saw this during the era of digital transformation. Senior management would demand digital transformation and were confused when it didn’t happen.

What they didn’t realize was that they were sending mixed messages to staff. Sure, they were asking for digital transformation, but they were still demanding that the same key performance indicators (KPIs) be met, and they still pointed out any mistakes in their annual reviews.

There was no space to fail, as the pressure to deliver was relentless.

This time around, it seems to be even worse. I hear horror stories of staff being reprimanded for using too many tokens just weeks after being told to adopt AI. Or staff being lectured so much about what they should or should not do with AI that they are afraid to try anything. It is safer to just do what they have always done.

Look, I get it. AI cannot be rolled out without some governance in place, but again, this is an area that organizations have typically handled poorly.

In the midst of digital transformation, governance would either be non-existent, or it would be so strict that it would stifle innovation, and unfortunately, I see the same pattern emerging with AI adoption.

Staff need some governance to help them know where they stand. It helps them understand what is expected of them and what they can and cannot do.

But too often organizations have been so strict that it is easier not to do anything at all. Pages of instructions about what people should and should not share with AI create that sense of fear that I mentioned earlier.

Of course, mistakes will get made, but that is the cost of change, and so organizations need to accept that and do what they can to mitigate that in how they roll out the technology.

That said, organizations will need to be careful in how they roll out AI from an IT perspective. Once again, it is easy to lock everything down and stifle the adoption of AI.

Again, this is something I highlighted back in 2014 with digital transformation. Overstretched IT teams would pick a set of technologies and roll them out organization-wide, often with little or no consultation with the individuals who would be using them. Anything outside of that set of technologies had to go through a complex approval process, normally involving a steering committee. The result was a glacial pace of change that was one of the major contributing factors to the failure rate of digital transformation projects.

Today we are seeing the same thing. IT teams are opting into a tool like Copilot and calling it a day, but that often falls massively short.

Take, for example, a UX team I am working with at the moment. Management is pushing hard for AI adoption, and the team is excited about the potential of creating an AI-powered research repository and even AI personas. It sounds like a wonderful case study in AI adoption, with enthusiastic management, an excited team, and innovative ideas.

Unfortunately, the reality is that nothing is happening because Copilot cannot deliver on the team’s vision, and so they are currently bogged down in bureaucracy as they try to persuade the AI steering group that they need to use a different toolset. Understandably, the team’s enthusiasm is waning. Why bother?

And that team is one of the more patient ones. In many organizations, staff are not waiting for the steering group at all. Just as we saw shadow IT during the digital transformation era, with people signing up for Dropbox and Google Docs because the official tools could not do what they needed, we are now seeing shadow AI. When the in-house AI tool will not let people do their jobs, they open a personal ChatGPT or Claude account on their phone or home laptop and get on with it.

That is far more dangerous than the problem the restrictions were meant to prevent. Company data ends up in tools the organization has no control over, with no oversight and no record of what has been shared. In trying to lock everything down, organizations end up pushing the risk somewhere they cannot see it.

The instinctive reaction is to clamp down with stricter policies, blocked websites, and warnings about disciplinary action. But that rarely works, and it drives the behavior further underground. Shadow AI is a symptom, and a useful one, because it shows exactly where the official tools are falling short.

Look, I understand the cost of a messy, out-of-control tech stack. It is not ideal. However, in the early days of adoption, we may have to live with a bit of chaos while people explore the edges of what is possible and work out common use cases.

Organizations need to allow staff to explore different uses of AI and even different AI apps to find what suits their specific needs in their specific roles. They can always start locking things down later as the real organizational needs become clearer.

I admit all of this feels dangerous to some organizations. They want to control the AI adoption process centrally and make sure nothing goes wrong. I understand that. But change comes with a degree of risk, and the risk of moving too slowly is greater than the risk of moving too fast.

However, a bigger danger still is when organizations see this as a technological challenge and overlook the human side of things. AI adoption is not simply about rolling out new technology. Just like digital transformation, it is about people, culture, and change management. The sooner organizations realize the scope of what they are dealing with, the better.

#575. MCP standardized tools. Now we need the infrastructure around them.

📅 Oct 15, 2026  |  Category: Technology  |  Read Source →

Developers can now connect models to repositories, databases, browsers, observability systems, internal APIs, and dozens of other tools through a shared protocol. Claude Code, Cursor, Codex, VS Code, and a growing list of other clients all speak it. Vendor-hosted endpoints exist for GitHub, Linear, Notion, and many others. The Tier 1 SDKs are approaching half a billion downloads a month.

That is a real achievement. For years every AI application built its own tool-calling layer. MCP gave the ecosystem a common interface. Once a server exists, multiple agents can use it without custom glue. That alone is worth the effort.

But after building around MCP for coding agents, I started noticing something else. The protocol was becoming standardized faster than the infrastructure around it. Connecting a tool was becoming easy. Running that system reliably across real users, real credentials, and real work was not.

The protocol solved a specific problem: how can an AI model talk to tools through a common interface? The next set of problems is different. How do we make thousands of those interactions reliable, secure, efficient, observable, and straightforward to deploy?

The happy path looks simple. An agent talks to an MCP client, which talks to an MCP server, which calls a tool that talks to an API or database. In a demo, that is often all you need.

In production, the picture changes. You have multiple agents, multiple users, many MCP servers, credentials that must not leak, rate limits, permissions that differ by person or by task, failures, retries, logs, tool schemas that change, context constraints, and machines that are not identical. The mental model becomes something closer to agents and clients sitting in front of authentication, routing or gateways, then a set of MCP servers, then the actual systems those servers touch. Every one of those layers can fail independently.

A concrete example: an agent that reads documentation and fails once is annoying. An agent that creates cloud resources, writes database records, or opens pull requests and fails halfway through is a different problem. Partial work, inconsistent state, and the need for idempotency or compensation become real requirements. The protocol does not magically supply them.

One pattern I kept seeing is infrastructure duplication. Developers and teams repeatedly build authentication, deployment, connection management, retries, logging, secret handling, health checks, access control, simple registries, caching, and rate limiting. The same pieces appear in different codebases because the protocol standardizes the message format, not the operational concerns around it.

This is not unique to MCP. Earlier infrastructure transitions followed a similar shape. Once physical servers became painful enough, cloud abstractions matured. Once every application reinvented authentication, identity platforms matured. MCP may be entering a stage where managing dozens of individual local servers, each with its own configuration and credentials, starts to feel like the old way of doing things. Whether the eventual abstractions live in agent runtimes, cloud platforms, gateways, or somewhere else is still open. The duplication is already visible.

Local servers over stdio are easy to understand, close to the user, and naturally connected to local files and processes. They were the perfect way to experiment. Local execution also avoids many of the authentication and multi-tenant problems that appear once the server moves onto the network.

Team-scale usage exposes the limits. Everyone needs installation and configuration. Versions drift. Credentials live on different machines. One developer’s server can break differently from another’s. Onboarding becomes repetitive. Observability is fragmented because each machine is its own island. Remote or hosted servers address some of those problems, but they introduce others: authentication that actually works across clients, latency, multi-tenancy, data handling, uptime, permissions, and questions of vendor dependence. Neither model is automatically superior. They solve different sets of constraints.

The July 2026 specification changes helped the remote case. Removing protocol-level sessions and the initialize handshake means a remote server can scale more like an ordinary HTTP service. That is useful progress. It does not remove the need for authentication, authorization, or operational discipline.

Coding agents need repository context. Naively giving an agent the whole tree creates token cost, irrelevant information, distraction, higher latency, and sometimes worse reasoning. Bigger context windows do not eliminate the problem. The question shifts from “how much can the model hold?” to “which context deserves to be there?”

This is where a lot of my early work sat. Hexum.dev began in part around making repository context more efficient, so the agent saw the relevant structure instead of a raw dump of files. On a published 24-task benchmark using MBPP and HumanEval, the measured context sent to the model dropped from 220,393 tokens to 27,352 (an 87.6% reduction) while still passing all official tests. The methodology is public. The number is less important than the observation: once you start treating context selection as a deliberate step rather than a dump, other constraints appear.

Developers talk about this constantly now under the banner of context engineering. Progressive or dynamic tool discovery is one response to a related problem: loading every tool schema from every server into the context on every turn. Client best practices now recommend deferring full definitions and providing a search-style meta-tool. The same guidance explains why: progressive discovery can dramatically reduce tool-definition tokens and can improve selection accuracy by keeping the model focused on a smaller set of relevant tools. The pattern is not universal yet, but the pressure is clear.

There is a point where giving an agent 50, 100, or several hundred tools becomes harmful rather than helpful. Selection accuracy can drop. Context fills with schemas the model may never need. Name collisions and vague descriptions make the problem worse.

Should every tool definition always sit inside the active context? Or should tools themselves be retrieved dynamically? Both approaches exist in the wild today. Static registration is simple when the surface is small. Progressive discovery, semantic search over tool descriptions, and gateway-style routing that exposes a smaller set are all being tried. The protocol itself is moving in this direction through progressive discovery guidance and related work. What remains open is how much of the selection logic lives in the client, in a gateway, in the server, or in the model’s own tool-use training. Least privilege also matters here: an agent that can see every tool is an agent that can be tricked into calling ones it should not have access to.

MCP security is not the same as ordinary API security. An agent can read untrusted text, interpret it as instructions, call tools, and mutate external state. That creates surfaces that look like prompt injection, confused-deputy problems, over-broad permissions, malicious or poisoned tool descriptions, secret leakage through arguments or results, and supply-chain risk from the servers themselves.

None of this means the protocol is inherently insecure. It means that once natural language can cause software to invoke real capabilities, the trust boundaries and permission model become critical. Least privilege, explicit approval for destructive actions, careful handling of tool results as untrusted input, and authentication that survives the full path from client to server to backend system all matter more than they do for a conventional API. A 2026 measurement study of 7,973 live remote MCP servers found that 40.55% exposed tools without authentication. That is a deployment problem, not a protocol problem, but it is the problem teams actually hit.

A human using software notices an error and stops. An autonomous agent may continue. That changes the requirements around retries, idempotency, timeout behavior, partial failure, and validation of tool results. Observability becomes more important because you may need to reconstruct what the model believed, which context it saw, which tools it knew about, which one it selected, what arguments it generated, what the tool returned, and what it did next.

Standardized telemetry is starting to appear. OpenTelemetry’s GenAI semantic conventions include MCP-related spans and attributes. Work such as SEP-414 reserves space in _meta for W3C trace context so traces can cross the MCP boundary. The official Python SDK now emits OpenTelemetry spans by default. Whether this becomes the default way teams debug agent-tool systems is still early, but the demand is obvious once agents move past demos.

At first I thought one of the main problems was context efficiency. Hexum.dev’s early work on shrinking repository context for coding agents reflected that. Once you optimize context, you run into tool selection. Once you expose tools, you run into deployment and configuration. Once tools are remote, you run into authentication and permissions. Once agents become more autonomous, reliability, security, and observability move to the front. The realization was that MCP is not merely a protocol problem. It is becoming an infrastructure category.

Hexum.dev today is a hosted remote MCP endpoint for coding agents. Its scope grew as we ran into adjacent problems around context handling, architecture checks, and controlling agent behavior. The agent still lives in the editor the developer already uses; Hexum.dev sits around specific parts of that workflow. Building it did not eliminate the surrounding problems. It made them concrete.

There is one lesson from building Hexum.dev that has nothing to do with protocols.

Most of building is uncertainty. Things fail, direction changes, and you spend a lot of time on ideas before anyone validates them. Having friends who listen, encourage you, and challenge you when needed matters more than founders often admit. Yuchen and Pranav have been two of those people for me. They are not building Hexum with me, but they have listened to countless ideas and made the uncertain stretches easier to keep moving through.

A possible future stack looks something like this: models and agents at the top, agent runtimes and MCP clients beneath them, then an infrastructure layer that handles routing, authentication, permissions, context management, tool discovery, caching, observability, policy, and reliability, then the MCP servers themselves, then the databases, APIs, code, and SaaS systems those servers touch.

This is a hypothesis, not a certainty. Some of those capabilities may end up inside model providers, inside agent runtimes, inside cloud platforms, inside gateways, or inside individual MCP servers. The boundary is not fixed. The interesting part is that the protocol’s success is forcing the question. Once tool interoperability is taken for granted, the remaining work is everything required to make that interoperability production-grade.

MCP’s biggest achievement may be that developers are beginning to take tool interoperability for granted. That is what successful standards eventually do. They make a previously hard problem feel ordinary.

Standards rarely eliminate infrastructure. They move the infrastructure problem somewhere else. HTTP standardized how systems communicate, but we still built CDNs, load balancers, API gateways, observability platforms, identity systems, and cloud infrastructure around it. MCP may follow a similar path. The protocol gave agents a common language for tools. Now we have to build everything required to make that language reliable at scale.

The interface is no longer the hardest part. The systems around it are.

📅 Oct 15, 2026  |  Category: Technology  |  Read Source →

Forum is a standalone Groups app that a small team built from scratch. It’s also where we tested a different way of working: treating an AI agent as a participant in the engineering process rather than a faster way to type.

That experiment needed a definition of success, and ours wasn’t code volume. We measured verified, production-ready outcomes — changes that build, pass tests, and survive review.

Pointing AI at the coding step alone doesn’t change much. Our results compounded as we extended the approach to the stages around implementation — planning, building, testing, and verification. The clearest way to see the shift is in who owns each step.

With human-in-the-loop, the engineer drives every step and the AI assists inside it by autocompleting a function, suggesting a fix, or answering a question. Each iteration advances at the pace of the person driving it.

With human-on-the-loop, the agent runs the iteration itself — plan, implement, build, test, correct, repeat — while the engineer sets the goal, watches the run, steps in when it drifts, and approves the result. The person’s job moves from executing the steps to owning the outcome and holding the quality bar. This is the target we are driving toward, not a finished state: some stages run autonomously today, while others still keep an engineer in each iteration.

When the engineer supervises, work stops being strictly sequential. Cycles that used to run one at a time can overlap, and an engineer’s time goes to direction and judgment rather than to sitting through the loop. But that only holds if what comes back can be trusted. Without verification, AI-generated code creates a familiar problem — plausible output that no one has confirmed actually works, which an engineer then has to read, debug, and often discard. Weak signals don’t remove the constraint; they move it from writing code to reviewing code that looks finished and isn’t.

So we set the bar at verification rather than compilation. Compiling isn’t the finish line — a task is complete only once automated tests and visual checks have passed. Agents check their own work before an engineer sees it, which means what reaches review is a smaller set of higher-confidence results rather than a pile of output to sift through. Less gets generated, and less gets discarded. Every shipped outcome still carries an engineer’s sign-off; our effort went into making that sign-off fast and well-evidenced, with build results, test outcomes, and recorded verification sessions attached to the change.

With the engineer outside of every cycle, the loop has to run safely on its own. Four capabilities make that possible:

Planning as technical specification: Agentic execution requires extreme precision. Ambiguity that an engineer might resolve through intuition results in agent failure. We invested in rigorous upstream decomposition and machine-readable context, which tightened the engineering loop for engineers and agents alike.

Automated verification inside the loop is the force multiplier: We integrated automated pass/fail signals — build status, unit tests, and UI spec matching — directly into the agent loop. This enabled asynchronous development producing ready-to-review pull requests with pre-populated test plans and recorded verification sessions. Verification is the hard part to get right, and how much we can safely hand to the loop is gated by how much we can trust the verifiers.

Simulated user testing with agents: We deployed navigation agents that interact with the live app exactly like a person would. These agents perform actions, read the screen, and report regressions. Navigation agents are able to run the same verification paths continuously.

Agentic production operations: After launch, agents help automate root-cause analysis. When someone using Forum submits feedback, the agents use that feedback to investigate possible regressions. The agents then forward the analysis to engineers who decide the next course of action.

The biggest gains came from changing our code and tooling, not our prompts.

Architectural legibility over inherited complexity: We worked to keep Forum’s codebase as straightforward as possible and chose to modularize key pieces of the architecture in order to get the benefits of battle-tested infrastructure while also letting the agents plug and play easily. Where we couldn’t easily do so, we rebuilt from scratch, trading reuse for agentic throughput, and it proved rewarding in development speed. Agents learn patterns from the code they read. Fix a weak pattern once and every future agent session inherits the improvement; leave it and the same shortcut shows up in everything the agent writes next.

Give agents tools, not descriptions: Our main failure mode was the agent losing track of where it was in the app — editing the home feed when asked to change the group home screen, or guessing at screen coordinates. So instead of describing the app to the agent, we gave it tools to check: read the live view hierarchy from the simulator, list the elements actually on screen, and look up the path to a target view — all before it acts. Misdirected edits dropped sharply. We applied the same approach wherever agents touched our systems: give the agent a way to check state directly rather than a description to reason from.

Build-level isolation for safe AI prototyping: As Forum matured toward production, we wanted early-stage prototypes and agent-generated experiments to have room to run while keeping the production app strictly limited to finished, reviewed work. We wanted a stronger guarantee than feature gating alone, where prototype code still exists inside the production build. Our solution was a separate build flavor, a sandbox app that shares the exact same codebase, frameworks, and design system as production, but compiles prototype code out of the production build entirely via a plugin/socket architecture.

The pattern let us keep fast AI iteration after we had real people using the app to protect.

Adapting the environment did more than make the agent faster to build with — it made the agent a tester. We didn’t point it at one specific defect. Instead, we set up repeatable stress scenarios that mimic real user behavior (aggressive scrolling, random group browsing, rapid navigation, repeated media loading) and ran them routinely across builds. Because these runs produce consistent signals (crashes, memory growth, page faults, UI regressions), the agent can triage anomalies, narrow to the triggering sequence, and then investigate the root cause.

One such run surfaced a memory issue. The agent isolated a repro, proposed a fix, and verified it — all during development, before the app reached users. The fix materially reduced on-device memory growth and page faults across repeated stress sessions.

While engineers made the architectural decisions, the detection and regression monitoring were automated and repeatable; once an anomaly was detected, the agent could reproduce → isolate → propose a fix → verify with the same harness.

We applied the human-on-the-loop approach in two places:

Building the stack: Agents mapped the architectural options and trade-offs; engineers then evaluated and chose. What we deliberately kept human was the target — deciding what a good outcome looks like is a product judgment, not something the system should define for itself.

Operating the stack: Questions that used to require whichever engineer knew the relevant code path now go to an investigation agent that gathers what it needs and posts a write-up with suggested fixes. After hand-scoring a batch of real investigations we arrived at a workflow where the agent compresses the mechanical work and delivers a structured write-up to an engineer, who then validates whether a finding is a real bug or an intentional trade-off.

What improved quality wasn’t better prompting. It was context. One recurring category of investigation came back weak until we gave the agent the same pointers to the relevant code, example queries, and design docs that we’d give any new engineer on day one. The quality of that category jumped. The difference from human onboarding is that you train once, and every future session starts from it.

Put native GitHub features to work to review outside collaborator access and archive stale repositories.

Working with outside collaborators can add more work for a repository owner. You need to confirm who still needs access, change permissions as projects evolve, and archive repositories once they’ve served their purpose.

To keep up, repository owners need to track collaborators, deadlines, and follow-ups for each repository. As a project grows, that manual housekeeping becomes harder to keep up with and easier to defer.

We faced this problem in a shared organization where GitHub employees (“Hubbers”) collaborate with customers and partners on product trials and professional services engagements. Our answer was Evergreen, a GitHub App built with native GitHub features. The workflows below exhibit a pattern you can adapt for your own organization.

Evergreen is a GitHub App that automates organization hygiene through two workflows:

Fail secure. If nobody responds to an access review, we don’t leave access in place and hope for the best. We revoke it. The safe outcome is the default outcome.

Never destroy anything. Evergreen will never delete a repository or its contents. Archived repos are recoverable, and every access change is written into the repo’s tracking issue, so reverting a mistake is as easy as a copy-paste to Copilot.

Under the hood, Evergreen is a small Go webhook server running in a container. But the interesting part is the choreography. Every moving piece is a stock GitHub feature: a GitHub App, scheduled actions, webhooks, issues, custom properties, and plain files in a repo. Nothing exotic to reinvent.

Evergreen tracks every repo’s status as a JSON file (one per repository) committed to the controller repo under state/repos/.json. When a review deadline passes with no response, cleanup revokes every collaborator in the snapshot. We were careful about a subtle edge case: what if some removals succeed while others hit a transient API error? Marking the review “done” while a removal is still outstanding would be a quiet inconsistency, and we didn’t want that.

So Evergreen fails closed. If any removal fails, the review stays pending and the issue stays open, and the next run retries the stragglers. It only records “revoked” once every removal actually succeeded. And whatever gets removed is written into the issue, so restoring access is a matter of re‑adding the handles it listed.

Automated housekeeping has a reputation for being the office smoke alarm: loud, easy to ignore, and usually going off while you’re cooking something perfectly fine. We worked hard to make Evergreen feel like the opposite:

Automation that manages access and archives repositories deserves a careful rollout, especially into a large, active org (ours has 1,400+ Hubbers, and many more customers and partners). We wanted the very first run to be a complete non‑event. A few practices got us there:

Dry‑run first. Evergreen ships with a DRY_RUN mode that logs every write it would make without touching a single collaborator or repo. We ran it against the real org and read the logs like tea leaves until we trusted the decisions it wanted to make.

Overcommunicate. Before flipping the switch, we broadcast what was coming, when, and what people needed to do, so the first issue anyone saw wasn’t a surprise. We found that when you’re telling a large group the same thing for the seventh time, it’s often when many are still hearing it for the first time.

Watch everything with Splunk. Evergreen emits structured logfmt logs to a dedicated Splunk index. That observability is how we caught edge cases in the wild (empty collaborator lists, unusual permissions, repos with issues disabled) and tightened the logic before they mattered.

Respect the platform’s speed limits. When you open issues and post comments across every repo in a big org, you slam into GitHub’s secondary rate limits for content creation: 80 requests/minute and 500/hour. While this is a thoughtful preventative control to avoid system abuse, it requires a bit of intention when automating IssueOps at large scale.

So Evergreen paces itself by construction. It processes repos in batches, spaces out each content‑creating call by a couple of seconds, and sleeps between batches to let the rolling window clear, and it only counts the repos that actually create content, so a quiet quarter where nothing’s eligible still runs fast. We opted for proactive avoidance over reactive back‑off.

Routine hygiene is the kind of work that’s easy to defer and perfect to automate. The trick isn’t heroic cleanup sprints: it’s making the boring, safe thing happen on a schedule, with a friendly face and an undo button.

That’s Evergreen. And because it’s built entirely from native GitHub features, you can stand up the same pattern yourself.
