#571. Redox Ring Buffers Project Summary

📅 Oct 29, 2026  |  Category: Business  |  Read Source →

Last year, the Redox team received a grant to develop io_uring-like Ring Buffer support at the system task level, as a first step towards ring buffer communications between the application and the majority of system services. This phase of the work finished up in September, as the last pieces were put in place.

We want to thank the NLnet Foundation, the NGI Zero Commons Fund, and Horizon Europe for their generous support. The NGI Zero Commons Fund is reaching its end, but NLnet is now accepting applications for grants from new funds, Restack and Code Supply, as well as some smaller theme funds. Apply for funding before November 3rd 2026! (and then every two months after that).

The team has done a fantastic job, and I want to congratulate Ibuki, Anhad and Jacob, and thank them for their time and effort.

In addition to implementing the Ring Buffer machinery for our system services and drivers that can support it, an io_uring and liburing-like API for applications was completed and demonstrated. There was also substantial work done on support crates, including an async executor for drivers.

And there was some very exciting work on various performance improvements, to allow much faster switching between applications and their system services. But I will let the team tell you all the technical details.

Historically asynchronous I/O on Linux was done through the kernel’s native AIO interface. AIO is mainly useful for unbuffered (O_DIRECT) file I/O, and buffered requests silently block1. Developers also raised concerns about its complexity and performance1 2. There is also POSIX AIO, but developers often consider its implementation lackluster and slow1. To address these problems, several alternative asynchronous mechanisms such as fibrils and syslets/threadlets were proposed but were never merged into the mainline Linux kernel. In early 2019, Jens Axboe proposed and developed the io_uring interface, designed to be an efficient, extensible and “easy to use, hard to misuse.” In its early days, io_uring did have a few security issues and memory leaks, but these have since been addressed3. It was merged in Linux 5.1 and is widely used today.

The Linux io_uring interface allows the user to submit one or more I/O operations to the kernel, which are then processed in an asynchronous fashion without blocking the userspace process. Redox, being a microkernel, handles I/O in userspace scheme processes rather than in the kernel. Each file description stores a handle to its scheme, so an I/O system call on that file can forward the request to the scheme. The async I/O interface developed in this project, called Redox Rings, uses a mechanism similar to io_uring. However, unlike io_uring which is used to submit operations to the kernel, the Redox Rings interface is used by the application to directly submit requests to the appropriate scheme asynchronously without blocking the application. Additionally, the interface allows I/O requests to be issued without any memory copies, by having a separate shared memory region between the scheme and the application (which can be requested as DMA-capable memory).

For portability, the Redox Rings API is designed to be similar to that of liburing and can also be used for general inter-process communication. For example it is used for communication between the RedoxFS filesystem service and NVMed which is the storage driver. The addition of this API has allowed several parts of Redox to reap significant performance improvements!

Since each queue has exactly one producer and consumer, each index is only ever modified by one side. This eliminates the cost of having a shared locking mechanism.

We’ve introduced the first ring buffer implementation to Redox OS. Unlike Linux’s io_uring, the submission queue (SQ) and completion queue (CQ) are shared exclusively between userspace processes and are never accessed by the kernel.

redox-rings is a new crate for ring buffer communication between userspace processes, also providing data structures for FFI use cases. It uses futexes as the main synchronization mechanism, with optional pipe file descriptor support.

Based on its FFI support, we’ve introduced the “redox-ring API” in relibc, inspired by Linux’s liburing.

liburing is a library for Linux’s io_uring, providing helpers for setting up and tearing down io_uring instances, as well as a simplified interface for submitting I/O requests.

Similarly, the redox-ring API allows applications to communicate with daemons that support ring buffers using custom protocols.

The API provides functions for managing ring buffers, shared memory, and requests.

The API also provides functions for registering file descriptors, freeing allocated buffers, and tearing down ring buffer instances.

The redox-rings implementation uses shared memory to exchange SQEs, CQEs, and I/O data between applications and daemons.

During initialization, the SQ, CQ, and data buffer pool are mapped into the application’s address space using the fmap syscall with MAP_SHARED. This allows both sides to access the same memory without copying I/O data between processes.

The redox_ring_queue_init_with_path function opens the scheme ring handle and uses the SYS_CALL system call on it to set up the ring buffer session with the given parameters. This returns file descriptors for the SQ, CQ, and shared buffer pool, which are mapped into the application’s address space. The application can then use the queues directly to submit requests and receive completions. On the scheme side, the worker task waits for entries in the SQ, processes them asynchronously and notifies the application on completion.

We developed an async executor for device drivers, with a single interrupt vector and an SQ/CQ pair per core architecture. A single core is used at the moment, and multi-thread-per-core support is in progress. Furthermore, we updated NVMe driver to use the async executor, and more devices such as virtio are expected to follow.

With the executor, schemes that support Redox Rings can handle each I/O request in its own async task, with a worker thread spawned for each session between the application and the scheme. On teardown, the worker task is stopped, pending I/O operations are cancelled and shared resources are cleaned up.

While it has substantially improved over the years, IPC is still quite slow on Redox, and this is important to optimize as ring buffers can only offset this overhead to a certain extent. This has been a focus of our work to improve system performance.

The acid test suite for Redox was expanded to include more targeted benchmarks that measure IPC latency, in particular acid ipc_latency_simultaneous, and also acid heavy_forking. Support was also added for repeating measurements and collecting more proper statistics (although still less feature-complete than e.g. hyperfine), making it easier to know whether changes in metrics are statistically significant and by how much.

Various single-digit speedups were attained from kernel refactors, such as eliminating redundant locking, hashmap lookups, and by adding a lower-overhead call for IPC, similar to seL4’s “reply-wait”.

Another source of overhead, from the flamegraphs, was found to be XSAVE and XRSTOR, a few hundred cycles combined (tested on an AMD Ryzen 9 5950X). These instructions save/restore vector registers, which is ~600 bytes on the CPU tested, and likely similar on other CPUs with AVX2 (which only userspace uses).

The optimization made here is that the kernel zeroes the vector registers if the caller and callee entered the kernel through syscalls, rather than saving/restoring (using vzeroall, ldmxcsr etc. as required for correctness).

Context switching can be triggered both by preemption, i.e. timer interrupts, and voluntarily from syscalls. After Redox destabilized its syscall ABI, instead preferring the libredox symbols provided by relibc, all syscalls will first go through a function call. Since the System V ABI clobbers all vector registers for all function calls, it is almost zero-cost to also define Redox’s syscall ABI to do so. Luckily, the generated assembly code for relibc was almost identical.

A major bottleneck during IPC is invoking the scheduler, as can be seen from various flamegraphs. The scheduler needs to access multiple data structures, primarily BTreeMap that takes up a large fraction of the overhead, and it also needs to acquire lots of locks, often blocking.

Direct context switching was implemented in kernel MR 694, resulting in a 15-20% IPC latency reduction. It separates the current context (reference) into the scheduled context and the running context, where the former is the context owning the current timeslice, and the latter is the context whose registers/memory/file table is currently active. When direct switching has not occurred, these always coincide. Consequently, a client process calling a scheme (typically using our SYS_CALL syscall) can completely bypass the scheduler and switch directly to the scheme, if ready, where the kernel will then prioritize returning to the scheduled context the next time the scheme yields. This mimics the behavior of how complex syscalls are handled in monolithic kernels, and should also be more cache-efficient, among other efficiencies.

The kernel previously only supported 4k pages. This is still the case on non-x86, and for all userspace cases, but now the kernel physmap will be mapped as 2M when possible. TLB usage can thus theoretically be reduced by up to 512x for heavy CoW, and in practice, the highest obtained L1DTLB-miss rate from acid heavy_forking was -75%.

IPC roundtrip latency has been reduced from ~5800 cycles to ~2700 cycles, but this is still high compared to fast Âµkernels like seL4. Additional optimizations could be to reduce locking, and reduce the syscall entry overhead, but primarily to simplify the IPC primitive and remove possibly unnecessary parts such as request buffers. While not as applicable for nonlegacy applications, automatic page-borrowing of clients’ buffers (in UserScheme) is also a major source of overhead and in a benchmark similar to dd bs=4k if=/dev/zero of=/dev/null, the overhead is at least ~32k cycles per call. However, while the existing benchmarks are useful as an approximate lower bound on latency, more investigation will be required to determine the distribution of overheads for more realistic workloads, both with and without userspace ring buffers.

We've open-sourced our Accessible Components Library, and, as you might expect, this includes the HTML, CSS, and JavaScript code. But, we thought, "Why stop there?" So, we've also published our documentation, including the accessibility requirements, test scenarios, and even the working automated tests which validate each one.

Here's what we've released, how it works, and why automated tests are worth the effort. One caveat: these components are opinionated and built for our needs. Feel free to reuse or adapt them, but test them in your product before relying on them. They're not a production-ready design system.

Documenting requirements is useful, but a document can't tell you whether a component actually meets them all. So, we converted each requirement into a test scenario using Gherkin syntax, and we wrote working Cucumber tests which validate them.

Gherkin is great because it describes complicated automated tests in plain language, using Given, When, and Then to describe each step. This makes it easier for non-developers to understand what the test is doing, and even help write tests. This matters because you don't need to be able to read all the complex JavaScript code to understand what the test is doing. A designer, a tester, a product manager and a developer can all read the same scenario, and all agree on what it means to pass or fail. And, even if you don't use JavaScript on your project, because Cucumber is available in most mainstream programming languages, you can still use the Gherkin feature files and write your own tests to validate them.

All of our test scenarios are written from a collection of shared steps, which was a lot of work at the beginning, because we had to write the underlying code to validate each one. But, each step is reusable, so scaling is easy.

We've published a full list of our test steps which work out of the box. This list is generated from the actual step definitions we use in the repository, so it's kept in sync automatically. This means any time we add a new one, you'll also get it for free.

Behind each test step is JavaScript code that controls a real browser using Playwright. The tests load the sample from a URL, and then interact with it the same way a real person would, by clicking things or focusing them using a keyboard. Then, they pull information from the browser, like the states and properties of the elements, and verify whether the things that were supposed to happen actually happened.

This is where our tests go much further than off-the-shelf accessibility checkers. A lot of these tools are valuable, and we do recommend using them, but they mostly inspect static markup. They often tell you about things like a button having no accessible name, but they don't often tell you about more complicated scenarios, like whether a focus indicator is hidden behind another element.

Most of our tests are automated, which has taken a bit of creativity at times. But, not everything can be reliably automated, and we'd be a bit suspicious of any tool that claims it can be. For example, an automated test can easily confirm whether a form field has an associated label. However, it's a lot more difficult to assess whether the label actually makes sense to the person reading it, because that relies on context. Arguably, we could capture screenshots and code snippets, and throw them over a wall to a large language model to assess whether something is readable. But, we think that it's ok to have some things reviewed by a human, because it's for humans.

In version 1.0.0, 97% of our scenarios are fully automated. For the remaining 3%, rather than just skipping them, we've added functionality which gathers the information a reviewer needs from the browser, and creates a list of what needs to be checked manually. Every test run produces a JSON report of what passed and failed in the automated tests, plus a Markdown checklist of what still needs verifying by a human.

Finally, all the assistive technology testing on each component is manual. Even if a component passes all the automated and manual tests and is technically compliant, it doesn't guarantee that there won't be any quirks with a particular screen reader or browser. So, we manually check each component, and if something is broken, we fix it.

In our strategy work with large organisations, we often find they struggle with sustainable accessibility. It's common for organisations to pay for an assessment, and then fix the issues. But, a few releases later, everything has quietly regressed, and nobody notices until a customer complains, or they pay for another accessibility assessment, which can get expensive.

Having automated tests breaks this cycle. You can plug them into your continuous integration (CI) pipeline, and have the tests run against every pull request, so you find out quickly when something is broken.

Here's why we think automated tests are so valuable:

Immediate feedback: a developer can run all the tests on their own device in about 30 seconds, and know straight away if they've broken something

Regression protection: every pull request runs all the tests as part of CI, so anybody reviewing your code can quickly check for regressions

Shared language: the scenarios are written in plain English, so accessibility requirements stop being technical, and become acceptance criteria the whole team can read

Traceability: Each scenario is tagged with a success criterion and conformance level, so it's easy to run a subset of tests, or search to see what's covered

Coding standards: Linting rules and CI checks are built in, so regardless of who writes the code, it should always feel familiar

More time to spend on usability: Because the mechanical checks are automated, people can spend more time on real-world testing, rather than inspecting the Document Object Model (DOM) for the hundredth time to see if a button is labelled

We've published the Accessible Components Library in its own repository on GitHub, and in the resources section on our website.

However, the cool part is that our website pulls all the documentation and tests directly from GitHub, so there's a single source of truth. The two can't drift apart or end up out of sync. So, if we want to add a new component to our website, we have to publish it to the repository first. This means you get it too, along with any tests and documentation that go with it.

We'll be releasing more components in the coming months. We've released a small set for now, so we can gather feedback and iron out any teething problems. So, make sure to star the repository to get any updates when they land.

We've released the library under the ISC licence, so you're free to use, copy, modify, or share any of the code and documentation, as long as you don't remove the copyright notice.

If you want to run the tests, the README in the repository explains how to install and run the tests.

If you want to fork it and expand it yourself, the development guide explains how the repository is put together, and how you can add your own components and tests.

If you spot a bug, or have ideas and opinions, please open an issue on GitHub.

We're not accepting pull requests at the moment, as each component needs a full set of requirements, tests, and assistive technology checks, which we need to keep in sync with the code. And, because these are the components we use in our own work, we're keeping things opinionated and in-house, at least for now.

#493. EMACS turns 50

📅 Oct 28, 2026  |  Category: Technology  |  Read Source →

How the MIT AI Lab’s text editor gave birth to the free software movement.

Programming used to be a very different experience from the one we know today. In fact, the first programmers didn’t write code at all; the six women who worked on the ENIAC, one of the world’s first computers, at the University of Pennsylvania in 1946 did it by physically configuring switches, cables, and plugboards.

A few years later, MIT engineers programmed the Whirlwind by punching code onto paper tape that was then loaded into the computer’s memory—making it among the first “stored-program” machines. Later, they and others moved on to punch cards, one for each line of code.

By the early 1960s, programmers with interactive computers could use a “line editor” to type their code on teletypes—large, noisy keyboard-and-printer machines. They’d type one line of code at a time, and their work would be saved on a spinning hard disk the size of a modern washing machine. But there was still no such thing as the now-familiar full-screen text editors that allow programmers to see and modify many lines at a time on a display.

One of the first such tools, EMACS, turns 50 this year, and it is still widely used.

EMACS first ran on the early video terminals at the MIT Artificial Intelligence Laboratory in 1976, but its core concepts were so powerful that it was rewritten for many operating systems in the decades that followed. Apple even distributed it with Mac OS X. Beyond that, the software-­sharing community that started around EMACS helped give rise to the modern-day free software movement and the GNU/Linux operating system.

EMACS’s roots begin with the TECO text editor (originally the “Tape Editor and Corrector”) that Dan Murphy ’65 created in 1962 for the pioneering PDP-1 computer at MIT. The program’s commands were uppercase letters: A user would type “I” to insert text, “D” to delete a character, and so on. When tape gave way as a storage medium to files on a huge shared disk, the “T” in “TECO” came to stand for “Text.” And as years passed, TECO became a full language that programmers could use to create new commands, called macros, for editing their code.

In the fall of 1971, Carl Mikkelsen ’76 created Control-R, an add-on program for TECO that took advantage of “glass teletype” terminals with video displays. Control-R immediately displayed changes to the file being edited on screen; the programmer no longer needed to reprint each line to see the changes. The drawback: The display could show only a few lines of code at a time.

“Experienced and sophisticated users found EMACS to be eminently more usable than any of the previous forms of editing.”

Then, in 1976, Richard M. Stallman, a researcher at the MIT AI Lab, saw a full-screen editor—called E—on a visit to Stanford’s AI Lab. Inspired, he returned to MIT and set out to improve Control-R. The most important change to the program’s underlying structure: Every key ran its own macro when pressed, making Control-R far easier to customize. The lab’s hackers took to Stallman’s code with gusto and started changing and adding commands.

That created an issue for Guy Steele Jr., SM ’77, PhD ’80. A graduate student in the lab, Steele frequently needed to help other lab members debug their programs. “I noticed that it was much harder for me to help someone who was using one of these packages rather than straight TECO,” he recalls. “Eventually, it occurred to me to try [to] broker consensus on a standard set of Control-R commands that everyone could agree to use.”

David Moon ’75, another member of the lab, helped out. Stallman jumped in as well, and eventually he took over. Together, the group assigned a standard set of commands that made use of the Meta key found on many of the lab’s early keyboards: Meta-F would move the cursor forward a word, Meta-B would move it back a word, and so on. They called the result EMACS, short for “Editor Macros” or “Editing Macros.” “My goal was not to construct a great new text editor,” says Steele. “I was trying to address a social problem.”

Nevertheless, EMACS was a great new text editor. Whereas Control-R could be tricky, EMACS users with “no technical experience at all” could learn to edit letters, emails, and even programs “within minutes or an hour,” according to a history by Bernard S. Greenberg, SM ’74. Meanwhile, “experienced and sophisticated users found EMACS to be eminently more usable than any of the previous forms of editing.”

Stallman started distributing EMACS to anyone who sent him a magnetic tape and a postage-paid return envelope. “EMACS does not cost anything; instead, you are joining the EMACS software-sharing commune,” he wrote in the 1981 manual. “The conditions of membership are that you must send back any improvements you make to EMACS.”

Greenberg, meanwhile, decided to write his own version for Multics, an early operating system by that time owned by his employer, Honeywell. Greenberg’s EMACS won first prize at the International Honeywell Software Conference in 1980, and Honeywell started selling it. Honeywell wasn’t alone in marketing a version of EMACS: James Arthur Gosling, a Carnegie Mellon graduate who went on to lead the development of the Java programming language, made a version that he eventually sold as a commercial product.

This transition from free to paid software ultimately spurred Stallman to launch a project to create an operating system that could be freely shared and improved by its users. He modeled this effort, called the GNU Project, after the increasingly popular Unix operating system from Bell Labs. “GNU” was short for “GNU’s Not Unix,” alluding to the fact that, unlike Unix, it would be free.

The project’s first major application was GNU Emacs (now restyled in lowercase). The GNU/Linux operating system was still years away, so, despite the project’s aim to create an entirely free operating system, GNU Emacs initally ran on Unix. It would eventually run on a range of operating systems, including Linux but also other Unix-based systems. When Apple launched Mac OS X, the first release of its Unix-based operating system, in 2001, GNU Emacs was included.

Apple stopped shipping GNU Emacs in 2019, but the company still has a program called mg (“Micro GNU Emacs”). Though it supports most EMACS commands, it lacks an integrated programming language, making it what some call an “ersatz EMACS.”

Meanwhile, much of Apple’s OS still has hidden support for EMACS commands. The keyboard has no Meta key, but Control-Option-B will move back one word, and Control-Option-F will move one forward.

We will post exactly what you need to do when it reopens. In the meantime: if you used the same password for your gitlab.alpinelinux.org account anywhere else, change it there. We have seen automated login attempts against our GitLab with passwords leaked from other sites.

If you have questions or concerns please reach out to us at infra@alpinelinux.org.

The vulnerability: CVE-2026-97229 is a critical (CVSS 10.0) vulnerability in how GitLab evaluates regular expressions in CI configuration. The underlying bug is in Onigmo, the regular expression engine built into Ruby. GitLab published fixed releases on October 12, but the fix itself is a set of patches to the Ruby that GitLab bundles in its own packages and container images. Upstream Ruby shipped the fix on October 23, in Ruby 3.3.13, 3.4.12 and 4.0.9.

The attack: On October 20 and 21, a newly registered account sent crafted CI configurations to our GitLab instance, which was still running 19.3.4 and did not have the October 12 fix. This crashed GitLab worker processes 8 times. In 4 of those crashes the attacker got partway through the exploit and failed at the next step. The attacker also downloaded our GitLab container image, which suggests they were tuning the exploit to our exact build. We have found no evidence that the attacker ran code on the server, but we cannot rule it out.

Our upgrade didn’t fix the vulnerability: Upgrading to GitLab 19.3.6 on October 22 didn’t fix the vulnerability. The fix isn’t in GitLab’s own code but in a patch to Ruby, which GitLab applies only in its official packages. Our image used standard Ruby, so it didn’t get the patch.

If you run GitLab with your own Ruby (from source or in your own container image) rather than GitLab’s packages, upgrading GitLab is not enough: you also need Ruby 3.3.13, 3.4.12, 4.0.9 or later.

If you use our alpinelinux/gitlab container image, pull alpinelinux/gitlab:19.3.6 again. The image published on October 27 contains Ruby 3.3.13. Any 19.3.6 image you pulled before October 27, and all older tags, are vulnerable.

What could have been exposed if the attack succeeded

Because we cannot rule out code execution, and the evidence we would need to confirm it no longer exists, we took the harder route and rebuilt the GitLab instance from scratch. This removes any foothold a possibly successful exploit could have left behind.

While GitLab is closed, our package mirrors, cgit, and mailing lists/IRC are available as normal.

We have found no sign of tampering in aports or the releases.

Every aports commit added October 20 to 22 arrived through a recorded push by a known developer. We checked this against records the attacker could not reach: a developer’s clone and all 45 builders. Every package built from October 20 to 24, on every architecture, came from commits as published on git.alpinelinux.org. The October 21 releases (3.21.9, 3.22.7, 3.23.7, 3.24.3) were built from those same verified commits.

We ran these checks on October 24, covering commits from October 20 to 22 and packages built up to October 24. Our GitLab stayed vulnerable until we closed it on October 27, so we are extending the same checks to that date.

The bug is in Ruby’s regular expression engine, so any program that compiles regular expressions from untrusted input is exposed, not only GitLab. Alpine 3.22, 3.23, 3.24 and edge ship Ruby 3.4.12, and Alpine 3.21 ships Ruby 3.3.13; both include the fix. Run apk upgrade to get it.

#446. Meta Andromeda: Powering the Next Generation of Ads Retrieval Through Model-System Co-Design

📅 Oct 28, 2026  |  Category: Technology  |  Read Source →

Meta Andromeda is Meta’s machine learning system for personalized ads retrieval, the first stage of the ads recommendation pipeline. Retrieval narrows a vast pool of eligible ads down to a small set of strong candidates in milliseconds; a later, more computationally expensive ranking stage then scores those survivors in fine detail.

Historically, the deep modeling quality of the ranking stage has been too costly to apply at retrieval’s scale. Building on the retrieval foundation established with Andromeda’s 2024 launch on the NVIDIA GH200 Grace Hopper Superchip, this post shares how co-designing the model, system, and hardware together brings near ranking-level performance to the retrieval scale.

The 2024 Andromeda deployment reimplemented retrieval with an end-to-end optimized retrieval implementation from custom AI hardware with hierarchical indexing and GPU-native operators to a purpose-built ML model, growing model capacity by four orders of magnitude. Since then, generative AI creative tools have helped advertisers rapidly create hundreds of millions of new ads, growing Meta’s ads candidate pool to an unprecedented scale.

Scoring such a large ad candidate pool with a more accurate model at a much higher system throughput requires fundamental technology breakthroughs in model quality, system architecture, and hardware utilization jointly.

Ads retrieval has an outsized ROI on incremental quality: Small improvements in retrieval model performance can drive large gains in advertiser value. The rapid expansion of our ads candidate pool makes optimizing for hardware capacity ROI an increasingly critical factor. The 2024 Meta Andromeda retrieval models have established a highly effective foundation with their GPU-optimized deep neural network architecture. To keep improving retrieval performance at a sustainable compute cost at our current scale, however, we must move beyond that paradigm. This requires a fundamental architectural evolution to push model performance boundaries significantly without a proportional increase in costs.

The 2024 Meta Andromeda system evaluates at tens of millions of ads per second per GPU card. Meeting the new business demand requires a throughput at multi-billion ads evaluated per second per card in the system. At billions of ads per second throughput, the memory bandwidth of passing ad tensors through memory hierarchy becomes the new bottleneck. Intermediate tensors between GPU kernels account for terabytes per second of memory traffic, and shipping ads between local CPU hosts and remote hardware accelerators evaluating models saturates the network link. This requires a new system co-design that unifies these fragmented, distributed workloads into a single GPU pipeline.

With retrieval running on GPU, the important optimization question is “How close are we to the hardware ceiling, and how much room remains for future model growth?” Answering this requires pushing each component of the retrieval pipeline to the limits of the current hardware generation, a challenge that motivated a joint collaboration with NVIDIA.

Each of these challenges drove a corresponding advance.

The latest iteration of Meta Andromeda introduces three synergistic architectural innovations that bring large language model (LLM)-inspired mixture-of-experts (MoE) into the retrieval (see Figure 1). With this highly expressive yet inference-efficient architecture, a new retrieval performance-efficiency Pareto frontier has been established: model performance approaches ranking-level in a typical retrieval-then-ranking system, at approximately 300x fewer inference-time FLOPs than the 2024 Meta Andromeda retrieval model.

On the user modeling side, we transitioned from a single user tower to an ensemble of specialized user towers as experts. This captures diverse, time-evolving, and contextualized user interests by integrating a vast array of high-fidelity signals: sequential ad engagement events, user-cohort representations, LLM-derived semantic features, and cross-surface co-engagement signals.

In the candidate ads tower, we employ a joint encoding strategy that incorporates real-time serving context, ensuring that downstream interaction models receive context-aware representations.

In the interaction overarch layer, the interaction model evolved from dense neural networks into an MoE attention-based gating network that dynamically routes candidates across the most relevant user experts, delivering near-ranking-level performance at a fraction of the FLOPs.

A defining property of the new architecture is that its performance is co-designed with the underlying hardware execution model. Model inference throughput has reached over 10 billion ads per second on a single GH200 GPU, and this efficiency allows model capacity to grow further, through richer feature interactions, additional expert sub-networks, and deeper architectures, without a proportional increase in GPU cost. Each incremental model advancement translates into greater advertiser value.

The 2026 Meta Andromeda pushes the model-system co-design to the next level with two innovations — a single GPU kernel fusing both model and system workloads per user-ad interaction and a strategy to co-locate per user request logics with per user-ad GPU kernels in a single GPU box. To this end, a highly optimized and fully fused GPU pipeline is built to host the entire end-to-end Meta Andromeda workflow.

At a high level, Meta Andromeda’s inference time per user-ad workload is a compact sequence of operations across model execution and system logics — gathering embeddings, executing user-ad interaction models, and scoring. The ~300x FLOPs reduction in the retrieval MoE gating architecture creates the necessary headroom and is less resistant to fully fuse both model execution and non-model system workloads into a single GPU kernel, compared to the 2024 launch where only operations within the model execution were fused. Consequently, the fused kernel now runs at over 10 billion ads per second on a single GH200.

This matters because retrieval workloads are fundamentally memory-bandwidth bound. At billions of ads per second, even a small intermediate tensor per ad multiplies into terabytes per second of high bandwidth memory (HBM) traffic. The memory workload of these intermediate tensors, not arithmetic, becomes the dominant bottleneck in multi-kernel retrieval pipelines.

The fused kernel eliminates this bottleneck entirely. Rather than dispatching multiple small GPU kernels for model and system operations, it executes the entire per user-ad computation in one pass. Intermediate results stay in GPU registers and thread block shared memory and are never materialized to HBM, achieving high utilization of the GPU’s peak memory bandwidth rather than wasting it on redundant intermediate traffic.

Measured in isolation, the per user-ad fused kernel runs at multi-billion ads per second on a single GPU. However, per-user request operations such as the index matching (i.e., enforcing advertisers’ targeting rules) and top-K selection run on separate local CPU hosts and communicate with the fused GPU kernel scoring service on remote accelerators through the network connection. At multi-billion ads per second throughput, this traffic alone saturates the network link, making the network bandwidth become the bottleneck rather than GPU compute.

The co-design response was to collapse the system architecture to match the model architecture: co-locate index matching, scoring, and top-K selection on the same GPU. Instead of shipping large candidate lists across hosts, the system sends a compact request payload — user features and a targeting query — to a single GPU server, which runs the entire retrieval pipeline locally and returns only the final top-K results. This reduces network traffic by ~100x and shifts the system back to a GPU-compute-bound regime.

Moving index matching onto the GPU is not straightforward. Ads index matching evaluates complex advertiser-defined targeting logic across tens of feature categories, and must support real-time index updates as ads are created, modified, or expired throughout the day. Supporting this on GPU required redesigning the index structure for GPU-parallel execution while preserving the full fidelity of production targeting semantics.

Combining the aforementioned two innovations, the fully co-located single GPU pipeline processes over one billion ads per second on a single GPU server while scoring every eligible ad in the candidate pool. This is a new throughput benchmark for ads retrieval-stage models, and as the next section describes, significant headroom remains.

With the production pipeline running at over one billion ads per second, a natural question follows: How close is the system to the ceiling of the current generation hardware, and how much headroom remains for future model growth? In early 2026, Meta and NVIDIA launched a joint collaboration to answer this question — systematically optimizing each component of the retrieval pipeline to push throughput toward hardware limits. NVIDIA contributed optimized GPU kernels, and Meta integrated and benchmarked the full pipeline. Each component achieved 2x to 5x speedup over the baseline.

The optimized gating kernel improved by 5.3x, from 2.4 billion to over 10 billion ads per second, reaching ~85% of the GPU’s peak HBM bandwidth. At this throughput, the execution time / latency of the gating mechanism is just as fast as what a simple dot-product scoring kernel achieves on the same hardware — while the model is substantially more expressive. This is the co-design validation: the additional model complexity is essentially free on Tensor Core hardware. INT8 quantization achieved a further up to 2x throughput increase over the optimized FP16 kernels, with accuracy on par with 16-bit precision.

Through targeted GPU kernel optimizations, index matching throughput improved over 2x, reaching over 100 billion ads per second — an order of magnitude higher than the scoring network. This headroom means index matching can be re-run across multiple retrieval pathways without becoming a bottleneck.

Beyond individual kernels, the collaboration profiled the full retrieval flow and identified that data movement between pipeline components — not computation — accounted for a significant fraction of end-to-end latency. By co-designing data layouts across index matching and scoring to eliminate unnecessary indirection, the team removed this overhead. With all optimizations applied, the full pipeline benchmarks at multiple times the current production throughput on a single GPU server, with further gains expected as additional optimizations integrate into production.

Building on the Hopper results above, we are extending our optimization and co-design work to Grace Blackwell. Here, we are focusing on platform design optimizations that enable different CPU-to-GPU compute ratios, which our work so far suggests is an important factor for Andromeda-like workloads. We are evaluating how sensitive end-to-end application performance is to these ratios, using Grace-class CPU performance and Blackwell-class GPU performance for their respective parts of the workload.

More broadly, we are exploring how these findings extend to the next platform generation, where greater flexibility in CPU+GPU execution, resource ratios, and coupling could bring more of these architectural improvements to bear on Andromeda-like workloads.

These results confirm that the co-designed retrieval pipeline is not yet at its ceiling. With quantization unlocking further scoring throughput and index matching operating at an order of magnitude above the scoring network, the architecture is positioned to absorb significantly more model complexity — deeper interaction networks, richer feature spaces, and additional retrieval pathways — without proportional infrastructure growth.

The advances described here follow a single principle: The largest gains come from designing model, system, and hardware as one integrated stack, rather than optimizing each in isolation. The retrieval MoE gating architecture delivers near-ranking-level expressiveness at no additional serving cost. Fusing the entire retrieval pipeline onto a single GPU eliminates network and memory bottlenecks. And pushing the pipeline towards its hardware ceiling confirms substantial headroom remains.

Looking ahead, the co-design principle that drove these results applies equally to next-generation model architectures and hardware platforms, with the demonstrated headroom enabling continued scaling without proportional infrastructure growth.

InfoQ Homepage News Airbnb Cuts Recommendation Staleness from 2 Days to Seconds with Chronon

Oct 28, 2026 2 min read

Airbnb has extended its open source Chronon feature platform with Push Mode and Near Real Time (NRT) Model Transform to update sequence based recommendation embeddings within seconds of guest activity. The change reduced embedding staleness from nearly two days to less than a minute, with typical updates arriving within 10 to 30 seconds. Airbnb also reported a 1.67% improvement in offline NDCG and an approximately 0.33% increase in uncancelled bookings in online A/B testing.

The work builds on Airbnb’s JourneyFormer based sequence recommender, which uses a Transformer encoder to represent a guest’s booking, review and browsing history. Previously, the encoder ran as a daily batch job, generating embeddings that were stored in a low latency store. During a search, the ranking system retrieved the latest embedding and combined it with the live query, keeping the Transformer outside the latency sensitive serving path. However, activity occurring after the daily batch could remain absent from the embedding until the following run, with processing delays bringing effective staleness close to two days.

Airbnb’s initial architecture showing the daily batch sequence encoder, embedding store and online ranking path. (Source : Airbnb Blog Post)

Airbnb addressed the freshness problem by adding two capabilities to Chronon. Push Mode causes a streaming job to publish a notification when a feature value is committed, allowing downstream processing to react to updated guest activity rather than polling or waiting for a scheduled job. NRT Model Transform allows an already deployed model to run inside that streaming pipeline. Airbnb uses the same Transformer sequence encoder for the near real time path, avoiding a separate inference implementation for the streaming workflow.

The resulting pipeline captures events such as searches and listing views, combines them with the guest’s existing short and long-term sequence data, and triggers model inference when the updated feature state is available. The generated embedding is then written to the same low-latency store used by the batch system. Consequently, the online ranking path remains largely unchanged while the representation it retrieves becomes more current.

Pengyu Hou, Senior Software Engineer, Infrastructure at Airbnb, described the platform change as addressing the gap between event-driven data and model inference:

NRT Model Transform lets Chronon call an already deployed model ... directly from within the streaming flow.

The approach follows a broader feature serving pattern in which predictions can be updated when underlying features change rather than computed on every user request. Feast, another open-source feature platform, documents cached prediction architectures where inference is triggered by feature updates, trading additional writes and pipeline complexity for lower serving latency. Chronon instead integrates streaming computation and model transformation into its feature platform and emphasizes consistency between offline and online computation.

Airbnb’s near real-time Chronon architecture (Source: Airbnb Blog Post)

Airbnb has contributed Push Mode and NRT Model Transform to the public Chronon repository. Chronon supports both batch and streaming computation and provides online feature serving designed to maintain consistency between training and production inference.

#517. AlpineBSD

📅 Oct 28, 2026  |  Category: Technology  |  Read Source →

AlpineBSD is an operating system based on the NetBSD kernel with a userspace inspired by Alpine Linux and the objective of making it possible to use as little AI-generated software as possible. There is no LLM output included in the base system or main package repository (AlpineBSD AI policy).

AlpineBSD is a work in progress. There is currently no installer available. For the adventurous, a very high-level installation guide is available here.

AlpineBSD ships the NetBSD kernel, libc, and essential platform-specific tools like mount.

NOTICE: The NetBSD kernel has spotty hardware support, much less so than Linux. You cannot necessarily expect AlpineBSD to work on any random computer you have lying around. Consult the NetBSD supported hardware list for more information, particularly for laptops.

AlpineBSD ships with the apk-tools package manager and busybox, and a slightly more GNU-oriented userspace, preferring e.g. GNU make over BSD make. AlpineBSD is not a fork of Alpine Linux, its package collection is original (though many packages are ultimately based on aports).

Alpine Linux uses the OpenRC init system. Currently, AlpineBSD uses s6 and we intend to add OpenRC as an alternative.
