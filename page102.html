#787. Findings from the $1M Vercel Sandbox challenge

📅 Oct 29, 2026  |  Category: Technology  |  Read Source →

In August, we launched the $1M hacker challenge for Vercel Sandbox, inviting security researchers to try and escape Vercel Sandbox. We also coordinated with cybersecurity experts Trail of Bits to review the source code and security architecture.

One Linux kernel zeroday vulnerability uncovered

No reports showed anyone accessing customer data in Vercel Sandbox. The most severe finding was the defect in the upstream Linux kernel.

The program's most important report arrived on day three.

Paulos Yibelo of pwn.ai, a HackerOne researcher working from a standard sandbox with no special access, found a defect in the Linux kernel's networking stack. Paulos discovered that specially crafted packets sent from within the microVM enabled three different attacks:

In the first attack, memory from the host, the machine your sandbox shares with other tenants, shows up in packets the guest sends over the internet. This can happen continuously, for as long as the guest keeps sending.

This attack was demonstrated against Vercel production sandboxes.

The researcher also found that by sending specific packets, they could compromise the host.

First, by sending two packets, the researcher crashed the host machine, shutting down every sandbox running on it. Second, using the same flaw, they were able to run commands with full administrator privileges on the host, breaking out of the sandbox’s isolation boundary.

The packet-related crash and code execution attacks were demonstrated on the researcher’s own KVM and Firecracker machines matching Vercel Sandbox configuration.

Almost every major cloud provider isolates customer workloads on this same layer of the Linux kernel, so any defect is shared-infrastructure risk.

Immediately after being notified, we collaborated with the researcher to understand and mitigate the vulnerability, working with AWS and other industry partners to prioritize a fix, and ensuring that Vercel customers and other developers using the kernel were safe.

The researcher also contacted the kernel maintainers and worked with them to create candidate patches. Fixes are under private review and CVEs are pending, so we are not publishing additional details until the patches are public. We are disclosing the existence of the vulnerability because it was separately disclosed in public.

The HackerOne challenge made bounties available to any researcher, but we also extended our program to include internal evaluations and an independent investigation.

Before launching the public bounty, we performed live security assessments internally with full source access and support from the engineers who created and maintain Vercel Sandbox. We also engaged Trail of Bits, bringing on two engineers to evaluate our security architecture.

Not every finding came from the outside. Marcos Hernanz, a Vercel intern, found a cross-tenant data leak in the Linux device-mapper storage layer. This vulnerability let any sandbox read recycled disk blocks from previously deleted sandboxes.

Trail of Bits spent four engineer-weeks inside our source code, with full access to the repositories and two enterprise test teams. They delivered 20 findings, and each was tested, confirmed, and referenced to the exact code.

They also performed an architectural review and concluded that our virtualization boundary is sound. Each sandbox runs on its own Firecracker microVM with a dedicated guest kernel, and the device model is deliberately tiny. No guest shares a running kernel with the host, or with another tenant.

On top of that foundation, they gave us three structural recommendations, which we implemented:

Find and eliminate all trust in the guest. Our control plane accepted values returned by software running inside the microVM, and every one of those values is tenant input. Anything that crosses the boundary should be derived server-side or signed with a key the guest cannot reach.

One policy, one decider. Egress enforcement was split across subsystems that each parsed the same network policy independently, and they did not always agree. We now use one canonicalization routine per data type, one component per decision, and revalidate connections when policy changes.

Assume the next zero day. Keep host and guest kernels up to date, reduce the kernel attack surface via build and runtime configs, disable nested virtualization, and use Firecracker’s jailer to run each microVM process with restricted permissions and isolate it from the rest of the host.

We received 1,285 reports in two weeks. This volume is only possible because researchers now hunt at AI speed.

Here is a breakdown of reports by category:

We have paid out $242,000 in bug bounties.

The medium, Low, and Informative findings are small policy-boundary gaps, like a firewall rule that behaved differently than documented and a field that trusted the guest more than it should.

The most severe finding was the Linux kernel zero day defect, and no reports showed anyone reading a customer’s files, secrets, or application data.

We were most impressed with the heterogeneity of the reports. It was clear that researchers used different setups and have different obsessions. Some clearly know Linux namespaces and steered their agents straight at the kernel boundary. Others went after the network policies, and many went after areas we didn’t think to put on the menu.

That variety is what you're funding with a public challenge. Here's one of the more interesting findings it produced.

Filed on day one of the challenge, this report is our favorite example of why we run a public bug bounty, even after internal assessments and a white-box engagement.

When you snapshot a sandbox, the control plane has to record where the snapshot data landed: {storage_url, size, checksum}. The flaw the researcher found was subtle: that answer came from software running inside the guest, and services running on the host trusted it. That is a trust-boundary violation. The guest is where our customers (and hackers) run untrusted code, so the host can never take its word as authoritative.

The researcher combined a known, documented container-escape primitive with this trust flaw. They intercepted the snapshot response inside their own sandbox and rewrote it, swapping the storage objects of two snapshots belonging to two separate accounts they owned. That meant restoring "your" snapshot materialized the other account's entire filesystem.

The researcher demonstrated that each account could read and modify the other’s files, verified the results using hashes, and preserved the test resources so we could independently reproduce the findings.

The limits of this attack matter. Aiming the swap at a specific victim required knowing that victim's internal snapshot storage key, a random 96-bit identifier the platform generates per snapshot and never exposes through the API. The only place that key appears is inside the victim's own sandbox. The researcher owned both accounts, which is what made the proof possible; there was no demonstrated path for a stranger to target another tenant. We still treated it as a priority fix, because a boundary that depends on a secret staying secret is not a boundary.

Trail of Bits independently flagged the same root cause in their assessment, which told us the finding was real, important, and discoverable from two completely different angles.

The fix shipped within a week, and the control plane now binds every snapshot object to the project that created it and rejects anything else. Snapshot creation moved out of the guest-reachable environment into a host-side service, and storage paths are project-scoped with strictly validated URLs.

We would like to thank every researcher who filed a report, whether their finding was a zero day or a duplicate. Every technique discovered in the challenge informs how we protect the workloads running on Vercel Sandbox.

Thank you also to Trail of Bits for your comprehensive internal investigation and guidance.

#766. Vercel Drives is now generally available

📅 Oct 29, 2026  |  Category: Other  |  Read Source →

Vercel Drives is now generally available for Vercel Sandbox on Hobby, Pro, and Enterprise.

A Drive is persistent storage that you mount as a directory in a Vercel Sandbox. Its files remain available after the sandbox stops, so later runs and other sandboxes can access them by mounting the same Drive.

Use Drives to preserve an agent’s workspace or file-based memory across runs, or to make datasets, models, dependencies, and build artifacts available across sandboxes.

You can also fork a Drive into independent writable Drives. Forks inherit the source Drive's data, region, and maximum size, then store their own changes. Parallel workers can start with the same files and make changes without affecting the original or one another.

With Secure Compute routing enabled, Connect’s provider requests use the selected network’s dedicated static IP addresses instead of Connect’s shared IPs. Requests to obtain and refresh access tokens follow that route; your app’s direct API routing is unchanged by this setting. Credential management stays the same, so you don’t need to store long-lived provider secrets in your app or build OAuth flows yourself.

To enable Secure Compute routing for a supported connector and all projects that use it:

Open your connector’s Settings in the Vercel dashboard.

Under Secure Compute Routing, choose an existing network.

If your provider uses an IP allowlist, add the selected network’s displayed IP addresses to it in the provider’s settings.

Requests for initial connector creation and all provider discovery requests bypass the selected network and connect directly to providers. If the selected network is unavailable, routed requests fail instead of falling back to Connect’s shared IPs.

#741. Python on Vercel is now generally available

📅 Oct 29, 2026  |  Category: Technology  |  Read Source →

Python on Vercel is now generally available. Build and run Python applications with the frameworks, libraries, and tools you already use.

Vercel automatically detects supported frameworks and configures the build and deployment. Your applications run on Fluid compute, which manages concurrent requests and scales with traffic. Idiomatic Python SDKs let you work with storage, queues, durable workflows, and AI models directly from Python. For full-stack projects, the Python backend and frontend share a workflow for local development, preview deployments, and production releases.

Ten months ago, we set out to make Vercel the best place to build and run Python applications. We wanted the experience to fit how Python developers already work, with three goals guiding our decisions:

Idiomatic Python SDKs. Working with Vercel infrastructure should feel familiar to Python developers, with APIs that use type annotations, async/await, and context managers.

A shared workflow for both the frontend and backend. Python applications often include a JavaScript frontend, so developers should be able to run both locally, review them in the same preview deployment, and release or roll them back together.

Compatibility with the Python ecosystem. The runtime should use CPython, the standard Python interpreter, on Linux to preserve compatibility with the packages and tools Python developers already rely on.

The first test of those goals is what happens when you deploy a Python application on Vercel: its framework, dependencies, and project structure should guide how it’s built and run.

We’ve worked to make Python feel native on Vercel. Vercel reads your project’s dependency files, including those managed by uv, and automatically detects frameworks such as FastAPI, Flask, Django, and FastHTML. Framework defined infrastructure configures builds and request routing, with framework-specific support for serving static assets through the CDN.

For applications with a frontend, Vercel Services brings both parts into one project. Running vercel dev starts them together, and shared previews let you test backend changes with the frontend that uses them.

For long-running workers that pull jobs from queues or databases, Vercel Daemons keeps your containers running with your Python code along with any of its packages, and system dependencies.

A Python backend might need to store files, send messages, run durable workflows, or call AI models. We’ve built Python SDKs for these tasks, with APIs that follow the conventions of the language:

Generate and stream model responses, call tools, and build agents.

Create and control isolated environments for running code.

Define durable workflows with retries and saved execution state.

Send and receive messages for background work and notifications.

Upload and retrieve files in object storage.

Obtain credentials for calling external APIs.

Python SDKs for storage, messaging, workflows, code execution, AI, and external API credentials.

These SDKs work alongside your framework and libraries, and the example below shows how they connect within a full-stack application.

Whether you’re starting a new project or deploying existing code, the framework guides cover setup and deployment on Vercel. For a guided full-stack project, the Python on Vercel course walks through building a FastAPI backend and Next.js frontend, then deploying them together with Services.

To show how these pieces work together, I built a collaborative web application to create and browse Python notebooks. It lets people create their own notebooks, publish them for others to browse or fork, and work with an AI assistant to write and run Python code.

The application pairs a Vite frontend with a FastAPI backend and uses PostgreSQL for notebook source and chat history. Services keeps the frontend and backend in one deployment, with the frontend served through the CDN.

Editing and running code: When a signed-in user opens their notebook in the editor, FastAPI creates or reuses a Vercel Sandbox running Jupyter, keeping user code isolated from the application backend. The browser connects directly to Jupyter, while mounted Drives provide the Python dependencies and workspace files.

Saving and publishing: The browser periodically sends the current notebook to FastAPI. FastAPI saves the source in PostgreSQL, renders changes as HTML, and uploads the result to Blob, so people can read published notebooks through the CDN without starting a Python kernel.

Sharing updates: After publishing a change, FastAPI sends a message through Vercel Queues. Each backend instance with connected browsers receives the notification and sends updated notebook listings over WebSockets, so people see changes without reloading.

Assisting with code: The agent uses AI SDK for Python and runs inside Vercel Workflows, which saves execution state and retries failed steps. Chat history stays in PostgreSQL, while notebook editing and execution tools work through the connected browser, which sends results back through FastAPI to resume the workflow.

The source code on GitHub includes the complete application and its deployment configuration. You can use it to explore these integrations or as a starting point for your own Python application.

Agents often handle complex work that continues across runs. As that work evolves, they may need a new environment with different tools, runtimes, or compute. They should be able to continue working with the same files when they change environments.

We built Vercel Drives to keep an agent’s files independent of its execution environment. It is now generally available for Vercel Sandbox. Agents can mount the same drive in a new environment configured for the next task and continue where they left off.

In this example, everything under /workspace persists on the drive. Everything else belongs to the sandbox. The next sandbox that mounts the drive finds the repository, and anything else the agent wrote there, where the previous run left it.

The drive keeps the agent’s files independent of the sandbox running it. An agent can resume work in a new sandbox or switch runtimes without transferring its workspace. Other sandboxes can mount the same drive.

Agents can prepare files on a drive once and reuse them across sandboxes. If one agent builds a dataset on a drive, other agents can mount read-only copies to analyze the data or generate reports without rebuilding the dataset. They use the shared files as input and save their results separately.

Agents can also fork a drive to explore different approaches independently. Each fork starts with the drive’s contents and provides its own writable workspace. Agents can try different transformations of the dataset in parallel without changing the original or affecting one another. Forks don’t merge back into the original drive.

Vercel Drives is now generally available for Vercel Sandbox on all plans.

Drives default to 1 TiB, or 1 GiB on Hobby, with up to 16 TiB available. See the documentation for configuration, snapshots, and limits, or the changelog for what changed at GA.
