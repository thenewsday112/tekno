InfoQ Homepage News AWS Shows Use of AI Agents to Triage Linux Kernel CVEs

Oct 27, 2026 4 min read

Engineers from Amazon Web Services (AWS) have described how the team that maintains the Linux kernel for EC2 infrastructure handles kernel CVEs. The process combines an automated filter, an AI agent and human review. The team also argues that it needs to move to newer long-term-support (LTS) kernels, as older branches collect fixes that are never backported.

Dylan Johnson and Justinien Bouron gave the talk at the Linux Plumbers Conference in Prague earlier this month. At the start of the recording, Johnson explains that the team maintains the kernel used within EC2 infrastructure. This is separate from Amazon Linux and from the kernels that customers run in their virtual machines.

After the kernel project became a CVE Numbering Authority in February 2024, the team saw about two kernel CVEs a week before 2024 and about 16 a day afterwards, with 848 published on 15 August 2026. The kernel CVE documentation states that the project cannot know how a given system uses the kernel, so users must decide which CVEs apply to them.

The first stage of AWS's process does not use AI. Bouron explained that kernel CVE records are published in JSON and list the affected versions and source files. A script discards a CVE if the kernel version is outside the affected range, or if none of the listed files are built into the image. In AWS's environment this removes about 70% of CVEs, although Bouron said the figure depends heavily on kernel configuration.

The remaining CVEs go to an AI agent. It receives AWS's kernel source tree, the configuration for each platform, a description of the environment and threat model, and a severity rubric. The agent produces a table that records the affected subsystem, the vulnerability type and the attack vector. Bouron said the team ignores CVSS scores, because they are not specific to its environment.

Two engineers usually review the table. According to the slides, the agent needs about 3.4 seconds per CVE, compared with minutes for a person. Bouron said review is now the slowest step in the process, and that the team does not intend to remove it.

When asked about accuracy, Bouron estimated that between 5% and 10% of the agent's decisions were problematic. This was an informal estimate, and the talk did not describe a formal evaluation.

The team also disabled kernel features it did not need, to reduce the number of applicable CVEs. Bouron called this approach "deceptively difficult". The slides list more than 32,000 configuration options, and removing the wrong one can cause bugs or performance regressions that appear months later.

The team's data also shows that older LTS branches receive fixes later and carry more unfixed CVEs. For CVEs affecting all six branches studied, the median time from a mainline fix to an LTS release was 31.8 days for Linux 5.10 and 18.1 days for 6.18. On 16 September, 1,709 known CVEs were unfixed in 5.10, compared with 229 in 6.18. These are counts for each branch, and they do not show how many affect AWS's own kernel.

Backporting fixes in-house brings its own risks. Bouron pointed out that CVE records often name only the final fixing commit. A team that misses the prerequisite commits may still be vulnerable after applying the listed fix.

AWS has shortened its own upgrades. Johnson said the move from 4.19 to 5.10 took about two years, measured from the start of porting work to full production deployment. The next upgrade took about a year, and the move to 6.18 took about six months. During the 5.10-to-6.12 upgrade, 43% of tracked issues were fixed in userspace, where workloads depended on older kernel behaviour. Johnson said the team will now run stable kernels in testing through the year, and move the fleet when each new LTS release appears.

Microsoft's Azure Linux team described a similar pipeline at the same conference. Its triage verdicts come from a rule table, and AI only suggests inputs to it. The team uses agents for backporting, and reported that a build-and-test feedback loop raised its success rate from about 50% to 80%. Google DeepMind's CodeMender, which InfoQ covered in October 2025, focuses on writing fixes. Its announcement stated that human researchers review every patch before it is submitted upstream.

Berend de Boer, CTO of Process Focus, commented on LinkedIn about the work involved in running cloud infrastructure. He listed host patching and Linux CVEs among the work that organisations take on when they build their own cloud. "Focus on what makes your business valuable to your customers," he wrote.

AWS has not released the tools. Asked about open-sourcing them, Johnson said the team would like to explore sharing the filtering tool. He also acknowledged that AWS's internal users make it easier to disable features than it would be for a general-purpose distribution.

#131. Announcing the Workload Conformance Working Group

📅 Oct 27, 2026  |  Category: Technology  |  Read Source →

Join us for four days of incredible opportunities to collaborate, learn and share with the cloud native community.Buy your ticket now! 9 - 12 November | Salt Lake City, Utah

We are excited to announce that the Kubernetes community now has a Workload Conformance Working Group. The working group is writing a shared standard for how workloads behave at runtime on Kubernetes. To get it right, we need input from the people who build those workloads and from the people who run the clusters they're deployed on.

Certified Kubernetes tests the cluster, and Kubernetes AI Conformance tests whether a cluster can run AI and ML workloads. Nothing comparable exists for the workloads themselves, so cluster operators still check each application by hand before routine maintenance or a Kubernetes upgrade.

The problems they find are familiar. A routine node drain is often how you discover that an application can't tolerate disruption. An upgrade can break an application that still depends on a removed API version. Others show up in day-to-day operation: workloads that ask for privileges they don't need, or reserve resources they never use.

Kubernetes already documents much of this, including security and handling disruptions. Even so, every cluster operator ends up repeating the same assessment, and application maintainers get the same questions from each environment they support. A common specification with repeatable tests would give both groups the same baseline to start from.

The first step is deciding which workloads and behaviors the specification covers. The scope includes security, resilience during disruptions, resource use, networking, storage, API usage, and observability, but the group hasn't yet agreed on specific requirements or on how to test them. However, one rule is already set: every requirement needs an objective test that a test binary can run, so nothing subjective goes into the specification.

The specification covers how a workload runs, and importantly not what it does. Consequently, application logic is out of scope of workload conformance. The binary won't retest anything Certified Kubernetes already covers, and it won't require a particular workload packaging format, or vendor tool like policy engine, security scanner, etc.

Two Special Interest Groups (SIGs) are sponsors for the working group.

Whenever a requirement touches another Kubernetes SIG's area, such as node behavior or networking, the working group will initiate conversations with those SIGs as well.

The working group is a forum where SIGs can get involved and shape the direction of Workload Conformance while the specification is being written. We're aiming for a stable first specification and working tests within two to three Kubernetes release cycles.

The specification will and needs to be built from real examples, so we want to hear your experiences. If you run clusters, tell us how you assess workloads today and what broke during your last upgrade or maintenance window. If you maintain an application, tell us what it needs from the cluster and where the existing guidance left you guessing.

You can find us in #wg-workload-conformance on Kubernetes Slack (visit slack.k8s.io for an invitation) and on the mailing list. The working group meets every other Wednesday at 15:00 UTC. The Zoom link and the agenda are in the meeting notes. If you want to raise a topic, add it to the agenda. Joining the mailing list usually adds the meeting invite to your calendar.

#545. The case of the 9 bit AES key

📅 Oct 27, 2026  |  Category: Other  |  Read Source →

Several PDF implementations advertise AES-256, but generate the 256-bit key from either a very small state space, or from insecure random sources.

We found that several PDF implementations generate their AES-256 file keys from state spaces small enough to enumerate. In MuPDF, only 9 bits of random state affect the actual AES-256 key. Other PDF editors like Foxit base their AES-256 key on time based randomness and thus also lead to keys that are trivial to recover.

PDF encryption protects the strings and datastreams in a PDF document, including metadata unless it is explicitly left unencrypted. The password protection mechanism has gone through a bunch of revisions over the years, moving from RC4 to AES and hardening password hashing against brute force attacks. The current version, revision 6, uses AES-256.

When a PDF is encrypted with AES-256, the password does not encrypt the document directly. The implementation generates a random 32-byte file key, which encrypts the content. The password and a salt are then hashed to derive a separate key, which encrypts this random 32-byte file key. Revision 6 makes this hashing deliberately slow; the older AES-256 revision 5 does not.

A PDF can have a user password for viewing and an owner password for changing permissions. Either unlocks the same file key, so the restrictions are up to the reader: with the viewing password, you can also make an unrestricted copy.

We found that this randomness is often generated very insecurely, allowing passwordless decryption of protected PDFs.

Workers AI runs GLM 5.3 with SGLang in a disaggregated configuration: a pool of prefill GPUs processes the prompt and produces the model's KV cache for it, then hands that cache over remote direct memory access (RDMA), via Mooncake, to a pool of decode GPUs that generate the response. The KV cache in GPU memory is a shared pool of fixed-size pages. Each request is assigned pages when it is admitted and releases them when it finishes. Pages are not currently zeroed between requests; the next request that gets a page simply overwrites it. This approach is common among inference engines and is necessary to achieve the best performance, but it means that the inference engine is responsible for tracking ownership of these memory pages. KV cache page ownership and lifetime tracking has to deal with not just shared ownership within a node (KV cache offload and token generation both access the memory with different lifetimes), but also ownership that is technically shared with the remote prefill node (which holds a simultaneous mutable reference to the page).

Furthermore, the size of this pool is not a configuration value. SGLang sizes it at startup from whatever GPU memory remains after loading the model weights. The model's advertised context length is a separate configuration value. Nothing forces the two to agree, and it is our job to check that they do.

On our GLM 5.3 prefill nodes with our configuration, the pool came to 681,280 tokens while the model's context length is 1,048,576 tokens. This bug belongs to a class of KV cache memory-safety bugs that Cloudflare has been working to address for several months. In each case, a page is freed, reused, or read while something else still has a claim on it. We see two common causes.

The first is page lifetime within a single node. Several tasks on a decode node can hold the same page at once: token generation, offload to host memory, the KV transfer receiver, and the abort and error paths. If one of them frees the page while another is still using it, a new request can be given that page while it is still being read or written. Our earlier fixes for decode offload (#24226, #30899) and double release on grammar errors (#30937) were of this kind.

The second is a race across nodes. When a request is aborted while prefill is still writing its KV cache to decode over RDMA, the writes already sent cannot be recalled. If decode frees those pages right away, those pages can be given to another request, and the late writes land in that request's KV cache. Cloudflare has contributed to the effort to fix this race through proposed fixes (#31357, #38961) and a reproduction script (#32564). #666. Billion-query-per-second lookup tables in C++

📅 Oct 26, 2026  |  Category: Technology  |  Read Source →

Daniel Lemire is a software performance expert. He ranks among the top 2% of scientists globally (Stanford/Elsevier 2025) and is one of GitHub's top 1000 most followed developers.

A lot of software spends its time mapping strings to values. A web server must identify the HTTP method (GET, POST, …). It must recognize header names. A URL parser must recognize the protocol (http, https, ftp, …). A compiler must recognize keywords.

In C++, the default approach is to put the strings in a std::unordered_map.

It works. But notice something: the keys are known when you write the code. They never change. And yet we pay at runtime as if they could change at any time: we hash the whole string, we pick a bucket, we follow a pointer, we compare, maybe we walk a list.

A hash function maps keys to slots. When two keys land in the same slot, we have a collision, and we must deal with it. Collisions are what make hash tables complicated and slow.

If you know all of your keys ahead of time, you can construct a hash function designed for your keys, a function that never produces a collision. It is called a perfect hash function. The idea is old: the GNU gperf tool has been doing it since 1989. You give it a list of keywords, and it generates C code.

We follow the same design as gperf. The slot for a key is computed as follows.

We add the length of the key to a few small values taken from an association table (asso) indexed by the characters at a few selected positions. Usually, one or two positions are enough. The table size is a power of two, so the modulo is a single bitwise AND.

Consider the four HTTP methods GET, PUT, POST and DELETE. We use only the first character. Set asso['G'] = 0, asso['P'] = 1 and asso['D'] = 0. Then GET goes in slot 3 + 0 = 3, PUT goes in slot 3 + 1 = 4, POST goes in slot 4 + 1 = 5 and DELETE goes in slot 6 + 0 = 6. No collision.

To look up PUT, we compute the slot (4), and we compare PUT with the one key stored in slot 4. One hash, one comparison. If you look up PATCH, which is not in the set, you land in slot 5 + 1 = 6, you compare with DELETE, and you are done: not found. There is no probing, no chain to walk.

How do we find the association values? We sort the characters by how many keys they touch. We then take them one at a time and try 0, 1, 2, … until we find a value that does not cause a collision. We never revise a value once it is set. It is a greedy algorithm with bounded work. The bound matters because we do all of this at compile time, and C++ compilers limit how much work a constexpr function may do.

With our library, you write ordinary C++23. There is no external tool to run.

The map is a compile-time constant. The compiler searches for the perfect hash function when it compiles your code. At runtime, computing the hash can take as few as four instructions: load one byte of the key, load one byte from the association table, add the length, apply a mask.

Computing the hash is cheap. But we still need to check that the string we are looking up matches the key stored in the slot. And comparing strings can be expensive: the textbook approach is a loop over the bytes with a branch for each byte. You can easily end up with dozens of instructions and several branches, and the branches are hard to predict when the strings vary.

Instead, we treat the key as a vector. Our processors, whether ARM or x64, have 16-byte registers. So we load 16 bytes unconditionally, even if the key is only three bytes long. We then use a shuffle instruction (tbl on ARM NEON) to zero the bytes past the end of the key. The stored keys are zero-padded at compile time. A single vector comparison handles the whole key. We go from about forty instructions and eight branches to five instructions and no branch.

But wait: is it safe to read 16 bytes when you only have three? Reading past the end of a buffer is fine as long as you do not cross into another memory page, and pages are at least 4 kilobytes. So we check whether the address is within 16 bytes of the end of its page. If it is, we take a slower path. Otherwise, we do the wide load. We traded several unpredictable branches for a single branch that is almost always taken the same way.

I ran the benchmarks on an Apple M3 Max with AppleClang 15. We look up the keys in random order and we report the time per lookup. Let us first consider the 20 standard HTTP header names.

We need about 1.3 ns per lookup, or about 5 cycles. The classic gperf needs 7.7 ns. Abseil’s flat_hash_map, an excellent hash table, needs 10.9 ns. And std::unordered_map needs 16.6 ns. We are thirteen times faster than the standard library.

It is not one lucky key set. Here are the results over several sets of keys, from 6 URL protocols to the 100 tickers of the S&P 100.

We stay between 1.2 ns and 2 ns per lookup. We are 3 to 6 times faster than gperf, and 7 to 13 times faster than std::unordered_map. Notice how gperf struggles with the JavaScript reserved words: there we are 17 times faster.

Why is std::unordered_map so much slower? The C++ standard essentially requires a chained hash table. A lookup hashes the whole string by calling a function, follows a pointer to a heap-allocated node and walks a list. Our lookup does a few loads and has no function call. The processor can retire over 8.6 instructions per cycle with our code, which is about as good as it gets on this chip, and it almost never mispredicts a branch.

On an Apple M4, with the URL protocols, we exceed one billion lookups per second.

If your keys are known at compile time, you should not pay for collision handling at runtime. A perfect hash function gets you down to one comparison. With some care, a lookup costs about five cycles. The library is a single header you can drop in your project: github.com/ConstexprCore/perfect_hash.

#537. How Noise-Cancelling Headphones Actually Remove Sound in Real Time

📅 Oct 26, 2026  |  Category: Technology  |  Read Source →

A noisy flight can make it difficult to enjoy a podcast or listen to music without turning up your volume super high.

Much of that disturbance comes from the steady rumble of the engines, which continues throughout the journey. Noise-cancelling headphones can reduce this background noise, making your listening experience more comfortable without requiring the surrounding environment to become any quieter.

This is possible because these headphones do more than physically cover your ears. They use microphones to capture surrounding sounds, electronic circuits to process the signals, and speakers to produce additional sound waves that counteract some of the incoming noise. The process happens continuously, allowing the headphones to respond to changes in the sound around you.

But how can one sound reduce another and how do headphones calculate the right signal quickly enough to make it work? The answer lies in the physics of sound waves and the real-time processing that brings this technology to life.

Before exploring how headphones erase background noise, we first need to establish the basic physics of what sound actually is.

Sound isn't a physical object. Rather, it travels as a series of pressure variations moving through the air. When someone speaks or an engine rumbles, it pushes air molecules back and forth, creating invisible waves of high and low pressure.

So a microphone’s primary job is to convert these shifting pressure variations into an electrical signal, just as a headphone speaker converts an electrical signal back into moving air.

Because sound consists of these shifting pressure waves, two distinct sound waves can physically interact with each other when they meet in the air.

This fundamental interaction leads us directly to the principle of destructive interference. When two suitably matched sound waves overlap in perfectly opposite phases, their pressure variations can partially or even substantially cancel each other out.

For instance, if one wave produces a positive pressure variation (a peak) while another produces an equal negative variation (a trough) at the exact same moment, the combined variation can approach zero.

Mathematically, this relationship is quite simple:

In this equation, p represents the sound pressure at a particular point in space and time. The crucial caveat, though, is that this cancellation is entirely local. So the waves don't disappear everywhere in the room. Instead, the noise cancellation works specifically by changing the sound pressure that reaches your individual ear.

To achieve destructive interference, the headphones must generate a sound wave specifically designed to oppose the incoming noise. We call this "anti-noise."

But it's not as simple as just playing a loud sound backward. The anti-noise signal needs to have an incredibly precise amplitude (loudness) and phase relationship with the original sound, precisely at the location of your eardrum.

Imagine an incoming sound wave that moves up and down like a roller coaster. The anti-noise must be an exact mirror image, moving down when the noise moves up and up when the noise moves down.

Simply having the opposite phase isn't enough, though. If the two waves don't arrive at the exact same time or if they have different amplitudes, you'll still hear residual noise. Because of this, consumer wearables don't generate a universal opposite wave for every sound in the entire room. Instead, they focus entirely on creating a very limited, tiny acoustic "quiet zone" right next to your ear canal.

So, how does a typical pair of ANC Headphones actually execute this in the real world? It all comes down to a continuously repeating signal processing pipeline.

First, external microphones capture the incoming ambient noise. In some advanced designs, internal microphones also measure the residual sound lingering near your ear.

Next, an internal digital controller processes this signal. It rapidly filters the microphone data and calculates the exact cancellation signal needed.

Then, the headphone speaker driver kicks into action, emitting a sound wave designed to oppose the incoming noise (the anti-noise).

Finally, the system continuously monitors and adjusts, constantly responding to your ever changing acoustic environment.

In this process, timing matters more than almost anything else. Sound takes time to travel and the digital system inside the headphones introduces processing and conversion delays. If the anti-noise arrives even a fraction of a millisecond too late, it can't cancel the original wave effectively.

The engineering challenge here is immense: the hardware must predict or respond to incoming noise while keeping its total delay exceptionally low. According to a 2018 study on the active feedforward noise control and signal tracking of headsets, minimizing processing delay is crucial for real-time applications because any lag immediately degrades the cancellation performance, especially for unpredictable sounds.

Not all noise-cancelling consumer wearables handle this processing loop the same way. Headphone designers can arrange their microphones and control systems in three primary configurations, depending on the desired performance and budget.

This setup places the microphone on the outside of your ear cup. The controller uses this early information to prepare a cancellation signal.

The advantage here is getting a head start. The challenge, though, is that the system must perfectly estimate the time required for the sound to travel from the microphone to the ear, factoring in its own internal processing delays.

An internal microphone sits inside the ear cup, capturing the sound right next to your ear, including the residual noise after cancellation. The controller uses this information to continuously correct its output.

Because it measures the result inside the cup, feedback alone has less opportunity to anticipate a sudden incoming sound before it reaches your ear.

Hybrid systems combine the best of both worlds. These systems use both external and internal microphone data to merge prediction with feedback-based correction.

As detailed in a 2019 study on reducing the effects of acoustic feedback in ANC systems, no single architecture is automatically best in every situation. Performance relies heavily on microphone placement, acoustic design, processing delays, and the specific type of noise you're trying to cancel.

Let's talk about the software side. An external microphone doesn't just pass a raw inverted signal directly to the speaker. The incoming audio must be carefully transformed using a digital filter to account for the headphone's own acoustic behaviour.

A digital filter uses the current and recent input samples to calculate an output signal. Its job isn't merely to invert every sample, but to output a signal that will successfully reduce noise after that signal has physically travelled through the headphone's speaker components and acoustic path.

To do this, many high-end headphones use adaptive algorithms. Filtered x Least Mean Squares (FxLMS) algorithm is one of the most established in active noise control.

The process is fascinating: the controller produces a cancellation signal, the internal microphone measures the residual noise (the "error"), and the algorithm uses that error data alongside a digital model of the speaker to ear acoustic path to tweak its filter coefficients. It's a continuous loop of measurement and refinement.

Not every pair of headphones uses FxLMS. Some rely on fixed, pre-trained filters, while others adapt actively. But as noted in the 2018 headset signal tracking research mentioned earlier, FxLMS based real-time control remains an incredibly effective standard for dynamic, on the fly adjustment.

If you've worn these headphones, you've likely noticed a quirk: they easily erase an aircraft's engine rumble, but struggle to block out a crying baby or a nearby conversation. Why does this happen?

It all comes down to frequency and predictability. Low frequency sounds, such as steady ventilation noise or a bus engine, have long wavelengths and change relatively slowly over time. This gives the controller ample opportunity to estimate the waveform and generate an accurate cancellation signal.

Conversely, higher-frequency and sudden sounds are incredibly difficult to predict. A slamming door, a loud hand clap, or a sudden shout changes faster than the controller's processing loop can respond. The microphone, processing system, speaker, and acoustic path all have physical constraints that make high-frequency tracking incredibly difficult.

Beyond this, the direction from which the sound originates also plays a crucial role. A 2014 causality study on feedforward active noise control headsets highlighted how different noise arrival directions alter the delays involved, directly affecting how effectively the hardware can align the phases for destructive interference.

Because active cancellation has these inherent limitations, passive noise isolation remains incredibly important. While active cancellation relies on electronics, passive isolation relies entirely on physical barriers, like dense ear cups, tight acoustic seals, and foam ear tips to physically reduce the amount of sound entering the ear.

Unlike ANC, passive isolation doesn't generate an anti noise signal. But interestingly, the two methods are perfect companions. A strong physical seal naturally handles the high-frequency noises (like chatter and sudden claps) that are difficult for an ANC controller to cancel effectively. Think of standard earplugs for studying, for example: they're entirely passive, relying on foam or silicone to block sound. Active headphones rely on their physical design to do exactly that, leaving the heavy, low frequency lifting to the electronic ANC system.

The physics and signal processing sound flawless in a laboratory, but the real world is messy. As you go about your day, your acoustic environment is constantly shifting.

If you turn your head while walking, adjust an ear cup, or put on a pair of thick framed glasses, the acoustic path between the speaker and your eardrum changes. Even a slight break in the physical seal around your ear alters the sound reaching the microphone. When this happens, a cancellation signal that worked flawlessly a minute ago might suddenly become far less effective.

Can headphones adapt to this in real time? Yes, but to varying degrees. High end adaptive algorithms constantly adjust their filter coefficients using measurements of residual noise. Other models might seamlessly switch between a set of pre trained filters suited to different conditions.

A 2022 study on adaptive-gain algorithms for fixed filters demonstrated how modern headphones combine pre-trained data with adaptive weighting to handle these sudden environmental shifts smoothly. Real-time processing doesn't necessarily mean every part of the system is rewriting its code on the fly, but rather intelligently blending fixed strategies with live adjustments.

It's time to correct a common misconception: active noise cancellation doesn't create a vacuum of total silence. Instead, it aggressively reduces unwanted low frequency sound. Human speech, sharp high-frequency noises, and sounds leaking through physical gaps will still easily reach your eardrum.

Some users occasionally report a feeling of "ear pressure" when they turn ANC on. This isn't the headphone blasting dangerous levels of air pressure into your skull. Rather, your brain is confused. It registers the sudden lack of low-frequency ambient noise as the sensation of pressure changes, much like an airplane ascending.

From a health perspective, ANC is quite beneficial, though it isn't a cure all. While it doesn't automatically protect your hearing from loud environments, it reduces background noise, which naturally encourages you to listen to your music at lower volumes. In fact, a 2012 study on noise canceling headphones and hearing hazards found that when people used ANC in background noise, their preferred listening levels were up to 4 dB lower compared to using ordinary earbuds.

While this isn't a guarantee for every listener, it shows how smart engineering can indirectly help protect our ears.

The next time you're sitting on a noisy train or an airplane, take a moment to appreciate the invisible tug of war happening right next to your ears. Your headphones aren't just a physical barrier against the outside world. They're actually actively measuring incoming noise, processing complex algorithms in milliseconds, and deploying targeted anti noise via a tiny speaker to reduce the original sound near your ear.

The sheer engineering required to pull this off is impressive. The internal controller must perfectly account for processing delays, acoustic behaviour, changing noise and the physical limits of its hardware. A quieter listening experience is the beautiful result of several systems working together seamlessly, bridging the gap between physics and computing in a device you can easily carry in your pocket or backpack.

#319. Scope your Personal Access Tokens

📅 Oct 26, 2026  |  Category: Technology  |  Read Source →

A Personal Access Token can do anything you can do in your Supabase account, across every organization and project you belong to. Until now, every tool you gave one to could access everything in your account, even when it only needed to perform a single, read-only task. Your CI pipelines, deployment scripts, and AI coding agents all have different jobs and their access should reflect that.

Now you can scope a token so what it's permitted to do matches the tool's job. If a coding agent only needs to read one project's database, you hand it a token limited to that project and that one read permission.

Token scoping became generally available on September 28, and we announced it at Supabase Select on October 2. Every token you create in the Dashboard is now scoped by default, although you can still create one with full account access if you need to. Nearly nine out of 10 tokens created there since launch have been scoped.

Take the coding agent from above. It needs to inspect tables, generate types, and run read-only SQL, but it shouldn't be able to write to your database or access other projects. A deploy script would get a separate token with the write permissions its workflow needs.

Head to your access tokens page to build the agent's token. Choose its resources, permissions, and expiry, then review its access:

You can grant access across multiple organizations, but the Dashboard recommends a project-level scope. Since the agent is only working on one app, select that single project.

Next, you define what the token can do within that project. The Dashboard offers presets that set all permissions at once (No access, Read-only, and Full access), but because "Read-only" includes secrets like API keys, start with the No access preset. From there, toggle "Database" to read.

You should never let a temporary tool hold a permanent key. You can set a custom expiration date up to one year out. If the agent's work is done in a week, its token should be too.

Before you hit create, the review screen shows you what you're authorizing. Expand any permission to see the specific Management API endpoints and MCP tools it covers. For the agent, "Database read" covers the tools needed to list tables, generate types, and run read-only SQL.

You'll also see a risk banner rating the token's combination of reach and write access as Low, Medium, or High.

Copy the token value before closing the page because it's shown only once. Its scope and permissions are fixed at creation. To change them, create a replacement token.

A token's permissions are strictly bounded by your own user account. Every request evaluates both the token's scope and your current user role.

If you leave an organization or lose permission to read a project's database, the agent loses that access too. If your access is later restored, the token works again. The token's detail view marks any resource you can no longer reach.

The same check applies when you create a token. The Dashboard flags any permission you select that your current role doesn't have. You can still add it to the token but the token can't use it until your role includes it.

A token created with a scope starts with the prefix sbp_fc and works in your existing workflows using standard bearer authentication.

If an API request is missing a permission, the 403 response names it in a missing_permissions field. Check that your own role has that permission and then add it to the replacement token. A request for a project outside the token's scope gets a plain 403.

Each tool checks permissions before executing and returns a tool error if denied. With the agent's Database read permission it can use execute_sql for read-only queries. A SQL write returns a Postgres permission error rather than a 403. Running apply_migration needs a separate Migrations read-write permission.

The browser flow of supabase login still creates a token with full account access today but we're updating it to create one with the scope you choose. Until then, create the token in the Dashboard and pass it with supabase login --token. For CI environments, set the SUPABASE_ACCESS_TOKEN environment variable which overrides any locally saved tokens. Database commands that rely on SUPABASE_DB_PASSWORD bypass token permissions entirely. If your CI workflow includes supabase link, your token also needs read access to Project Settings, API Keys, and API Key Secrets.

For a full map of permissions to endpoints and MCP tools, see the Personal Access Tokens documentation.

Your existing integrations keep working, and no deprecation or shutoff date applies to them. Every existing token works until it expires or you delete it.

In the Dashboard, tokens with full account access carry a "Legacy" badge, and the "Create legacy token" option is still there for a workflow that needs it.

Choose an agent or integration and create a token for it, limited to its project and the permissions its job needs. If it already has a token with full account access, create a replacement and swap it in.

If a permission you need is missing, or the creation flow doesn't fit your workflow, submit a support ticket.

#6. Our Response To The eMudhra Key Disclosure Incident

📅 Oct 26, 2026  |  Category: Technology  |  Read Source →

Stories about how and why companies use Go

How Go can help keep you secure by default

A complete introduction to building software with Go

Reference documentation for Go's standard library

Tips for writing clear, performant, and idiomatic Go code

Learn and network with Go developers from around the world

Roland Shoemaker, on behalf of the Go Security team 26 October 2026

On October 19, the Go team initiated an expedited security release to protect Go users and their applications from a critical public key infrastructure (PKI) compromise involving certificates issued by eMudhra.

Within approximately seven and a half hours of being notified, we shipped a targeted patch, which was included in our first-ever URGENT track security release.

Here is the context behind the incident, why Go stepped in at the runtime level to protect our users and how our incident response unfolded.

On October 17, Mozilla added eight intermediate certificates (six used for TLS, and two used for code signing) issued by a root certificate controlled by eMudhra to OneCRL, effectively blocking their usage in Firefox. Soon after, a number of security researchers noticed this and began investigating what might’ve caused this.

On October 19, the Go Security team was made aware of these investigations and their conclusions, which showed that the keys associated with these intermediates were trivially weak, allowing recovery of the private keys in microseconds.

Due to the fact that the eMudhra root certificate was present in most trusted root programs, recovering the private keys would allow any attacker to sign arbitrary TLS certificates for any domain name, without the usual requirement to show proof of control of said domain name. This would allow an attacker to man-in-the-middle (MITM) TLS connections and present a valid certificate for a domain name they did not control, effectively allowing them to impersonate any TLS server the targeted machine attempted to connect to.

Go ships a TLS certificate verifier in the standard library. When users use net/http or crypto/tls to connect to a TLS service, the verifier is called to check if the certificates the other side of the connection presents are valid. On Windows and macOS we delegate these checks to the platform APIs, and on Linux, which lacks platform APIs, we use our own verifier implementation.

Since Linux does not have a uniform built-in mechanism to handle revocation checking, and in order to provide a timely fix for users on other platforms that might not receive platform updates, we decided the best way to protect Go users was to do an URGENT track security release which similarly removed trust.

A typical Go security release follows a multi-day process, with advanced pre-announcements in order to allow those who rely on Go to prepare. In this case, because we believed that private key exposure was imminent, our team chose to use the URGENT track for the first time in order to ship protections before active public exploitation could begin.

Our Security team was alerted by an independent external researcher, citing unreported actions by Mozilla and other organizations to remove trust in eight eMudhra intermediates. It became clear quickly that this was due to weak private keys they used.

Mozilla independently reported the issue to our Security team, confirming the issue, and asking that we not immediately disclose the issue, but encouraging us to release a fix as soon as possible.

We finalized a patch which blocked the usage of certificates which chained to the compromised intermediates, and thanks to the researcher who initially alerted us to the issue, had a set of certificates signed using the recovered keys to test against.

We began the process to release minor Go versions 1.27.3 and 1.26.10 containing our patch. Due to the urgent nature of this issue and its exploitability, and with the belief that the private keys would likely become publicly known within hours, we decided an immediate release was the most prudent option.

We finalized the release and announced it publicly. At this time the underlying issue was still not widely known. In an effort to give other defenders a chance to protect as many users as possible without revealing to attackers how the issue could be exploited, our patch and communications were somewhat opaque, warning users that we were “blocking trust in a small set of intermediate certificates due to specific security concerns around their operation” and urging users to immediately upgrade to this release.

In under seven and a half hours from initial notification, patched Go releases were live worldwide, giving users everything they needed to secure their deployments before the keys became public.

By the morning of October 20, numerous independent researchers had publicly disclosed the weak keys.

This was our first ever URGENT track security release, and during the release process we ran into a number of issues which caused the release to take longer than expected.

While we are happy we were able to get a release out the same day we were notified of the issue, in the modern security environment we feel that we should be able to provide releases in a more compressed timeline. The issues we ran into caused our release process to take just under four and a quarter hours from start to finish.

These issues had previously not been problematic, since the typical release process is split up over a number of days.

We’ve subsequently made a number of changes to improve our release efficiency, which should significantly reduce the time it takes us to push out a release, enhancing our ability to quickly respond to urgent security threats.

PRIVATE track security fixes are pre-announced three to seven days before their release. URGENT track fixes happen on a shorter time schedule, but we could have pre-announced the upcoming release when we began the release process, giving users at least a few hours to prepare.

While on Windows and macOS we rely on the revocation mechanisms the platform APIs provide, on Linux we don’t currently have a similar mechanism. The lack of this support was one of our major drivers to issue an expedited security release, as we did not want to leave Linux users exposed to this issue longer than was necessary.

Hence we are planning on prioritizing work to bring parity to revocation support on Linux, to help mitigate this class of issues in the future. Part of this work will involve investigating adding support for the upki project, which aims to “provide reliable, privacy-preserving and efficient certificate revocation” for Linux (see issue #82402).

If you run Go binaries which interact with network services using TLS (such as directly via net/http or crypto/tls or via a dependency such as gRPC), ensure you are running on the latest minor releases. Binaries rebuilt with Go 1.27.3 and 1.26.10 will automatically reject certificates issued by the compromised eMudhra intermediates.

You can verify your current toolchain version using go version and you can check the version of Go a binary was built with using go version -m .

The govulncheck tool can also be used to determine if a binary is affected by this issue:

For us, securing Go and its users extends beyond fixing direct security vulnerabilities in the runtime and libraries we ship. In order to keep the ecosystem secure, we believe we also need to provide users with the right tools to write secure software, look towards the future of cryptographic algorithms and protocols, and proactively respond to ecosystem wide issues when we can.

#2. How to fund Rust contributors

📅 Oct 26, 2026  |  Category: Technology  |  Read Source →

There is always so much to do in the Rust Project! New features to implement, bugs to fix, performance optimizations to make, issues to triage… It takes a lot of work to keep our high bar of quality while also shipping new features and improvements. And the workload keeps increasing with the continuous growth of Rust adoption.

As is unfortunately common in open source projects, a large fraction of that work is currently done by volunteers. That causes various issues, such as people burning out or complex features taking many years to ship.

Unsurprisingly, one of the best ways to help improve that is to get more people who work on Rust funded! This year, several funding initiatives started ramping up, and we already experience many positive effects. They helped us improve the maintenance status of critical Rust projects and make significant progress on several long-awaited features, such as allocators, the never type, the next trait solver or the Polonius borrow checker. However, only a fraction of people working on Rust are currently funded for their work.

We know that there are Rust users, both individuals and companies, who would like to help improve Rust by funding it, but it might not always be obvious how exactly to do that. This post thus provides suggestions on how you can support the development of Rust in three ways.

If you're unsure which option fits, or would like to discuss funding on behalf of your company, please contact the Funding team.

Maintenance is a continuous process required to keep Rust (or any software project for that matter) working. It consists of two main activities. The first is general housekeeping, such as ensuring that Continuous Integration works, dependencies are kept up-to-date and issues, bugs and security incidents are promptly triaged and resolved. The second is performing refactorings and code reviews, which ensures that the codebase will be able to evolve and continuously ship new features, without accruing extensive technical debt.

Having quality maintenance is crucial for the long-term health of Rust, yet it is typically very difficult to find funding for it; funders often want to sponsor specific new features, rather than just "keeping the lights on". However, without sufficient maintenance, it becomes much more difficult, and much slower, to ship new features. Improving the maintenance of Rust thus also helps us ship features and improvements faster, though the effects are sometimes only observable over longer periods of time.

Funding maintenance is a great choice if you want to let us decide how best to improve Rust. The Rust Funding team continuously looks for Rust teams and projects that require help with their maintenance efforts, and allocates available funds to Rust maintainers who could help improve the situation.

To fund Rust maintainers, consider donating to the Rust Foundation Maintainers Fund or sponsoring the RustNL Maintainers Team.

There are always many Rust improvements and new features that are in progress. We track some of those initiatives through Rust Project Goals. Each Goal describes a specific improvement to Rust: what it is, who is going to develop and drive it forward and which Rust teams are willing to help reviewing and maintaining it.

Some of those Goals are looking for funding. Either to help their owner dedicate time and focus to push the given feature forward, or to fund maintainers who will perform refactorings necessary to unblock that feature and review its implementation. Often funding is required for both. When a Goal is properly funded, the probability that it will achieve its milestones is much higher, which then translates in the given improvement being shipped sooner to Rust users.

Funding Project Goals is a great choice if you want to help push forward specific Rust features or Rust toolchain improvements that will benefit you or your company.

To fund contributors working on Project Goals, consider taking a look at Goals that need funding and reaching out to their funding contact. If in doubt how to proceed, reach out to the Rust Funding team.

There are hundreds of people in the Rust Project who continuously work on improving Rust. Some of them have personal fundraising profiles (e.g. on GitHub Sponsors), which allows you to support them directly.

There might be various reasons for supporting a specific person. Maybe they are maintaining a crate that you love to use, maybe you like reading their blog posts, or maybe you are simply a fan of the work that they do. Whatever the reason, we are sure that they would appreciate your support!

Funding individual contributors is a great choice if you want to directly support Rust contributors whose work you appreciate.

To fund individual Rust contributors, check out their GitHub profile or personal website to see what options there are for supporting them. You can also examine our list of Rust Project members who can be supported through GitHub Sponsors[1].

We hope that this post is useful to anyone who would potentially like to invest funds into making Rust better. You can also find a shortened version of the "how to fund Rust guide" at the Funding page of the Rust website, or check out a RustConf 2026 talk by Niko Matsakis about how Project Goals and their funding works.

If you are a company looking to fund the development of Rust, consider joining the Rust Commercial Network. Joining the network is free, and Rust Foundation membership is not required. It can help you find opportunities for funding improvements in specific areas related to Rust usage (e.g. user interfaces, language interop, supply chain security, etc.) and collaborate on funding Rust development with other companies.

There are of course other ways of helping Rust other than donating funds. For example, you can check out Project Goals that are looking for contributors or more generally check our contributor onboarding guide. Companies can also help by giving employees paid time to contribute upstream, or by hiring Rust contributors to do that work. One possible model is the Engineer in Residence role, that was recently established in the Rust Foundation.

Note that this list is not exhaustive; there are some Project members who accept donations through GitHub Sponsors (or another fundraising platform), but did not opt into being listed on this page. ↩
